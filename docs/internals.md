# 内部设计

用法看 [README](../README.md)，本地流程看 [development.md](development.md)。这里放「为什么是现在这样」。

## 迁移会话为什么不是「改一个字段」

DSH 里「会话属于哪个工作区」不是可改字段，而是由会话日志 header 的 `cwd` 推导出来的：

- 宿主用 `projectKey(cwd)` 决定日志所在目录：`<root>/<projectKey(cwd)>/<encodeSegment(id)>/`
- 加载时校验「文件所在项目目录 == `projectKey(header.cwd)`」，不一致即抛
  `corrupt session log … header id and cwd identify …`——**硬失败，不是降级**
- `@deepseek-ai/dsh-workspace` 的 README 明确写着「来自其他目录的会话无法移入」，且公开 API
  （`create` / `get` / `list` / `delete` / `insertBefore` / `archiveSession` / `resolveByPath`）
  **没有任何 reassign / move**

所以迁移必须是三件事同时一致地做：**改 header cwd + 移动日志目录 + 改工作区注册表**。
少做一件，要么会话加载不了，要么它变成 Ungrouped。

## 多帧 zstd：把静默数据丢失变成启动期硬失败

宿主按「一条事件一次 flush」追加写日志，磁盘上的 `.zstd` 因此是**多帧拼接**（实测单文件可达上千帧，
最大见过 6.5MB 压缩 / 33MB 明文 / 1962 帧）。而 `node:zlib` 的 `zstdDecompress(Sync)` /
`createZstdDecompress` **只解第一帧、其余静默丢弃**，连截断帧都不报错——只解首帧就只剩 session 头
那一行，整个会话看起来「没有内容」。

这个坑在本仓库的开发过程中**真的发生过一次**（21 个日志被截成 ~180 字节），靠执行前的字节级备份才
完整恢复。因此这里不是写注释提醒，而是让它变成硬失败：

- 解码器由调用方注入，核心层自己**不挑**解码器；
- `assertMultiFrameAware()` 构造两个 raw 帧、期望读回 `"AB"`，只解首帧的解码器会让它抛错；
- 回归用例里**直接用 `node:zlib` 验证这条守卫确实会拒绝它**。

## 只重写第一个 frame

改写时只重新压缩**首个 frame**，其余 frame 字节**原样保留**。三个理由：

1. 产出结构与宿主自己写出的多帧布局一致，任何能读宿主日志的解码器都能读；
2. 尾部在字节层面可审计地不变（端到端用例逐行比对，回滚后逐字节断言还原）；
3. 最省——一条 1.8MB 的日志只需重新压缩 ~180 字节。

首帧边界**不靠猜魔数**（压缩载荷里可能偶然出现魔术字节）：先用魔数出现的位置（外加文件尾）收窄
候选，再在候选里取最小的偏移 `i` 使

```
decodeAll(buf[0..i)) + decodeAll(buf[i..)) === decodeAll(buf)
```

且前半段是完整的行。截断帧会被解码器抛错或被该等式排除。可解码的输入恒有切分（`i = buf.length`
退化为整份单帧），所以 `null` 分支对可解码输入不可达——这是有意的保守设计，不是遗漏。

## 写侧为什么零依赖

`fzstd` 只能解压、不能压缩；`node:zlib` 内置 zstd 有 Node 版本下限（本包 `engines.node` 写的是 `^22.19.0 || >=24.0.0`，
按 Node 的 zstd 支持时间线，内置 zstd 大约从 22.15 / 23.8 才有）。两者都不能作为写侧依赖。

`encodeRawFrame()` 因此手写了一个只含单个 **raw（未压缩）block** 的合法 zstd 帧
（Single_Segment=1、Block_Type=Raw、无校验和），代价是首帧不压缩——而首帧本来就只有一个 header 行，
压缩收益可忽略。这样写侧不依赖任何压缩器、外部二进制或 Node 版本特性。

## 启动不变式：违反就是启动直接报错

宿主的 `WorkspaceRegistry` 在启动时走 `validateStoredState()` 校验已存状态，以下任一都让**启动失败**
（不是静默降级，报的是 `workspace domain is inconsistent: …`）：

- 两个 workspace 记录的 `path` 相同
- 同一个 `sessionId` 出现在多个工作区注册表里
- `global.workspaceIds` 有重复
- `global.workspaceIds` 的集合 != `tables.workspaces` 的键集合（顺序漂移）

`validateRegistry()` 复刻这四条，`reHome()` 在操作**前**与操作**后**各校验一次，因此不可能产出
让宿启动失败的注册表。

## 有损编码的碰撞

`projectKey` 把 `/`、`\`、`:` 折叠成 `-` 并截断到 251 字符，所以 `C:\x\y` 与 `C:\x-y` 编码结果
**相同**，而宿主的 `realpath` 唯一性检查抓不到这种碰撞。计划层因此在动手前显式检查源/目标项目目录名
是否相同，`detectProjectKeyCollision()` 作为通用工具暴露。

## 产物的证据分层，与两个必须做的收窄

「这个会话创建了哪些文件」只有强弱不同的证据：

| 证据 | 强度 | 语义 |
|---|---|---|
| `write` 工具的 `file_path` | 权威 | 创建 |
| `deliverables/presented` | 权威 | 主动交付 |
| `edit` 工具的 `file_path` | 权威 | 修改（非创建） |
| `pwsh`/`bash` 命令里的造物路径 | 启发式 | 需含造物动词才计为候选 |

不做收窄的计划会很难用，因此有两道：

- **与磁盘存在性求交**——实测 51 个候选里 39 个早已被会话自己删掉；
- **嵌套剪枝**——某目录要整体搬走时，它内部的文件不再单独搬一遍。

## 生效模式：为什么改了注册表可能要重启 DSH

`WorkspaceRegistry` 持有**内存**注册表与一个 header 索引，而重建该索引的 `replaceHeaderIndex`
是**私有**方法。于是绕过宿主直接改写 `workspace.json` 之后（这条路径以前主要来自已删掉的离线
CLI，现在主要来自本插件自己的落盘）：

- 注册表会被宿主的旧内存副本覆盖；
- 即使不覆盖，宿主的索引仍是旧的，被搬走的会话会被过滤成 Ungrouped。

`effectMode(ctx)` 因此**如实探测**：上游若提供 `workspaceRegistry.reassignSessions` 就走进程内
即时生效，否则返回 `restart-required`，由工具返回值告诉调用方「必须重启 DSH」。不假装即时生效。

## `.dshsess` 包：一条 gzip 流，而不是 tar

容器是「magic + 清单 + 原始载荷」拼起来再整包 gzip：

```
gzip( 'DSHSESS1\n' | u32le 清单长度 | 清单 JSON | 各文件的原始字节 )
```

后缀与开头那串魔法字节是同一件事的两种说法：`DSHSESS1` 与 `.dshsess`（DSH + sessions）。这层
一致性值得钉住，因为**只错在文案上也会把功能弄坏**：客户端的导入框曾带着 `accept=".dhsess"`，
而宿主导出的文件名一直是 `.dshsess`——选择框的过滤器把刚导出的包挡在外面，用户看到的是"导入坏了"。
所以 `test/client.test.mjs` 里有一条专门断言产物里不再出现那个少一个字母的后缀。

三个取舍：

- **不用 tar**：这里只需要「清单 + 一段连续载荷」，而 tar 的 512 字节头、路径长度限制与 PAX
  扩展在这个固定用途上全是负担。tar 换来的好处（`tar -xf` 就能拆）在这里也不成立——拆出来
  的单帧文件本身还得按宿主的目录布局摆回去。
- **载荷是原始日志字节，不重新编码**：日志内部本来就是 zstd 帧。解了再压会让「导出的东西」
  与「磁盘上的东西」不再是一回事，而本包的立足点正是字节级可复原。
- **整包 gzip，而不是逐文件压**：日志的 zstd 帧大多已是压缩态，逐文件再压收益接近零，却把
  「解出来看一眼」变成要写代码的事；整包 gzip 对**迁移重写过的 raw-block 帧**（未压缩）是
  实打实的收益，对已压缩的也只是几十字节。

`readBundle()` 在导入之前逐条校验，任何一条不过就直接拒绝，坏包进不了会话库：

| 校验 | 挡下什么 |
|---|---|
| magic 与 `formatVersion` | 不是 `.dshsess`、或是换代后本包读不懂的包 |
| 每个条目的 `[offset, offset+bytes)` 落在载荷内 | 清单被改坏、偏移溢出 |
| 每个条目的 sha256 | 载荷被截断或改动了一个字节 |
| 会话目录名 == `encodeSegment(id)` | 宿主启动时会校验目录名与 header id 一致，不满足的包会污染会话库 |

## 导入为什么「只跳过、不覆盖」

导入是**跨实例**的操作：同一个 id 在源库里是唯一的一条会话，在目标库里可能已经存在（曾经导过、
或本来就是同一台机器）。三种处理里，覆盖最危险（会顶掉目标库里那条会话的历史），合并语义上不可
判定（两条日志没有共同的祖先），所以这里只留一条：**冲突只报告**。预演里那条会话标成 skip 并附上
它在库里的位置，落地时创建数为 0 就直接 409。

无 cwd 的会话（`_no-cwd` 项目目录）同样不硬塞：保持没有 cwd、不参与注册表重挂。给它编一个 cwd 会让
header 声称一个它从未工作过的目录。

落地时每个文件先写成 `<规范名>.part` 再 rename：`parseSessionLogName` 不认 `.part`，所以中途
崩溃留下的是「发现阶段会忽略的文件」，而不是一个只有半截日志、看起来却正常的会话。

## 同一份迁移编排，两个入口

迁移这件事有两个入口：模型工具（4 个里的 3 个）与设置里的「会话管理 → 迁移」分页。
它们的**编排只有一份**（`src/migrate.ts`：预演 / 执行 / 回滚 / 备份清单），各入口只负责把结果
翻译成自己的形状。不这样做的代价不是"多写点代码"，而是**同一件事在两个地方给出两种说法**：
工具说"会迁移 3 条"，界面说"会迁移 4 条"，用户就没有理由相信任何一个。

**这里原本还有第三个入口：离线 CLI（`src/cli.ts` → `lib/cli.js`，附 bin）。** 它带来的东西只有
一件：DSH 没启动时也能搬会话。另外两个入口各有覆盖面——工具层覆盖"让模型先预演再落盘"，设置页
覆盖"人自己点着看预演"。删除的收益是实打实的：少一份命令行解析与退出码约定、少一个 `bin` 与
`./cli` 导出（都是对外契约，改一次就要兼容一次）、少一份要跟着改的文档。要恢复离线能力，正确的
位置是**另起一个不依赖宿主进程的入口**，而不是把 CLI 塞回这个包里。

同一条原则落在两处细节上：

- **界面与工具调的是同一个 `runMigration()`**，`apply:false` 就是预演。所以"预览和实做不一致"
  在这种结构下不可能发生——它们本来就是同一次计算，只是一个不落盘。
- **注册表的前置校验（`loadRegistryForWrite`）在这条链路的最前面**：注册表不满足启动不变式时
  一律拒绝，而不是"先在坏注册表上叠一层改动，回头再说"。

界面这一侧另加一条**越界拒绝**：回滚只认 `backupRoot` 下面的目录（`assertBackupDir`）。回滚会按
清单里的路径搬目录、按字节还原日志、恢复注册表，等于"以清单为准的任意写"；界面能传的字符串
不该换来这种权力，所以路径检查放在宿主侧，而不是指望前端不乱传。

最后是一个容易被忽略的对称性：`applyPlan` 会删掉空掉的**源**项目目录（`execute.ts` 第 5 步），
回滚如果不对称地做，就会在会话根下留下一个空目录。`rollback()` 因此也删空掉的**目标**项目目录
（只删确认为空的），`test/migrate.test.ts` 把这条钉住了。

**"只迁其中几条"的边界在来源，不在界面**：一次请求只处理**一个来源**——一个源目录（源项目目录由 `from`
决定），或者跨目录的「未分组」（源项目目录由**每条会话自己的 `cwd`** 定，见下一节）。`sessionIds` 只做
子集筛选——所以界面列的会话**只是勾选面**，真正搬哪些由宿主按来源里的实际内容算。
两个后果是刻意的：点名的会话不在这个来源的候选里时预演直接报 problem（不静默少搬，未分组来源下
"在册的"或"没有 cwd 的"会话就落在这里）；`reHome` 只摘走被点名的
id，**源工作区只有在被搬空时才从注册表上删掉**——搬走一半却把整条工作区记录删了，等于让剩下那几条
会话变成孤儿。`test/migrate.test.ts`（编排层）与 `test/web.test.ts`（端点层）各钉了一条。

来源是「未分组」时，上面那条"搬空就删项目目录"的口径从**一个目录**变成**每条会话各自的目录**：执行阶段按
`sessions[].sourceDir` 的父目录去重后逐个检查空不空（单目录来源下这就是同一个项目目录，行为与以前等价），
目标项目目录永远跳过不删——`cwd` 已经在目标上的那些会话本来就住在那里。`test/unowned.test.ts` 用一个
"三个目录 + 一条无 cwd 老会话"的沙箱把这条钉住：只搬空的那两个项目目录被删，还留着在册会话的那个项目目录必须
保住。

## 浏览器半侧的产物与依赖约束

**一、产物必须是一个经典脚本。** DSH 的[客户端模块系统](https://deepseek-harness.github.io/deepseek-harness/reference/subsystems/client-modules)
只认 `window.__ModuleLoader__.load({ id, factory })` 这种方式报名的脚本，工厂拿到一个同步的
`require`，返回的 `module.exports` 就是插件的导出面（`inject` 与 `apply`）。因此 tsdown 的
client 一份配置是 `format: 'cjs'` 外面套三行（banner/intro/footer），只有平台基线模块保持
`require`，其余一律内联——客户端模块系统没有旁挂依赖的路由。`test/client.test.mjs` 用假的加载器与
假 `require` 按这份契约执行 `lib/client.js`：契约错了在源码层面看不出来，只有跑一遍产物才知道。

**二、控件走官方控件库，不手写。** 基线模块有三个：`react`、`react/jsx-runtime`，以及
[Web Client](https://deepseek-harness.github.io/deepseek-harness/reference/subsystems/web-client)
页点名可以共享的 `@deepseek-ai/dsh-client-ui-primitives`——官方给 Web Client 写的共享 React 原子
组件库（Button / Checkbox / Tag / Switch / Input / Modal / SettingsForm…，zero Cordis）。它是
**平台基线**，用之前不必声明：0.1.7-rc.2 这一代里，官方 60 个 `dsh-client-*` 包中有 46 个的产物
直接 `require` 它，而没有任何一个包把它写进 `dsh.client.external`。本包也已经接上（peer + devDep +
构建外置，见 `tsdown.config.ts` 的 `CLIENT_EXTERNALS`），只是源码还没 import 它——产物里现在仍只有
`require('react')` 与 `require('react/jsx-runtime')`，手写的控件在逐个换掉。它必须保持外置：内联等于
把一份 React 组件复制进包，还会跟宿主那份的 hooks 语义脱钩。官方「包边界」只禁止运行时导入**另一个
功能插件**的值，而 `ui-primitives` 这类"职责收窄、没有功能生命周期"的静态 owner 正是它鼓励共享的那类。

代价是跟上游的版本节奏绑在一起：模块表按 specifier 分发、没有版本协商，控件 API 改了编译期发现
不了。所以 `engines.dsh` 与两个 DSH peer（`@deepseek-ai/dsh-tools`、
`@deepseek-ai/dsh-client-ui-primitives`）都写 `^0.1.7-rc.2`（`@deepseek-ai/cordis` 按自己那条线写
`^4.0.4`），同代副本进 `devDependencies` 供构建，版本对不上时拦在激活；真遇到改名删导出，`Slot` 条目
会渲染成一个空 `div`（控制台里是
`slot entry crashed in '<slot>'`），用户看到的是空白而不是错误。

颜色的纪律不因控件库而变：只用 `Theme` 检查面列出的 `--dsw-alias-*` token（每个都带中性回落值，
深浅主题自动跟随），类名收在自己的 `dsm-` 前缀下。

那条"只用检查面的 token"不是洁癖，是踩过的坑：**颜色写死只会在一种主题下错**。真事是
`.dsm-primary` 写死 `color: #fff`——浅色主题下 `brand-primary` 是近黑（白字没问题），深色主题下它
是 `--dsw-static-neutral-bluish-50` 的 **#f9fafb**（近白，因为它是"表面的反色"，不是为了当填充色
才存在），于是白底白字、对比度 1.05:1，按钮上的字整个没了。类型、产物冒烟、真实 profile 的 HTTP
核对全都抓不到这种错，只有肉眼能发现。现在 `.dsm-primary` 的字色走
`var(--dsw-alias-label-primary-foreground, var(--dsw-alias-bg-layer-1, #fff))`：检查面没给这个位置
token，所以显式挂了回落链（拿不到就退到表面色——brand-primary 在明暗两套里都是表面的反色）。
同一类的还有悬停底色：`bg-layer-3` 在浅色主题里就是 #fff，铺在白卡片上等于没有反馈，改成把
`label-primary` 兑 8% 透明的薄雾（宿主外壳自己也这么兑）。还有**state 色**：那四个
`state-*-primary` 是"指示色"（点、边框、淡填充），色值本身没按文字对比度选，当小字颜色用就会
在一种主题下淡到看不见——浏览器里量到的：`state-idle-primary` 是 #d4d4d4，白底 **1.48:1**；
深色主题里它是 #545557，在 #232324 上 **2.1:1**；`state-warn-primary` 是 #f59e0b，白底 **2.15:1**。
所以文字一律走 `label-*`（浅 5.8:1 / 深 10.4:1），state 色只留在边框和一层淡填充上；非当文字色
不可时就 `color-mix(in srgb, …, 55%, label-primary)` 兑一下：亮色主题往深里走、深色主题往浅里走，
**同一条声明在两套主题里各自走向可读的一侧**（实测 warn 5.57:1 / error 9.75:1 / ok 5.82:1）。

这五条纪律由 `test/styles.test.mjs` 机械核对（颜色必须走 token、token 必须在名单里、token 必须带
回落值、标签不许折行、state 色不许裸当文字色），反事实都验过会失败。**上面这些比值是浏览器里量
出来的，不是推的**：`agent-browser` 打开真实的设置页，逐个元素取 `getComputedStyle` 的前景色，
背景色沿祖先链一路 `color-mix` 合成到不透明为止，再按 WCAG 相对亮度算比值，明暗两套主题各跑一遍
（换主题可以在设置里点「深色 / 浅色」，也可以把主题设成「跟随系统」后 `agent-browser set media dark`，
页面认 `prefers-color-scheme`）。对比度推不出来——它
取决于宿主**当时**给的那套 token 值，只有量了才知道。

**页头是这条纪律的延长线，也是踩过的坑**：官方设置页的页头**没有原语可用**——
`dsh-client-ui-settings-plugins`（「插件」那一页）自己手写 `h2` + `p`，用打包哈希的类名
（`pbvGtq_section` / `pbvGtq_heading` / `pbvGtq_intro`）写本地 CSS。那份类名与那个功能插件包都不该
复用，所以规格只能**去真实设置页里量**：`h2` 18px/600 的标题独占一行，下面隔 12px 跟一行 13px 的
说明行，整体是 `display:flex; flex-direction:column; gap:12px`。这里原先写成 14px 的 `span` 加一行
`row` 布局，一眼就能看出"和内置插件那页不是一套"。说明行的颜色是 `--dsw-alias-label-tertiary`
（浅色主题 **#81858c**，量的就是那一页 `p` 说明行的计算色），而检查面只列到 `label-secondary`
（#61666b，深一档）——所以它进了
`test/styles.test.mjs` 的例外表并带回落链。规格现在有两处钉着：`test/styles.test.mjs` 查
`font-size/flex-direction/说明行的 token`，`test/client.test.mjs` 查结构（标题必须是 `h2`、
说明必须是 `p`、说明不在标题行里）。

**版面上还有一条同类纪律：一句说明别挂在"会被滚动条挪动的边上"。** 坑出在「会话」页筛选条末尾那句
「多选＝任一命中」：起先用 `spacer` 顶到右端，它的位置就等于容器的右边缘——设置弹窗内容区那条滚动条
一进一出，内容宽度变 15px，这句话跟着平移（这台机器的 Chrome 滚动条不占位，量到的位移是 9px；装了
占位滚动条的环境是 15px）。改成紧跟胶囊的同一行，横向是稳了，可那一行只剩三十来 px 的余量，容器再窄
一点就整行换行、句子跳一行。现在它自己占一行（`<p>`，在 `.dsm-filters` 后面）：左边固定不动，胶囊那
一行的余量也一下宽出九十来 px——同样的刺激下换行阈值从 30px 变成 135px，一次滚动条切换越不过去。
`.dsm-list` 另加了 `scrollbar-gutter: stable`：装了占位滚动条的环境里，列表溢出与否都不再改变行宽。

**根子在"这一页的高度会随筛选变"**：列表以前是 `max-height`，筛掉行就变矮，整页跟着变矮，外层那条
滚动条于是在"有"与"没有"之间切——占位滚动条的环境里，它每切一次就把整个卡片的右边缘挪 15px，卡头
按钮、行里右对齐的字节与时间全跟着跳。所以列表高度改成**固定**（`height: min(420px, 42vh)`），
"一条都没筛出来"的空态也画在那个框**里面**（换成框的兄弟就等于把框撤了，高度又变回去）。真实
GUI 里量到的：35 行 / 5 行 / 1 行三种状态下列表框都是 242px、卡片都是 608px、外层滚动容器的
`scrollHeight` 都是 760px——外层滚动条再也不会因为筛选而切换。代价是筛完只剩几行时框里留一块空。

头两条（说明句自己一行、空态画在框里）在 `test/client.test.mjs` 里按结构钉住——位置本身在这种
环境里量不出来，但"又挤回那一行""空态又把框撤了"这两个退化会被抓住。

注册进 `settings.section`：设置左侧导航里的一页，与「通用 / 模型 / 插件 / 账户 / Agent 预设」
并列，`order: 30` 排它们之后（这一形态的官方说明：[新增设置卡片](https://deepseek-harness.github.io/deepseek-harness/reference/cookbook/adding-a-settings-card)，
那里也把插件包的两侧叫 **Host 半侧** / **浏览器半侧**）。相近的 Slot 有两个，各有一个真问题，所以都没选：

- `plugins.detail.section`（插件详情页配置/行列表之后的一段）：归属感最贴，但要按 subject
  （`item` / `row` / `bundle`）自过滤，而判断依据是**包在插件管理器里的表示形态**；猜错不报错、
  只是永远不渲染——静默空白最难发现。它还会在包内每一行的页面上各渲染一次，而本页要的是整页宽高。
- `settings.plugins.tab`（「插件」设置区里的一个页签）：那条页签栏的语义是「插件列表的视图」，
  一个功能页挤进去属于借位。

注册走 `ctx.slots.inject(slot, () => ctx.slots.register(...))` 而不是直接 register：目标 Slot
由设置外壳在运行时声明，那个声明完全可能晚于本插件 `apply`。`label` 给的是 thunk：外壳投影
导航行时走 `resolveSlotLabel`（是函数就调用），并且订阅了 locale 快照，所以切语言或后到的
字典都会让那一行重新投影，不必自己重新注册——`test/client.test.mjs` 把这条也钉住了。

## 导出列表为什么按目录分组，而不是按「工作区」分组

要带走一批会话时，人的说法永远是"把这个工作区的会话都带走"，所以列表得一组一组地给，并且组头
就是整组勾选。**分组键取的是目录（`cwd`），不是注册表里的工作区 id**，因为这两件事经常不是一回事：
注册表的 `sessionIds` 只是"登记在册"的那部分。真实库里就能看到这个差：写这份文档时
`~/dev/dsh-session-manager` 注册表登记 5 条、目录里实际 7 条（多出来的 2 条没被任何工作区登记），
`~/test` 登记 5 条、实际 6 条——两边的数都随本机使用漂移，要紧的是"登记条数会少于目录里的会话数"。
按工作区 id 分组会同时犯两个错——
把一个目录劈成"工作区"与"未登记"两组，而且两组都不是用户想带走的那一批。按目录分组天然把它们
合成一批，工作区标题只是这个路径的**标签**（登记过才有；没登记的目录直接显示路径并标出来）。

### 外壳侧边栏那个「未分组」是什么

它就是同一件事的另一种投影，不是第三个概念：外壳的分组键是**注册表成员表**
（`tables.workspaces[*].sessionIds`），把没被任何工作区登记在册的会话（外壳源码里的 `stray`，
建成 `buildGroup("", undefined, …)`，所以那一行的 DOM 键是 `workspace:` 后面空着）收进一行，
标题取字典里的 `group.ungrouped`。**同一条会话在这里、不在那里是正常的**，本机就有实例：
`session-aaa2ebd1…`（「dsh-session-manager 使用说明」）的 `cwd` 是 `~/test`，但它的 id
不在任何 `sessionIds` 里 —— 侧边栏把它挂在「未分组」下，本插件把它挂在 `test` 组里。

两边的差别一共三处，别把它们混成一个：

1. **分组键**：成员表 vs 目录（`cwd`）；
2. **可见性**：外壳按 `sessionVisible` 隐藏三类会话——子代理（`origin === "subagent"`，它被挂在
   父会话下面，不是没有位置）、空白会话（一个 turn 都没开始过，当前那条临时 New Session 除外）与
   已归档会话（默认过滤）。本插件的导出列表照单全收——"这条会话要不要带走"是人的决定，替人预先
   藏起来只会让"我明明有这条会话"变成找不着的谜；迁移的候选与「会话」页则跟外壳对齐（下一节）；
3. **残余项的粒度**：外壳的「未分组」是一个可以横跨多个目录的残余分组；本插件的每一组必须**是一个
   真实目录**（勾组头 = 带走那个目录；迁移页的源目录下拉框也要一个具体路径可显示）。

所以"为什么导出界面没有「未分组」"的答案是：那一组既不是目录、也不是一个可以整批带走的实体，
而「未分组」这件事本身在迁移页有个正经出口（`includeUnowned` 复选框），不需要在这里再造一组。

但差异不该只活在文档里：导出列表给这些行挂一枚「未分组」小标签（判据就是 `SessionSummary.workspaceId`
缺省——宿主在 `/state` 里早就按成员表填好了这个字段，此前一直没人用），悬浮提示里点明"外壳侧边栏把这类
会话挂到「未分组」下"。这样"那边有一条、这边没有这一组"在界面上就能自证，不必让人对着两个界面猜。
标签是**逐行**的，不能按组一刀切：真实库里同一个已登记目录下就混着登记在册与没登记在册的会话
（组头的条数会大于注册表里的登记数，差额就在这几行上）。这一行也因此从"网格的一格"变成"一格里的 flex 行"，
名字单行省略、标签 `flex: none` 不被压变形——细节写在 `styles.ts` 的 `.dsm-rowLabel` 注释里，
`test/client.test.mjs` 按行核了标签挂给谁。

### 迁移页为什么把「未分组」当独立来源（传输页却不行）

上面那条"导出列表不能再造一组"的理由是**组头的语义**：勾一个组头 = 带走那个目录，组头必须是一个
可以整批带走的实体。迁移页没有这层约束——它的源是一个值控件（下拉框自己就是那个值），旁边还有
"只迁其中几条"的子集模式，所以"这一批不是目录"不构成障碍。反过来说，那批会话**恰恰需要**一个
独立来源：它们可以横跨多个目录，一个目录一个目录地勾，谁也说不清"这两个目录里没在册的那两条"
是一件事。

四种口径因此被钉在一起，少一条就会出现"界面说 2 条、宿主说 3 条"：

- **候选**：`unowned` + `workspaceId === undefined` + **有 `cwd`**（`planRows.unownedSessions()` 与
  `plan.ts` 的发现阶段是同一条判据）。没有 `cwd` 的老会话排除在外不是偷懒：迁移要改写 header 里的
  `cwd`，而 `relocateHeaderCwd()` 明确拒绝一个没有 `cwd` 的 header（换来的是"绝不凭空造一个 cwd"）。
- **请求**：界面上的哨兵值 `@unowned`（`planRows.UNOWNED_SOURCE`）在发请求那一刻被翻译成
  `unowned: true` + `from: ''`；哨兵既不下线也不当文案露出来（下拉框那一行自带文案，输入框里显示的
  也是"未分组"）。
- **计划**：`from` / `sourceProjectDir` 是空串（源不是一个目录），每条会话各自的源在 `sessions[].from` 里；
  `describePlan()` 于是报"横跨 N 个源项目目录"而不是一个假路径。
- **两个被关掉的开关**：「连同未分组的会话」（那批本来就全都没在册）与「搬迁会话产物」
  （产物定位是相对于源目录的，跨目录的源给不出这个基准——显式报 problem，而不是悄悄不搬）。
  界面在这个来源下把这两个复选框换成一句说明，而不是显示成"能点但没用"。

备份清单里这次迁移的 `from` 因此是**缺席**的（界面显示成「—」）：清单里的 `from` 只是给人看的一句
摘要，写一个假路径不如不写；真正的源头在清单的每条会话记录里（`sourceDir` 与 `dirName`，项目目录名从前者推），
回滚只认那些字段——跨目录对回滚是透明的，`test/unowned.test.ts` 跑到 apply → verify → rollback。

这与迁移页选源目录的口径是同一条：那边的候选也是"已登记工作区 **+** 库里真有会话的目录（带条数）"。
几个分页面对同一个库必须给出同一个心智模型，否则用户会在两页之间看到互相矛盾的数字。

落地的细节：已登记的工作区按注册表顺序在前、其余目录按路径排序在后、没有 `cwd` 的一组在最后
（导入把它落进 `_no-cwd` 项目目录且不进注册表，所以它是单独一组，不是某个目录）；组内新会话在前；
空组不出现。组头是个三态勾选框（全选／部分／未选），`indeterminate` 不是能写进 JSX 的属性、
只能在节点上赋值，所以那里用 ref 同步一次——少了这一步，组里勾了一部分时选框画成"空"，
用户会以为自己的操作没生效。规则的边界（顺序、重复路径、空串 cwd、组内定序）都在
`test/groups.test.ts` 里钉着。

### 迁移为什么排除侧边栏不显示的会话

同一台机器上，迁移页的「未分组」报 4 条、外壳侧边栏那一组只显示 1 条——差的 3 条是三种不同的隐藏
理由（一条子代理会话、两条只有 seed 事件的空白会话，其中一条还已归档），而迁移当时把它们都算进了
候选与条数。这类账对不上不能靠"把判据在界面上再抄一遍"解决，于是判据收进一处：`src/visibility.ts`
的 `hiddenReasonOf()`。计划层（`src/plan.ts`）与界面（`src/web.ts` 的 `/state`）读的是同一份结论，
`/state` 把结论作为 `hidden` 字段发给「会话」页，界面只负责显示。

三处输入各自的来源与取舍：

- **子代理**：`header.origin === "subagent"`，发现阶段本来就在解首帧，不额外读盘；
- **已归档**：注册表 `global.archivedSessionIds`；
- **空白**：只有宿主自己知道（它记在投影缓存的 `sessionListMetadata.blank` 里，初始 `true`、
  第一个 `turn/start` 之后翻掉），所以读 `<registryPath 同级的 storages>/session_projcache/sessions/<id>.json`。
  **读不到就按"会显示"处理**（`blank` 缺省 = `false`），与宿主冷会话分支的 `metadata?.blank ?? false`
  同一口径：反过来假设它空白，就会把用户看得见的会话从候选里悄悄拿掉，而"少迁一条"是无声的。
  身份（`createdAt` + `cwd`）对不上也不认——同 id 的另一条生命周期、残留的缓存条目都不算。

命令行那条路（`plan_session_migration`）与界面走的是同一个编排层，空白读取器由 `src/migrate.ts`
按 `registryPath` 反推缓存目录自己造一个，所以"工具说 12 条、界面说 10 条"这种事不会再出现。
点名叫一条隐藏的会话不会被静默忽略，而是如实报
`session <id> is hidden from the host sidebar (<理由>) — migration does not take it`：
"我没选它"和"我选了它但你没动"必须能分辨，`test/hidden.test.ts` 把四种输入逐个钉住。

### 删除为什么先备份、而且不碰注册表

宿主没有"删除一条会话"的能力：`dsh-session-persistence` 那条缝上没有 delete，sqlite 的
`_deleteSession` 是私有的。所以删除只能是本插件做文件系统操作（`src/remove.ts`），而真删用户数据
这件事本身没有第二次机会——于是先往本插件的备份根落一份**整目录**（日志的原始字节 + `session.lock`
+ 任何别的东西）再删，清单标成 `kind: "delete"`。恢复就是把整个目录搬回原位，所以"恢复的字节和删掉
之前一模一样"是结构上成立的，而不是靠逐一列举文件来对齐（`test/remove.test.ts` 连锁文件一起核）。

**删除刻意不动 `workspace.json`**，这一条容易被误当成遗漏：

- 注册表里的悬空 id 是宿主本来就容忍的状态（`Workspace.sessionIds` 会按 header 索引过滤、成员表里
  查不到的 id 直接跳过），删掉目录不会让宿主起不来；
- 反过来，删除时顺手清理注册表就会**覆盖**掉用户在那之后的任何改动（重命名、归档、pin），
  而回滚一份删除备份不需要这些清理——目录回来了，成员表里那条登记本来就还在，归档状态也一样。
  于是回滚删除备份时第 4 步（还原注册表）被显式跳过，动作清单里写着 `registry untouched`，
  界面上那句文案也从「回滚」改成「恢复」。

归档则是**只能走宿主能力**的一条路：`ctx.workspaceRegistry` 的 `archiveSession()` /
`unarchiveSession()` 一次落盘 + 改内存 + 广播，侧边栏即时跟着变。宿主没有这个服务（非 Web profile）
时如实回 409 并说明原因，不绕过去直接写注册表文件——那样写出来的状态与宿主内存不一致，
下次宿主自己落盘就把它盖掉了。

删除**只有界面这一个入口**（4 个工具里没有它）：它要做的是"把人点的那一下忠实做完"，而"让模型自己
决定真删用户数据"是另一件事——要做也得先想清楚权限边界与撤销面，不是把同一个函数挂到工具上就完了。

### 三个分页的列表是同一份实现：行、框、筛选条

行怎么画、勾选框怎么摆、标签挂哪几枚、列表框多高、筛选条长什么样，都只在
`src/client/sessionList.tsx` 里写一遍。写三遍的代价已经付过两次：迁移页那份 `formatTime` 收的是
ISO 串（调用处 `new Date(createdAt).toISOString()` 绕一圈，三份实现里只有它的容错不一样），
"注册表没认领"这枚标签在三页里叫两个名字（「未登记在册」与「未分组」）。**一处逻辑写三遍，改一处
就会漏两处**——所以共用的边界划在一行的解剖结构与列表的框上；各页自己的东西（传输页按目录分组的
组头、会话页的归属那一格与删除计划、迁移页的「全部 / 子集」单选框与备份回滚）留在各页。

三页的列表都**高度固定**（`dsm-listFixed`，理由见 `styles.ts`），并且连"一条都没筛出来"也画在框
里面——否则那个状态会把整页高度改回去，外层滚动条就能再挪动一次整个卡片。

筛选条分两行：上面一排类别胶囊，下面一行是搜索框与那句说明。这是量出来的结论，不是排版偏好：
说明句只要挂在容器右边缘附近（`margin-left: auto` 或 `spacer`），设置弹窗里那条 15px 的滚动条一进
一出就会挪动它（实测旧写法挪 9px）；改成紧跟胶囊同一行仍然不稳（那行只剩三十来 px 余量，实测窄
135px 就整行换行）。两行之后，搜索框与说明句都落在固定的左边界上。

**分组列表能折叠，而且折叠只改"画不画"**：组头最前那个按钮把组内的行收起来，组头自己留着（连着
"这组几条 / 勾了几条"）——收起来的是显示，不是"算不算"。这条界线是刻意的：让折叠把行从"列出来的"
里摘出去，就等于"点一下箭头悄悄改了要导出的东西"，而头部一直报着"显示 N / M 条"，两者一对不上就
是 bug。反过来，组头的条数在收起时也得照报：一个目录收起来之后，"里面有几条、勾了几条"正是最该看见
的信息。列表高度是固定的，所以折叠不会改整页高度（实测 35 行 → 33 行 → 0 行，列表框 242px、卡片
508px、外层 `scrollHeight` 898px、卡头按钮 x 845/927 全都不动）。

折叠标记在组头**最前**（树的惯例：左缘就是"这一组能不能折"的位置），代价是组头的内容整体右移了一个
开关的宽度，组内那些行的缩进得跟着加同样多（`.dsm-group > .dsm-row` 的 `padding-left: 48px` = 4px
内边距 + 20px 开关 + 8px 间距 + 16px），否则组头的勾选框会跑到组内行的右边去，"行挂在组头下面"就反了。
这一档是量着调的：行里的标题因此窄了 22px（实测组头勾选框 x=504、组内行 x=520、标题列 255px）。

组头的结构因此从"一个 label 包住整行"变成"一个 div 装着按钮与 label"：整组勾选那一块仍是 label
（点组头任意一处仍等于勾上／取消整组），折叠按钮留在它外面——label 里放可交互元素（按钮就是）是非法
嵌套（labelable 元素只能是被标注的那一个），点击行为也会两头打架。折叠状态存的是"收起了哪几个路径"
（空集合 = 全展开），键与 React 的 key 都是 `groups.groupKey()`；"全部收起 / 全部展开"只对**眼下
列出来**的那些组生效：没画出来的组是什么状态看不出来，也不必记住。

**三页给的筛选项不一样**，因为三页列的东西不一样：传输页与会话页列**整个库**（隐藏会话也在），
所以五类胶囊都有意义；迁移页列的是**候选**（隐藏会话按设计不进候选），子代理 / 空白 / 已归档在那
页永远是 0，摆出来只会让人以为筛选坏了，于是那页只给搜索框。搜索**标题与 id 都搜**：id 永远在、
标题可能没有（老会话日志里就没有标题事件），"按 id 指名道姓"与"按标题回忆上次那个问题"都是真实
需求，区别只是行上显示哪一个（见 `planRows.sessionLabel`）。关键词与类别是**两条独立的轴**，一起
用时是"与"（搜 foo 且只看空白 = foo 里的空白）。

「未分组」在这套口径下是**一枚类别胶囊**，同时是行上的标签：一个事实一个名字，与外壳侧边栏那一组、
迁移页那个来源同名（会话页那行已经写着"未分组"归属，就不再挂重复的标签）。

### 筛选条按"它是什么"判，不按"它显示成哪枚标签"判

行上会挂标签（子代理 / 空白 / 已归档 / 活动中），筛选条也按这几类筛。两者共用一套**事实**
字段（`origin` / `blank` / `archived` / `live`，见 `src/client/sessionFilter.ts`），而不是共用 `/state`
里那个 `hidden`：

- `hidden` 只报**宿主先判的那一条**理由（一条会话既是空白又已归档时是 `blank`）——它回答的是"侧边栏
  为什么不显示它"，与宿主 `sessionVisible()` 的顺序一致，这个口径不能动；
- 但筛选与标签问的是"这条会话**是什么**"。按 `hidden` 筛「已归档」，那条空白+已归档的会话就筛不出来
  了；按 `hidden` 挂标签，用户会看到"筛了归档，却有几行没有归档标签"。所以标签**能挂几枚挂几枚**，
  筛选读原始事实，两边自洽。

其余三条是刻意的：**多选＝任一命中**（这几类两两之间本来就很少同时成立，做成"全都要命中"的话，勾
第二枚时列表多半直接空了，"把这几类都摆出来"才是勾选面的直觉）；**每类的条数对整个库数**，不随当前
筛选跳（会跳的计数没人信得过）；**「全选」选的是眼下列出来的那些**（筛出空白再一键全选，要的就是删
它们；传输页的「全选整库」同理，筛着的时候"整库"就是眼前这一批），而已经勾上的不会因为切换筛选而
丢——头部一直报着"已选几条"，与列表看到什么无关。

各页的筛选状态与勾选集都是**页内状态**，所以切到别的分页再回来会清空（分页是挂载 / 卸载的）。
这不是这次改动的取舍，而是这一页骨架一直以来的样子——只是筛选条多了之后更容易被注意到。要留住它
得把状态提到骨架那一层，那是另一件事，没做。

## 两级怎么在一眼之内分开：组头是工作区，缩进的行是会话

分组本身只解决了"哪些会话是一批"，没解决"哪一行是工作区、哪一行是会话"。这两件事在同一个列表里
必须一眼分得开，因为**会话标题是用户自己写的第一句话**，它长得像个目录名是常事——本机就有一条叫
「dsh-session-manager 使用说明」的会话，跟组头「dsh-session-manager」并排时，只靠读字是分不出来的。

所以两级的区分叠了四层，任何一层失效（换个主题、换块屏幕、色觉不同）都还有别的手段兜住：

| 层 | 组头（工作区） | 会话行 |
|---|---|---|
| 底色 | 字色薄雾 12% 兑在卡片表面上，一条不透明的实心横幅 | 卡片表面色（悬停时才兑 6% 的薄雾） |
| 缩进 | 贴列表左缘 | 整行缩进 26px，左缘一条 2px 导引线逐行相接 |
| 字号 | 14px / 600 | 13px / 400（跟页面正文一致） |
| 图形 | 文件夹（`dsm-levelWorkspace`） | 对话气泡（`dsm-levelSession`） |

为什么不靠"底色再深一点"单独扛：浅色主题里 `bg-layer-1/2/3` 是**同一个白**，能用的只有"字色兑出来的
薄雾"，而薄雾的可见度本来就依赖屏幕与视力。缩进、字号、图形这三层跟颜色无关，是层次的**主承重**。
图形两个轮廓自己内联在 [src/client/icons.tsx](../src/client/icons.tsx) 里（`currentColor`，不引图标包、
不加资源），因为宿主的图标包是打包器哈希过的私有产物；设置导航那一行的图标改不掉这件事见
[src/client/index.ts](../src/client/index.ts) 顶上的注释。

组头是 `nowrap` 的一条，右边那两串数字（这组几条 / 选中几条）是**一整块**：让位的必须是路径
（`flex-basis: 0`，先截断，悬浮提示补全），不是折行。这不是洁癖——本次改之前正是 `wrap`，路径一长
数字就被挤到第二行，组头长成两行、数字跑到左边，看着像坏了（532px 宽的列表里真实发生过）。

这四层都在 `test/client.test.mjs`（两级各挂各的标记、组头仍是整组勾选的入口、计数块是一整块）与
`test/styles.test.mjs`（颜色只走 token）里钉着。

## 界面里的目录字段：一个值控件，加一条按能力选的路

源目录与目标目录都是**任意绝对路径**：源是「会话日志里那个 `cwd` 字符串」，目标是「你想搬到哪儿，
那个目录可能还没登记过」。这排除了"只能用下拉框"的写法（列表列不全），也排除了"下拉框只负责把
路径填进另一个文本框"的写法（那是把命令化装成控件：框里永远显示占位符，看着像没选中，而真正生效的
值在别处）。落地的形状是**一个值控件 + 三条改值的路**：

- 下拉框自己就是那个值（`value={from}` / `value={to}`），候选＝已登记工作区 **+ 库里真有会话的
  目录**（后者带条数——注册表的登记条数会骗人，同一个目录下可能有没登记在册的会话）；
- **当前值永远在候选里**：值可能是「浏览…」选回来的、注册表与会话都没覆盖到的目录，补这一行之后
  框里显示的永远就是将要用的（否则设置过值也只显示占位符）；
- **「手输路径」**是万能兜底：展开一个和下拉框同值的文本框。宿主没有目录选择器、或要在
  候选之外敲一个路径时，它是唯一的路，所以它对每个宿主都在，且只换控件不改语义（两边都是同一个值）；
- **「浏览…」的行为由宿主报来的能力种类决定**，见下。

### 「浏览…」为什么不能直接调 `uiWorkspace.pickDirectory()`

宿主的目录选择器（`@deepseek-ai/dsh-host-directory-picker`）是一只**互斥的能力位**服务：
`capability()` 返回 `{ kind: 'native', ... }` 时**只**提供 `pick()`（在宿主显示器上弹系统对话框），
返回 `{ kind: 'browse', ... }` 时**只**提供 `list()`/`createDirectory()`（页面自己画浏览器）。
`dsh-api-workspace-controller` 在协议层就把两者分开了：浏览器界面这一侧的 profile 装的是
`dsh-client-ui-directory-picker-browse`，即 `browse` 那一只——此时硬调 `pickDirectory()` 一定被宿主
以 `directory-picker/unavailable`（`… needs the native capability; the composed picker serves
"browse"`）拒绝。也就是说，**"「浏览…」调 `pickDirectory()`"这个写法在浏览器里是必错的**：
桌面端能用，正是这一点让它在开发机上不容易被察觉。宿主文档给出的默认约定也是"认不出的种类就
别显示这个入口，而不是让它失败"。

所以本插件的做法是：

- 宿主侧 `directoryPickerKind(ctx)`（[`src/tools.ts`](../src/tools.ts)）读出 `capability().kind`，
  经 `GET /state` 的 `pickerKind` 字段交给页面；读不到、认不出、或 `capability()` 抛错都退回 `null`；
- 页面按 `pickerKind` 走：`native` → `pick()` 弹系统对话框；`browse` → 页面内展开一个目录浏览框
  （[`src/client/DirectoryPicker.tsx`](../src/client/DirectoryPicker.tsx)），数据来自宿主的
  `listDirectory()`，每一步跳转用的都是宿主返回的 `path`，本插件不碰文件系统、不猜路径；
- `null`（含旧宿主没有这个字段）→ **不显示**「浏览…」，只留「手输路径」+ 候选列表，并给一句说明。

原则一句话：**不摆一个一定会报错的按钮**。选择器返回值先削掉结尾斜杠（`normalizePickedPath`）：
会话 `cwd` 与注册表路径都不带结尾斜杠，`/a/b/` 会凭空多出一个「不同的项目目录」，匹配不到任何会话。

`uiWorkspace` 在客户端同样受"Cordis 服务属性必须声明过 inject 才可读"这条规矩管（见下一节）：
它在别的客户端插件手上，写进本插件顶层 `inject` 就等于"没有它整页都别装"。所以用
`ctx.inject(['uiWorkspace'], cb)` 把两个调用面（`pick` / `list`）收成一个 thunk 存在
[`src/client/directory.ts`](../src/client/directory.ts)，界面点「浏览…」时才取当前那一个——服务晚到
也能用上，服务不在则退回"只有手输路径"的形状。

## 宿主侧的一条硬约束：可选服务只能用 `ctx.get` / `ctx.inject`

Cordis 的 Context 是个 Proxy，**服务属性只有在当前 fiber 的 `inject` 里声明过才可读**，否则同步抛
`cannot get property "X" without inject`——**即使那个服务确实存在**。所以：

- 硬依赖写进 `inject`（本插件是 `tools`）；
- 可选服务（`webServer`、`workspaceRegistry`）走 `ctx.get(name)`，或用 `ctx.inject([name], cb)`
  开一个子 fiber——后者顺带解决顺序问题：服务由别的 bundle 提供、晚于本插件到位时，回调会在它
  到位后跑，端点不会永远缺席；
- 卸载时子 fiber 随父 fiber 一起释放，所以 `ctx.inject` 里注册的路由不需要再手工收集。

这条坑的隐蔽之处在测试里：**根 context（fiber 没有 runtime）走的是非严格路径**，属性读法在
根上、或从根 `provide` 的服务上都能蒙对。纯对象假 ctx 更是完全读得到。本插件因此在真实 profile
里整个起不来（`web-dev` 的日志：`cannot get property "webServer" without inject`），而当时的假
ctx 测试全绿。`test/artifact.test.mjs` 与 `test/tools.test.ts` 现在都在**真实 Cordis 的 fiber 上**、
并由**兄弟** fiber 提供服务，就是为了让这类错误在测试里就炸。

## 设置导航那一行的图标：插件指定不了，只能吃外壳的兜底

「会话管理」在设置左侧导航里和「通用」共用同一个齿轮图标。这**不是本插件写错了**，而是外壳的行为：

- 外壳那张表是硬编码的 id → 图标映射（`dsh-client-ui-settings-general` 的 `navIcon(id)`）：
  `account` → 用户、`models` → 数据、`agent-presets` → 预设、`plugins` → 个性化、
  `archived-sessions` → 归档，**其余一律** `IconSettingsOutlineMedium`（齿轮）；
- `settings.section` 的注册选项只有 `id` / `order` / `label`，没有 `icon`——
  `SettingsSectionOwnerProps` 只给一个 `close`，注册面也捡不到第二个字段。

所以只有两条路：等上游给注册选项加 `icon`（本页 id 已稳定，加了只需多传一个字段）；或者改 id 去蹭
别人的图标。后者只有 `archived-sessions` 空着，而它的语义是"归档会话"，蹭它既可能与内置页撞 id，
也是拿图标撒谎——不做。判据留在 [`src/client/index.ts`](../src/client/index.ts) 的模块头注释里。

## 会话标题从哪来：界面显示标题，id 退到悬浮提示

列表里显示 `session-24ee5b02-…` 这种 uuid 对人是零信息——用户是在"我上次问那个问题的会话"这一层挑
会话的。所以行上显示**标题**，id 只在悬浮提示里出现（真要指名道姓时报 bug、对日志用）。标题不是 header
字段，而是宿主写的**日志事件**：

```json
{"type":"session/title","seq":25,"time":…,"data":{"title":"…","source":{"kind":"fallback"}}}
```

最新一条生效（用户改名压过首条 fallback），且它**不是模型输入**，所以只是展示文本：一行、裁掉首尾空白。

读它有两个来源，[`src/session-title.ts`](../src/session-title.ts) 按顺序取：

1. **宿主的投影缓存** `<DSH_HOME>/storages/session_projcache/sessions/<encodeSegment(id)>.json`
   （`record.rows.title.val`）——宿主自己列会话就读它，所以它是"最新一条"的权威副本，零解码、零 I/O
   放大。读之前核对 `record.identity` 的 `createdAt` 与 `cwd`：同 id 的另一条生命周期不能借到标题。
2. 缓存里没有（例如刚被本插件导入的会话、宿主还没重建缓存）才去**解日志开头**：只看**最新一代**文件，
   且只读开头 `DEFAULT_TITLE_BUDGET_BYTES`（256 KB）。写这份文档时整库 23 条会话、含 6 MB 的大日志，
   带标题的 `/state` 是 79 ms（不读标题 43 ms；单独那条 6 MB 的 12 ms），而全量解码是 3.6 s 量级。
   预算之外读不到就**不显示标题**（回落 id），这是有意的代价：`/state` 每次刷新列表都会走一遍，
   不能为了边缘情况把整页拖慢。解不动、文件不在、形状不认识——一律静默回落，标题是装饰，
   不该让"列出会话"失败。

导入预演里的标题不走上面这条路：它直接从 `.dshsess` 的**载荷**里折（[`src/transfer.ts`](../src/transfer.ts)
的 `bundleTitle`），因为那些会话还没落盘、宿主也没有它们的缓存。清单格式没为此改过
（`BUNDLE_FORMAT_VERSION` 不动），所以旧包、别人的包一样能被折出标题。

判据必须是**解析出来的** `type === 'session/title'`，不能是子串：日志里同时存在
`session/title-llm-request` 事件与"引用标题事件"的消息文本（本仓库自己的日志就是如此）。折叠前先用
`"session/title"`（带引号）做一次廉价预筛，再 JSON.parse 逐行确认。
