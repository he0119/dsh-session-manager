# Agent Note: 同步预演不再每轮重问 git、重算全库指纹

Status: implemented

## Problem

同步弹窗每打开一次就算一份只读计划（`GET /sync`）。本机真实库（1294 条会话、远端索引 2097 条）上量
到 **8.7 秒**，隔了很久的第一次是 **21.1 秒**。按 SSE 的进度事件切开：

| 段 | 耗时 | 在干什么 |
| --- | --- | --- |
| scan | 0.94 s | 扫本机 1294 条 |
| remote | 0.30 s | 读远端索引（冷的时候十几秒） |
| **repo** | **4.30 s** | 26 个候选目录 × 3 条 git 命令 = 78 个进程 |
| **compare** | **2.60 s** | 两边都有的 1285 个文件，逐个读整份、解压、按归一化 cwd 哈希 |
| relate | 0.50 s | 21 对"两边各自写过"的解压比对 |

三样里两样是**纯重复劳动**：项目身份（git remote）在两次预演之间几乎不可能变；日志文件只在会话被写时
才变，其余文件一个字节都没动。可是每一轮都要重新起 78 个进程、重读重解一遍这 1 GB 里"两边都有"的
那部分。用户每改一次裁决（保留本机 / 保留远端）就再付一遍；后台的自动推送每安静 5 分钟也付一遍。

## Decision

两样都按**进程级**缓存，`prepareSync()` 缺省用进程里那一份：

- **目录 → 项目身份**（`repo.ts` 的 `createRepoLocationCache()`）：同一个目录只问一次 git。入口
  （`src/index.ts`）造一份，`/state`、手动同步、自动推送三条路共用（`SyncDeps.repoLocations`、
  `ApiDeps.repoLocations`）；没注入时按调用新建一份，行为与原来逐字节一致。
- **文件内容指纹**（`sync.ts` 的 `createFingerprintCache()`）：键是路径，失效判据是 `size + mtimeMs`；
  戳没变就直接给上一次的值，连文件都不读。缺省用进程里那一份，`SyncDeps.fingerprint` 可以换一份
  （测试要"每一轮都现算"时用）。

扫描本身（0.94 s）与远端索引（网络）不动：前者有投影记录那层缓存兜着，后者是网络往返，各是各的。

## Alternatives considered

- **给缓存加过期时间。** 项目身份的变化不是时间驱动的（用户改 remote、换克隆），TTL 只让"过多久才准"
  变得随机；而进程级缓存的失效方式与 `/state` 那份 `createRepoLookup()` 完全一样——重启 DSH。
- **把 git 结果写进配置或注册表。** 那是用户的文件，git 身份是**旁路信息**（读不到时整条路退回 cwd），
  不该为它引入一份要维护的落盘格式。
- **把指纹写进远端索引缓存。** 索引里的指纹本来就有（推送时写），但本机文件变没变得靠本地判断——
  远端索引只记它自己那一边。
- **给同步复用 `/state` 的 `createRepoLookup()`。** 它只记身份字符串（`host/owner/repo`），而同步还要
  仓库根与仓库内相对路径（落地时改 cwd 要用）。
- **只缓存"每次预演里问过的目录"（现状本来就只缓存一次调用内的）。** 这只省同一次计划里的重复问法；
  重复发生在**下一次**预演，所以缓存得挂在调用之外。

## Consequences

- 预演 8.7 秒 → 同一份实测 **1.5～2 秒**（第二次起）；进程里第一次仍要问一遍 git（约 4 秒），
  之后目录不再变就一直命中。自动推送每轮的 8～21 秒后台负担同步下降。
- 改了某目录的 git remote，要重启 DSH 才在同步映射里看到（与 `/state` 显示的项目身份同一条取舍）。
- 指纹缓存的失效窗口：同一个文件在同一毫秒里被改写、又恰好大小不变时，这里会用旧值（与投影记录缓存
  同一个理论窗口）。下一次写入改了 `mtimeMs` 自然更新。
- 缓存无上限增长的风险：目录数受工作区数量约束；指纹按路径记，上限 4096 个文件，超过整份清空。
- 测试里注入 `repoLocations` / `fingerprint` 就能回到"每一轮都现问、现算"的口径，缓存的命中与失效
  各自有用例钉住。
