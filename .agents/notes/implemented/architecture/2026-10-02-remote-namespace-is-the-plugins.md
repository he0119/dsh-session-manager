# Agent Note: 远端第一层是插件自己的命名空间

Status: implemented

## Problem

`sync.url` 在语义上要同时回答两个问题：「WebDAV 在哪」与「本插件占哪个集合」。两个问题压进同一个输入框
时，只有填一个恰好专供本插件的地址才不出事：填服务器根或账号根，包就直接躺在根下，与同一台服务器上的
别的用途混作一团；想换目录也只能连"这是本插件的数据"这层归属一起重新约定。

远端位置是对外契约——多机并用、跨版本都看它——所以"数据属于谁"这一层该由代码定死，而不是靠每台机器
都记得在 URL 里手写一遍。

## Decision

远端所有路径相对资源根的第一层固定是插件命名空间 `dsh-session-manager`（`SYNC_NAMESPACE_DIR`），
机器格直接放在它下面：

```
<url>/dsh-session-manager/<machineId>/index.json        这台机器贡献了哪些会话
<url>/dsh-session-manager/<machineId>/<id>.dshsess      一条会话一个包
```

- 命名空间与机器格都不必先建：`put()` 逐层 MKCOL，所以 `url` 可以直接是服务器根、账号根或任意一层
  上级集合。
- 这一层是**常量**，不进配置：`url` 的语义因此收窄成"WebDAV 上的哪一处"，"这是本插件的数据"由代码
  保证。
- 索引名、包后缀与机器格的名字都没变（`SYNC_INDEX_FILE`、`.dshsess`、`SYNC_INDEX_UNIT`），变的只是
  它们上面多了固定的一层；索引格式版本仍是 1。
- 命名空间这一层就是机器格的父目录，路径只有 `SYNC_NAMESPACE_DIR` 一处字面量
  （`remoteBundlePath()` / `remoteIndexPath()` / 列机器格都从它拼）。
- 列机器格时只收集合、每个格子的索引还要过 `SYNC_INDEX_UNIT` 与格式版本，所以命名空间里万一混进别的
  条目也不会被当成一台机器。
- 同步功能尚未发版，所以这是**从第一版起**的布局：没有需要兼容或迁移的老位置。

## Alternatives considered

**在命名空间里再套一层（`<url>/dsh-session-manager/machines/<machineId>/`）。** 换来的是命名空间根
还能放非机器格的东西（一份全局索引、一个版本标记之类）。但那是猜测中的需求：真要加就那时再加一层，
而多套一层是每条路径都要多写一段、每份文档都要多解释一个词——命名空间自己已经说明数据属于谁了。

**让用户在 `url` 里自己写这一层（`https://host/dsh-session-manager`）。** 每台机器都要记得写，忘一台
就是一个各写各的库；而"填根"这个最自然的填法会把数据摊在共用集合里。

**把这一层做成配置项（`sync.prefix` 之类）。** `url` 本来就逐字照用（只去掉结尾斜杠），"数据落在哪个
路径"已经由它表达，配置项是同一件事的第二种写法；换来的却是多一个必须逐字跨机对齐的值——两台机器写
不一样时就是同一个 url 下的两套库，预演里只显示"远端是空的"，最难查的那种错。允许留空更糟：那会把
"这一层是本插件独占的"这个保证拿掉，集合里任何子目录都会变成候选机器格。

## Consequences

- 同一台 WebDAV 上跑本插件的多套数据只能靠 `url` 指向不同集合来区分；命名空间固定为
  `dsh-session-manager`，与同服务器上的其它插件互不干扰。
- 命名空间是远端位置的一部分，改它（或改机器格在它下面的排布）等于换一套远端库：`test/sync.test.ts`
  里那条钉住字面路径的用例就是这条契约的钉子。
