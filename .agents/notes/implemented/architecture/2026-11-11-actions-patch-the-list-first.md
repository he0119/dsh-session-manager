# Agent Note: 动作之后先改那几行，不等整库快照

Status: implemented

## Problem

这一页的清单只有一条来路：动作（归档、删除、迁移、重算名称、导入、同步落地）成功之后调用 `reload()`
重连那条面板流，宿主重新扫一遍整库，再把清单发回来。本机 1425 条会话、750 KB 快照上，那一步实测
**0.9～1.1 秒**（扫库 + 序列化 + 客户端解析 + 重画 1295 行），而这次动作改了哪几条，响应里本来就写着。

「取消归档」一条会话实测：点击 → 响应 **0.73 秒**（宿主还是要先扫一遍库认族）→ 再等快照回来，那一行
的标签到 **1.97 秒**才变。用户把这段等成了"这一页很慢"。

还有一处会把这个等待拉长：面板流每次 `publish` 都会把**同一份** `snapshot.state` 再发一遍（连接状态、
扫库进度、后台同步的状态都在变，清单没变）。订阅处原来无脑 `setState(snapshot.state)`，所以哪怕动作
落地时先改过那几行，下一次 publish 也会被旧快照盖回去。

## Decision

1. `src/client/logic/statePatch.ts`：四个纯函数，按动作响应改那几条——`patchArchived`（`archived` 与
   `hidden` 一起按宿主那条优先级重算：子智能体 > 空白 > 已归档）、`patchRemoved`（会话与工作区登记一起
   摘）、`patchTitles`、`patchMoved`（换 cwd / dir，清「未分组」，没 cwd 的不补）。一条都没变时原样返回
   同一个 `state`，不做无谓重画。
2. 动作处理里先 `patch(...)` 再 `void reload()`：改的那几行立刻对；整库快照随后在后台取回来覆盖它
   （快照是磁盘的真话，到了以它为准）。
3. 订阅处只认**换了对象**的快照：`snapshot.state !== lastSnapshotState.current` 才 `setState`。patch 改过
   之后旧快照的引用对不上，不会被盖回去；新快照到达时引用变了，照旧覆盖。

## Alternatives considered

- **继续等 `reload()`**（现状）。动作的等待从 0.7 秒拉长到 1.9 秒，而且每次动作都要整库重扫一遍。
- **在客户端挂一层"待合并的补丁"，渲染时合进快照。** 两个来源、两份真相，还得处理"补丁何时作废"；
  直接改同一份 `state` 让快照覆盖，只有一条真相。
- **把整库重扫改成增量扫（只重读变了的会话目录）。** 那会同时让首次打开、每次刷新都变快，是下一步
  真正值得做的事；但它改动的是扫描那一层（`discovery` / `scan-cache`），与本条"动作之后立刻看到结果"
  互相独立。
- **给列表做虚拟滚动。** 少画 1295 行（0.23 秒），但扫库那一秒还在；而且分组、粘性组头、勾选都要重做。
- **让宿主在动作响应里直接带回新清单。** 那等于把同一个响应的体积从几 KB 涨到 750 KB，而且与服务端
  "清单只从面板流来"这条边界冲突。

## Consequences

- 归档 / 删除 / 迁移 / 重算名称之后，那几行按响应立刻改对；实测「取消归档」一条的标签从 1.97 秒降到
  **0.87 秒**（就是宿主那一次响应的时长，快照再回来时以快照为准）。
- 整库快照仍然照旧扫一遍，只是不再挡在用户面前；它在后台到达时覆盖本地补丁——两边不一致时以磁盘为准。
- 只改响应里点名的那些：宿主逐条拒掉的那几条不会被 patch 成"成功"。
- 面板流上同一份快照的重发不再覆盖本地状态；新快照仍然覆盖。
