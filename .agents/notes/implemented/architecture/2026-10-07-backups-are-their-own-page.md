# Agent Note: 备份清单是独立分页，不挂在「迁移」底下

Status: implemented

## Problem

「备份与回滚」那张清单原先长在「迁移」分页的底部。可它躺的不只是迁移留下的备份：`src/journal.ts` 给
每份备份记一个 `kind`，三种来路——迁移（`migrate`）、删除（`delete`）、同步覆盖本机那份（`replace`）。

于是界面得在三处替它"远程引路"：

- 「会话」页删除的说明写着"要恢复就去「迁移」页的「备份与回滚」"（`manage.delete.backupTo`）；
- 「同步」页的结果与进度说明写着同一句（`sync.appliedReplaced` / `sync.progress.note`）；
- 说明页的 FAQ 写着"清单在「迁移 → 备份与回滚」里"（`help.faq.backupA`）。

一个面板要三处文案指路，说明它不在用户会去找的地方。反过来看迁移页：用户来搬家，页面末尾却摆着一张
删除与同步留下的备份表，两件事之间没有先后关系。

## Decision

- 「备份与回滚」是页内第六个分页（`src/client/components/BackupPanel.tsx`），页签顺序 会话 → 迁移 →
  传输 → 同步 → 备份 → 说明：它是三个写操作共同的后悔面，不属于其中任何一个动作页，所以排在动作页
  之后、"一次性读的参考页"「说明」之前。
- 迁移页只剩「迁移会话」这一张卡；清单、回滚 / 恢复弹窗与 `isRestore()` / `backupKindLabel()` 整套
  搬进新分页，迁移页不再 import `fetchBackups` / `rollbackBackup`。
- 上述三处引路文案改指「备份」页（`manage.delete.backupTo`、`sync.appliedReplaced`、
  `sync.progress.note`、`help.faq.backupA`），说明页的"每页做什么"多一条 `help.tabs.backup`。
- 清单的重读不靠别的页通知：切分页会**卸载**上一个分页，这一页每次挂载都自己 `GET /backups`。于是
  "刚做完迁移 / 删除 / 同步，切过来就能看见它留下的那一份"是卸载-重挂顺带得到的，不需要跨页事件。
- 迁移落地后不再顺带重读备份清单（原先的 `reload().then(() => loadBackups())` 只剩 `reload()`）。

## Alternatives considered

**保持现状，只把三处引路文案改准。** 引路文案本身就是迁就布局的补丁；把补丁写得更准，不会让"删除留
下的备份长在迁移页"这件事变得合理。

**每个动作页各自显示自己那一类备份。** "是谁留下的"是备份上的一个标签，不是三份各自独立的清单：同
一个动作判据（`isRestore()`）与同一份动作清单会因此拆成三份，用户还得记住去哪个页找哪一次操作留下的
那份。

**做成页头的一个全局入口（弹窗 / 抽屉）。** 页头按内建设置页的规格只有标题与说明行两行，页面级的那枚
「刷新」挂在页签那一行（见
[页头照内建设置页的规格](2026-09-28-page-header-matches-the-builtin-settings.md)）；把一份可能
很长的清单塞进弹窗，会丢掉"时间、来源、源 → 目标"这一列一眼可比的信息，也丢掉"回滚动作清单与确认同
框"那层保护。

**排在「迁移」之后。** 页签顺序按日常程度排，迁移是动作页、备份是几个动作页共同的善后；把它夹在动作
页中间，"动作页 → 参考页"这条顺序就断了。

## Consequences

- 页签从 5 个变 6 个（`test/client.test.mjs` 钉着顺序与默认停在第一个）；说明页词条数 20 → 21。
- 「备份」页与动作页共用页头（会话库位置）与同一份 `/state`；它自己只读 `/backups`，不依赖会话库清单，
  所以"库里一条会话都没有"不影响它。
- 回滚 / 恢复落地后照旧 `reload()` 再重读清单：回滚会改工作区注册表，页头那行"N 个工作区"要跟着变。
