# Agent Note: 同步的落地进度走 SSE 事件流

Status: implemented

## Problem

同步是这个插件里唯一"按条走网络"的动作：库里有多少条会话，就有多少次往返。实测把本机 84 条会话推给
一个本地远端，从按下「确认同步」到结束是 100 秒、上传 65.5 MB。这一百秒里界面能给的**全部**信息就是
一个「同步中…」的按钮——在推进、卡在第一条、远端已经不响应了，三者看不出区别。

预演那份清单说的是"将要"：它逐条列出会做什么、落到哪里。按下确认之后清单要么被收走，要么继续摆着让
人以为还没开始。用户缺的是第三样东西：**做到哪了**——第几条、共几条、正在处理的是哪一条。

这一条不只是"好看"：同步会写盘（推是往远端写、拉是往本机写），中途撒手会留下中间状态，而用户凭一个
不动的按钮判断不出"还要等一分钟"还是"该重来一次"。

## Decision

`POST /sync?mode=apply` 的成功响应从一次性 JSON 换成 **SSE**（`text/event-stream`），宿主按条推事件：

- `{ type: 'progress', progress: { phase, total, done, id, label } }`——**每开始处理一条之前**发一次。
  `done` 是"已经做完的条数"，所以正在处理的是第 `done + 1` 条；`label` 是标题（读不到退 id）。
- `{ type: 'result', result: <一次性 JSON 那份形状> }`——收尾，形状与原来完全一样。
- `{ type: 'error', error: '...' }`——流已经开始之后才出的错（那时 HTTP 状态早就是 200 了）。

进程里由 `src/sync.ts` 的 `runSync(deps, { apply, onProgress })` 报事件，`src/web.ts` 转成 SSE。要点：

- **拉与推各自一段，分母不同**：`total` 是**那一段要做的条数**。跳过的（库里已有同 id、远端那份没变、
  没配映射、目标目录不存在）**不进分母**——它们不花时间，算进去进度条就走不满。
- **流开始之前的错仍是一次性 JSON**：没配同步（409）、`mode=test` 这些在 `sendEventStream` 之前就返回
  了。客户端按 `content-type` 分流，所以同一个端点两种形状都认。
- **界面把弹窗正文换成进度条**：`src/client/ProgressBar.tsx`（手写的 6px 轨道，颜色只走检查面的
  token）+ 「正在推送 22 / 84」+ 当前那一条的标题 + 一句"中断了再点一次会接着补齐"。弹窗标题从
  「将要同步」换成「正在同步」，按钮从「导入中…」换成「同步中…」——落地时它已经不是"将要"了。
  计划的算不出来之前（读远端索引、扫本机库、比指纹）没有逐条事件，正文是「正在读取远端索引…」。
- **没有「取消」**：中途撒手会在宿主侧留下半截状态（远端可能已经收下几个包）。同步是只增不覆盖、可
  重复的，再点一次就接着补齐——这句写在弹窗正文里，取消键在落地期间保持禁用。
- **分帧与解释放在与 DOM 无关的 `src/client/syncStream.ts`**：一次 `response.body` 的读取边界与事件
  边界无关，一条事件被拆在两次读取之间是常态（中文标题还会让 UTF-8 多字节跨块），所以"攒够一条才吐"
  是有状态的。它放在单独一个文件里，是因为 Host 侧那份 tsconfig **没有 DOM**（那条边界让"浏览器 API
  出现在 Host 代码里"在类型层面就不成立）——把纯字符串处理与 `fetch`/`response.body` 分开，测试就
  能直接 import 它；真正的读流留在 `src/client/api.ts`。

## Alternatives considered

**轮询一个进度端点**（另开 `GET /sync/progress`，客户端定时问）。要多一个端点、多一份"这次同步是
谁、跑到哪了"的过期状态，还要处理重入与并发；SSE 是同一个请求里顺带把进度带回来，没有额外状态。

**NDJSON**（一行一个 JSON，用 `response.text()` 的流式变体读）。Host 半侧那层 gzip 中间件只豁免
`content-type` 以 `text/event-stream` 开头的响应，NDJSON 会被压缩中间件缓冲，进度就不是"实时"了。

**前端画一个不定长的假进度动画**。那正好是用户要的反面：一个永远在动的条子说不了"还剩多少"。

**把两段合成一个总百分比**。拉与推的分母不同（也会各自为空），合成一个数会先爬到某个位置再回退，
是在骗人。

**用官方控件库里的东西**。那一套没有进度条原语，最近的 `StateDot`（ongoing 转圈）与 `TextShimmer`
都只表达"还在动"。

**让预演那份清单留在弹窗里、进度另找一个地方显示**（页面横幅、toast）。进度与"将要做什么"是同一件
事的两段，分开放会让用户同时在两个地方找状态；而且落地时那份清单已经过期了（它描述的是将要）。

## Consequences

- 同一个端点在 `mode=apply` 下的成功响应**形状变了**：从 JSON 变成 SSE。仓库内部只有浏览器半侧读它
  （模型工具 `sync_sessions` 直接调 `runSync`，不走 HTTP），但外部脚本若直接打这个端点需要按
  `content-type` 分流——客户端的 `applySync` 就是范例。
- 进度分母是"要做的条数"，不是"成功的条数"：某一条推失败时进度照样走到底，失败那条在 `problems`
  清单里（实测 84 次尝试 / 83 条成功时会同时看到 84/84 的进度条与一条"推 xxx 失败"）。
- 进度事件发在**开始处理**那一条之前，所以一条几 MB 的包会让进度条停一会儿——那是真的在传，不是卡住。
- 没有做中断（见上），也没有做其它动作的进度：迁移、删除、导入的落地仍是"按下到结束之间没有反馈"。
  它们可以复用同一套地基（`onProgress` 回调 + SSE 端点 + `ProgressBar`），但各自的循环不在这条路径上。
- 实测（真实 dev GUI，两种主题都量过）：轨道 6px / 圆角 3px，浅色 `rgba(0, 0, 0, 0.1)`、深色
  `rgba(255, 255, 255, 0.12)`（都来自 `border-l2`）；填充浅色 `rgb(15, 17, 21)`、深色
  `rgb(249, 250, 251)`（`brand-primary`）；计数行 13px/20px，颜色是 `label-secondary`。
- 验收用了一个本地假 WebDAV（`test/dav-fixture.ts` 加一层"每条 PUT 慢 250ms"的代理）与真实的
  `~/.dsh/sessions`（**只推不拉**，84 条会话写到临时目录里），验完删干净、配置改回原值。
