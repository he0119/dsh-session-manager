# Agent Note: 同步的预演与落地都走 SSE 报进度

Status: implemented

## Problem

同步是这个插件里唯一"按条走网络"的动作：库里有多少条会话，就有多少次往返。实测把本机 84 条会话推送给
一个本地远端，从按下「确认同步」到结束是 100 秒、上传 65.5 MB。这一百秒里界面能给的**全部**信息就是
一个「同步中…」的按钮——在推进、卡在第一条、远端已经不响应了，三者看不出区别。

预演那份清单说的是"将要"：它逐条列出会做什么、落到哪里。按下确认之后清单要么被收走，要么继续摆着让
人以为还没开始。用户缺的是第三样东西：**做到哪了**——第几条、共几条、正在处理的是哪一条。

这一条不只是"好看"：同步会写盘（推送是往远端写、拉取是往本机写），中途撒手会留下中间状态，而用户凭一个
不动的按钮判断不出"还要等一分钟"还是"该重来一次"。

**预演同样要算一遍计划，它也要等**：扫本机库、读远端索引、逐个候选目录问一次 git、再逐条比对内容。
真实库上实测这四段加起来 0.5～2.3 秒（其中读远端索引一次往返就可能 1.7 秒、认仓库那段 13 个目录约
0.2 秒），而这段时间界面上只有一句「预演中…」——按下「同步」之后先盯着这句静止的话，再看到清单，用户
没法判断它是在干活还是已经卡住。落地那条路上的空档更糟：按下「确认同步」到第一条拉取完成之间，弹窗里
摆的还是那份"将要"的清单。

## Decision

`/sync` 的成功响应换成 **SSE**（`text/event-stream`）：预演的 `GET /sync` 与落地的
`POST /sync?mode=apply` 回同一个形状，宿主按条推事件：

- `{ type: 'progress', progress: { phase, total, done, id, label } }`——**每开始处理一条之前**发一次。
  `done` 是"已经做完的条数"，所以正在处理的是第 `done + 1` 条；`label` 是标题（读不到退 id）。
- `{ type: 'result', result: <一次性 JSON 那份形状> }`——收尾，形状与原来完全一样。
- `{ type: 'error', error: '...' }`——流已经开始之后才出的错（那时 HTTP 状态早就是 200 了）。

进程里由 `src/sync.ts` 的 `runSync(deps, { apply, onProgress })` 报事件，`src/web.ts` 转成 SSE。要点：

- **两条路报同一套事件**：落地要先算一遍计划，所以预演的四段（`scan` 扫本机库、`remote` 读远端索引、
  `repo` 逐个候选目录认仓库身份、`compare` 逐条比对内容）在落地那条路上也照报一遍，之后才是 `pull` 与
  `push`。界面因此只有一套渲染：同一个 `ProgressBlock`、同一个按 `phase` 选文案的 `progressTextOf`（这一套现在六个动作共用，见 [每个长动作都报进度](./2026-10-08-every-long-action-streams-progress.md)）。
- **拉取与推送各自一段，分母不同**：`total` 是**那一段要做的条数**。跳过的（库里已有同 id、远端那份没变、
  没配映射、目标目录不存在）**不进分母**——它们不花时间，算进去进度条就走不满。
- **`total: 0` = 这一段没有分母**：读远端索引是一次网络往返，没有"第几条"可讲。给它一个假的分母
  （1/1）会让条在等待期间就画满——那正读成"已经做完了"。所以协议里留了 `total: 0`：界面只摆那句话、
  不摆条（渲染判据是 `progress.total > 0`），与"还不知道总数时不画条"是同一条规矩。
- **比对那一段的分母只数两边都有的会话**（`compareTotal`）：本机独有的那些只算字节、不读内容，算进
  分母会让那条停在半路上。
- **同一份指纹函数分两个名字**：`runSync` 里算计划用带上报的那份（`planHash`），推送写远端索引时
  用不带上报的那份（`contentHash`）——否则收尾时会再冒出一条 `compare` 事件，界面上的条会跳回 0。
- **流开始之前的错仍是一次性 JSON**：没配同步（409）、`mode=test` 这些在 `sendEventStream` 之前就返回
  了。客户端按 `content-type` 分流，所以同一个端点两种形状都认。
- **界面把弹窗正文换成进度条**：`src/client/components/ProgressBar.tsx`（手写的 6px 轨道，颜色只
  走检查面的 token）+ 「正在推送 22 / 84」+ 当前那一条的标题 + 一句"中断了再点一次会接着补齐"。
  弹窗标题从「将要同步」换成「正在同步」，按钮从「导入中…」换成「同步中…」——落地时它已经不是"将
  要"了。预演那条路上弹窗标题是「将要同步」（它确实还没写盘），正文在计划回来之前就是这段进度。
- **浏览器半侧只有一个读流的实现**：`fetchSyncPlan` 与 `applySync` 都走
  `src/client/api.ts` 的 `readEventStream(response, onProgress, what)`——先按 `content-type` 分流，
  是事件流就逐条 `interpretStreamEvent`，否则退回一次性 JSON。错误文案带上 `what`（"预演" / "同步"），
  两条路的失败提示因此是同一种句子。
- **没有「取消」**：中途撒手会在宿主侧留下半截状态（远端可能已经收下几个包）。同步是只增不覆盖、可
  重复的，再点一次就接着补齐——这句写在弹窗正文里，取消键在落地期间保持禁用。
- **分帧与解释放在与 DOM 无关的 `src/client/logic/eventStream.ts`**：一次 `response.body` 的读取
  边界与事件边界无关，一条事件被拆在两次读取之间是常态（中文标题还会让 UTF-8 多字节跨块），所以
  "攒够一条才吐" 是有状态的。它放在单独一个文件里，是因为 Host 侧那份 tsconfig **没有 DOM**（那
  条边界让"浏览器 API 出现在 Host 代码里"在类型层面就不成立）——把纯字符串处理与
  `fetch`/`response.body` 分开，测试就能直接 import 它；真正的读流留在 `src/client/api.ts`。

## Alternatives considered

**轮询一个进度端点**（另开 `GET /sync/progress`，客户端定时问）。要多一个端点、多一份"这次同步是
谁、跑到哪了"的过期状态，还要处理重入与并发；SSE 是同一个请求里顺带把进度带回来，没有额外状态。

**NDJSON**（一行一个 JSON，用 `response.text()` 的流式变体读）。Host 半侧那层 gzip 中间件只豁免
`content-type` 以 `text/event-stream` 开头的响应，NDJSON 会被压缩中间件缓冲，进度就不是"实时"了。

**前端画一个不定长的假进度动画**。那正好是用户要的反面：一个永远在动的条子说不了"还剩多少"。

**把两段合成一个总百分比**。拉与推的分母不同（也会各自为空），合成一个数会先爬到某个位置再回退，
是在骗人。

**用官方控件库里的东西**。那一套没有进度条原语，最近的 `StateDot`（ongoing 转圈）与 `TextShimmer`
都只表达"还在动"。

**让预演那份清单留在弹窗里、进度另找一个地方显示**（页面横幅、toast）。进度与"将要做什么"是同一件
事的两段，分开放会让用户同时在两个地方找状态；而且落地时那份清单已经过期了（它描述的是将要）。

**预演照旧回一次性 JSON，只在落地报进度**。同一个端点两条路两种形状，客户端就得写两次分流；而且预演
正是用户**第一次**看到"它要干活了"的地方——冷启动那几秒的空等就发生在这里，落地那条路上的计划重算
同样要报。两条路共用一个端点形状与一份读流代码，代价只是预演的响应从 JSON 变成 SSE（仓库内部只有
浏览器半侧读它）。

**给读远端索引那一段也画一条 1/1 的条**。等待期间那条会画满，读成"已经做完了，怎么还不动"——比不画
更糟。`total: 0` 让界面在那一段只说在做什么。

**把这一段做成不定长的动画条**（一直来回走的那种）。那又回到"永远在动、说不了还剩多少"；本仓库的
`ProgressBar` 是定长语义，加动画要另立一套 CSS 与无障碍语义，收益只是这一段的观感。

## Consequences

- **两条路的成功响应形状都变了**：`GET /sync` 与 `POST /sync?mode=apply` 从 JSON 变成 SSE。仓库内部
  只有浏览器半侧读它们（模型工具 `sync_sessions` 直接调 `runSync`，不走 HTTP），但外部脚本若直接打
  这两个端点需要按 `content-type` 分流——客户端那条 `readEventStream` 就是范例。
- **算计划那几段仍然有空档没报**：`repo` 段结束到第一条 `compare` 事件之间还要逐个远端条目探一次目标
  目录是否在（实测 85 条约 0.18 秒），这段在 `planSync` 内部，没有上报点。四段的实测（真实库 88 条
  会话 / 远端 84 条，冷启动）：扫本机 87 条事件 < 1ms、读远端索引 1.74s、认仓库 13 个目录 0.21s、
  比对 85 条事件 < 1ms，整次预演 2.33s；同一个库热着（远端连接已建、标题缓存已热）时整次约 0.5s，
  界面上看到的是「预演中…」→「正在读取远端索引…」→「正在核对本机仓库 5 / 13」→ 清单。
- 进度分母是"要做的条数"，不是"成功的条数"：某一条推失败时进度照样走到底，失败那条在 `problems`
  清单里（实测 84 次尝试 / 83 条成功时会同时看到 84/84 的进度条与一条"推 xxx 失败"）。
- 进度事件发在**开始处理**那一条之前，所以一条几 MB 的包会让进度条停一会儿——那是真的在传，不是卡住。
- 没有做中断（见上）：落地期间取消键禁用，再点一次接着补齐。
- **其它动作后来也接上了同一套地基**（迁移 / 删除 / 回滚 / 导入 / 归档 / 扫库）：`SyncProgress` 与
  `readSyncResponse` 因此变成了通用的 `ProgressEvent` 与 `readEventStream`，`ProgressBlock` 从
  `SyncPanel` 里搬出来共用；`/sync` 那两种响应形状没变。决策与实测见
  [每个长动作都报进度](./2026-10-08-every-long-action-streams-progress.md)。
- 实测（真实 dev GUI，两种主题都量过）：轨道 6px / 圆角 3px，浅色 `rgba(0, 0, 0, 0.1)`、深色
  `rgba(255, 255, 255, 0.12)`（都来自 `border-l2`）；填充浅色 `rgb(15, 17, 21)`、深色
  `rgb(249, 250, 251)`（`brand-primary`）；计数行 12px/18px（次要文字那一档），颜色是 `label-secondary`。
- 验收用了一个本地假 WebDAV（`test/dav-fixture.ts` 加一层"每条 PUT 慢 250ms"的代理）与真实的
  `~/.dsh/sessions`（**只推送不拉取**，84 条会话写到临时目录里），验完删干净、配置改回原值。
