# Agent Note: 删除先备份，且不碰注册表

Status: implemented

## Problem

宿主没有「删除一条会话」的能力：`dsh-session-persistence` 那条缝上没有 delete，sqlite 的
`_deleteSession` 是私有的。所以删除只能是本插件做文件系统操作（`src/remove.ts`），而**真删用户数据
这件事本身没有第二次机会**。

剩下的问题是：删掉之后，注册表里那条登记怎么办。

## Decision

- **先备份整目录再删**：日志的原始字节 + `session.lock` + 任何别的东西，清单标成 `kind: "delete"`。
  恢复就是把整个目录搬回原位，所以「恢复的字节和删掉之前一模一样」是结构上成立的，而不是靠逐一列举
  文件来对齐。
- **刻意不动 `workspace.json`**：注册表里的悬空 id 是宿主本来就容忍的状态（`Workspace.sessionIds`
  会按 header 索引过滤、成员表里查不到的 id 直接跳过），删掉目录不会让宿主起不来；反过来，删除时
  顺手清理注册表就会**覆盖**掉用户在那之后的任何改动（重命名、归档、pin），而回滚一份删除备份不需要
  这些清理——目录回来了，成员表里那条登记本来就还在。
  于是回滚删除备份时第 4 步（还原注册表）被显式跳过，动作清单里写着 `registry untouched`，界面上那句
  文案也从「回滚」改成「恢复」。

删除**只有界面这一个入口**（4 个工具里没有它）：它要做的是「把人点的那一下忠实做完」，而「让模型
自己决定真删用户数据」是另一件事。

## Alternatives considered

**删除时顺手清理注册表。** 覆盖用户在那之后的改动，而且回滚时无法判断「该不该把那条登记加回去」。

**只删日志文件、不删目录。** `session.lock` 之类的残留会让「这个会话还在不在」变得模糊，而备份里的
东西也不再是「删掉之前那个目录」。

**把删除也挂到工具上。** 要做也得先想清楚权限边界与撤销面，不是把同一个函数挂到工具上就完了。

## Consequences

- 归档走的是**相反**的一条路：它**只能**走宿主能力（`ctx.workspaceRegistry` 的 `archiveSession()` /
  `unarchiveSession()` 一次落盘 + 改内存 + 广播，侧边栏即时跟着变）；宿主没有这个服务（非 Web
  profile）时如实回 409 并说明原因，不绕过去直接写注册表文件——那样写出来的状态与宿主内存不一致，
  下次宿主自己落盘就把它盖掉了。
- `test/remove.test.ts` 核「预演零写入、先备份再删、复核、空项目目录清理、活着的会话拒删、恢复把
  目录（含锁文件）搬回来且**不还原注册表**」。
