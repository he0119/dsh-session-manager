# Agent Note: 卡片级的主动作统一放卡片底部的动作行

Status: implemented

## Problem

页内各动作页"按下去就会写盘"的那枚按钮，原先有两种摆法：

- **卡片头部右端**：传输页的「导出所选」、同步页的「同步」；
- **卡片底部的动作行**：会话页的「归档 / 取消归档 / 删除」、迁移页的「迁移」、传输页的「导入」。

同一个设置页里两套语法，用户学到的是"这张卡的动作可能在头上、也可能在尾上"，每换一页都要重新找一遍。
而两种摆法各自的理由都不硬：导出之所以在头部，只是因为它旁边正好摆着"已选 N 条"这个数字；同步之所
以在头部，只是因为下面那张配置表单太长。

## Decision

- **卡片级的主动作一律放卡片底部的动作行**（`.dsm-controls`）。动作跟着它的输入走：字段与清单在上、
  动作在下，与确认弹窗底部的按钮同一个阅读顺序。
- **卡片头部只放不动数据的工具**：刷新、全选 / 清空、收起 / 展开。它们不改任何东西，摆在"读"之前合
  理，因此不算主动作。（选行那一对**跟着它选的清单走**：清单就是整张卡时在卡头，清单是卡片里的一段时
  在清单上方那一行，见 [选行工具只有一对](../bug-fix/2026-10-08-one-pair-of-pick-tools.md)。）
- **破坏性动作用 `.dsm-spacer` 顶到同一行的右端**（会话页的「删除所选」），不单独占一行、也不靠颜色
  分主次。
- **一行一个动作的清单留在行上**（备份清单的「回滚 / 恢复」、计划表里的行按钮）：那不是卡片级动作，
  不必也不该挪到卡片的某一端。
- 据此的两处改动：传输页的「导出所选」从卡头挪到列表下方的动作行；同步页拆成两张卡——「WebDAV 同步」
  （标题 + 远端 + 一句话 + 动作行里的「同步」）与「同步设置」（表单，它自己的保存 / 放弃 / 测试连接本来
  就在动作行里）。
- 这条规矩由 `test/client.test.mjs` 按结构钉住：一次下探里每一枚 `dsm-primary` 按钮所在的容器只能是
  动作行，不能是卡头（`primaryPlacements()`）。

## Alternatives considered

**统一到卡片头部右端。** 迁移与导入的按钮会跑到它们依赖的字段上方：字段还没填，按钮先灰在那儿，"按
下去会发生什么"的前提反而看不清；会话页的头部还要同时挤进"已选 N 条 / 全选 / 清空"与归档 / 取消归档 /
删除五枚按钮，窄一点的分辨率下只能换行。

**保持现状，按"正文是清单还是表单"各用一套。** 这套判据对外不成立：用户看到的不是"这张卡是表单"，而
是"同样一件事的按钮换了地方"；而它给出的两种摆法本身也没有稳定到能当规律的边界（导出是清单却在头部、
删除是清单却在尾部）。

**同步页不拆卡，把「同步」放到表单下方的动作行。** 那张表单十来行（地址、机器名、超时、账号、密码、
映射表），按钮会被埋到折叠线以下；而它读的是**已保存**的配置，与表单里正在编辑的草稿没有先后关系。
拆成两张卡之后，"这条通道现在通到哪、要不要走一趟"与"怎么改它"各自成块，动作也不必挤在任一端。

**把会话页的「删除所选」标成实心（`dsm-primary`）。** 那一行是三枚同级动作，只把其中一枚涂实心等于
说"主次分明"，而它们真正的差别是**破坏性**——由右端那一段空白与确认弹窗表达，不需要第三种语法。

## Consequences

- 同步页多一张卡片，多一个文案键 `sync.form.title`；没配同步时那张设置卡照旧在（配好 URL 保存之后
  「同步」才出现，这条"没配置不摆点了没反应的按钮"的口径没变）。
- 传输页导出卡的卡头只剩标题、已选条数与选行那一对（2026-10-08 起叫「全选」「清空」，位置见
  [选行工具只有一对](../bug-fix/2026-10-08-one-pair-of-pick-tools.md)），写盘入口在列表下面的动作行里。
- 这条规矩只覆盖**卡片级**动作。页面级的那枚「刷新」在页签那一行的右端（`page.refresh`，见
  [页头照内建设置页的规格](2026-09-28-page-header-matches-the-builtin-settings.md)），清单行上的动作仍在
  行上。
