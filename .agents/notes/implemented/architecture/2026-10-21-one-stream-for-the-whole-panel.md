# Agent Note: 这一页只连一条长连接，各种状态都从它来

Status: implemented

## Problem

「会话管理」页打开之后要盯四件事，`.agents/notes/` 里对应四份互不相干的实现：

- 整库清单：`GET /meta` + `GET /state` 两个请求；
- 落地那一趟（同步）：`GET /sync?mode=status` 一次性状态，页面靠轮询它认领"后台还在跑"；
- 自动推送那一轮：`GET /auto-push?mode=status` 一次 + 说"在跑"才开的 `GET /auto-push?mode=watch`；
- 用户自己点下去的动作：各自那条响应的 SSE。

四种形状、四份重连与看门狗逻辑。更贵的是**"没在听的那些事永远看不到"**：

- 后台自己跑的那一轮自动推送、另一个页签点的同步、工具层调的迁移或删除——这一页要么完全不知道，
  要么得靠"进页面时问一次"去撞。实测：打开同步页问一次状态，25 秒后还是那一次，期间定时器起的一轮
  不上屏；用户点「立即推送一次」只会吃一句"上一轮还在跑"，却看不到它在跑什么；
- 反过来，"库被别处改过了"这件事没有任何通知渠道，只能靠手动「刷新」。

官方那条连接（`@deepseek-ai/dsh-client-connection` 的 `/api/remote.mux`）就是按"一条连接 + `ready`
握手 + 之后只推增量"设计的，但它的转发事件白名单是宿主侧的固定集合（`API_REMOTE_FORWARDED_EVENTS`，
见 `dsh-api-remotes` 的 `registerRemoteEvents()`，文档写的是"唯一的应用选择事件源"），第三方插件加不进
自己的事件类型。

## Decision

这一页只保留**一条**长连接：`GET /panel/events`（SSE）。它按顺序发：

| 事件 | 内容 | 替掉的东西 |
| --- | --- | --- |
| `ready` | 宿主事实（与 `GET /meta` 同一份取值） | `GET /meta` |
| `progress` | 扫库"扫到第几条" | `/state` 流里那一段进度 |
| `snapshot` | 整库清单（与 `GET /state` 同一份取值，同一个 `readState()`） | `GET /state` |
| `sync` | 落地那一趟：`applying`（跑着的那一趟 + 最后一条进度）+ `last`（上一轮结论） | `GET /sync?mode=status` |
| `auto-push` | 自动推送那一轮：`running` + `last`（只回计数） | `GET /auto-push?mode=status` 与 `mode=watch` |
| `stale` | 本机会话库被改过了，请重连要一份新清单 | 无（原来靠手动刷新） |
| `ping` | 15 秒一次心跳 | 无 |

顺序是有意的：`ready` 不扫库，页头立刻能画；两种后台状态紧跟其后，于是"这一页打开时后台正在跑什么"
一眼就有；清单最后发，因为它要真扫库（实测 468 条 / 232 MB 约 0.2～0.45 秒，冷缓存与大库上几秒），
而扫库那一段是同步的，会挡住这条连接上其它推送——先发状态，用户至少知道"后台在跑"，不是干等。

客户端侧（`src/client/logic/panelEvents.ts`）是模块级的一份状态：`meta` / `state` / `scan` / `sync` /
`autoPush` / 连接状态。清单只有一条读法——重连一次（`refresh()`），手动「刷新」、`stale`、以及"一次动作
落地之后要重读"走的都是它。原来那些端点与"在跑才开"的小流全部删掉：

- 宿主：`/sync?mode=status`、`/auto-push?mode=status`、`/auto-push?mode=watch` 三条不再存在；
- 客户端：`fetchSyncStatus()`、`fetchAutoPushStatus()`、`watchAutoPush()`、`fetchMeta()`、`fetchState()`
  五个函数删掉（前两个是轮询用的，最后两个已被 `ready` / `snapshot` 替掉）；
- `syncJob.ts` 认领"后台那一趟"的入口从"每 3 秒问一次"换成"订阅面板流上 `sync` 那一条"。

**动作的进度不搬上来。** 用户点一次同步、迁移、导入、导出，那一次的进度与结果仍走它自己那条请求的
SSE：它天然属于那次点击（谁点的谁看细节，包括上千行的计划正文），面板流只承担"别的页面也该看见"的
那部分状态。

## Alternatives considered

- **一条连接，动作的进度也搬上来**（宿主侧再建一份"后台任务登记表"：任务 id、发起者、TTL、断线清理）。
  这是最彻底的一种，但代价是把"一次点击的进度"变成"一份要复用的资源"：谁发起的、连接断了谁清理、
  页面重进怎么接、任务过期怎么算——每一条都要定，而且都属于"以后会慢慢长出小毛病"的那一类。这次先
  只搬"本来就是后台的"那两件事；动作那部分留在原处，等真需要"另一个页签看这次点击的进度"时再说。
- **每秒轮询一个状态端点。** 最省事，也最费：一轮几十分钟的自动推送会让这一页每秒发一个请求，而
  进度本来就是一条条产生的，轮询看到的是"跳着走"的。
- **接官方那条连接（`$events`）。** 顺手、零成本，但第三方插件加不进转发事件白名单；官方也没打算让
  插件往那条连接上塞自己的事件（`registerRemoteEvents()` 是"唯一的一个"）。所以这条流只能是本插件
  自己的，也就要自己管重连与心跳。
- **把清单也放进 `ready`。** 少发一条事件，但页头就得等扫库——正是
  [分两份加载](./2026-10-07-page-loads-in-two-phases.md) 要解决的那件事。
- **`stale` 之后只补读清单，不重连。** 那要多一条"只读清单"的入口，而它与面板流上那份清单是同一份
  数据的两条路，迟早分叉（"刷新之后少一条"那类错）。重连一次多花的是那次扫库的钱，换来的是"清单
  只有一条路"。
- **保留 `/meta` 与 `/state` 端点让页面挑着用。** 两条路读同一份清单，等于给自己留一个分叉的口子。
  页面只走流；两条端点仍在（`readState()` / `metaFacts()` 是同一份实现），因为它们是不开浏览器也能
  读一眼库的一次性入口，且测试逐条钉着扫库语义。

## Consequences

- 一条连接断了就等于这一页什么都不知道：必须有退避重连（500ms 起、翻倍到 10 秒封顶，与官方那条
  连接同一套节奏）与 15 秒心跳，`test/panel-events.test.ts` 钉住"断了会自己接回来""`stale` 只换一次
  重连""页面走了不再连"。
- 重连不重放事件：接回来时宿主重新发 `ready` + 两种状态 + 一份新清单，所以"断开期间缺了哪几条进度"
  不需要补——状态本身就是新的。
- 浏览器对同一来源的并发连接有上限（HTTP/1.1 约 6 条），这条流占一条；页面里也只有这一条，动作的
  进度还在各自那条请求上，同时点两个动作时才会临时多一条。
- 开页面从"两个请求 + 之后若干次轮询"变成"一次连接"：实测进同步页只发一条 `GET /panel/events`，
  25 秒内没有第二个请求。
- 别处（另一个页签、工具层）改过库之后，这一页现在会自己重读一次（`stale`），不再需要用户按「刷新」。
  发起动作的那一页会同时收到"自己刚重连过"与一条 `stale`：`stale` 攒 600ms 之后再看一眼上一次重连的
  时刻，1.5 秒之内就当作那条已经被接住了，不再多扫一遍库（扫库是这一页最贵的一步）。
