# Agent Note: 导入只跳过，不覆盖

Status: implemented

## Problem

导入是**跨实例**的操作：同一个 id 在源库里是唯一的一条会话，在目标库里可能已经存在（曾经导过、
或本来就是同一台机器）。而两条日志没有共同的祖先——「这两条哪条更新」不是一个能算出来的问题。

## Decision

三种处理里只留一条：**冲突只报告**。预演把那条会话标成 skip 并附上它在库里的位置，落地时创建数为
0 就直接 409。

两条同源的细节：

- **无 `cwd` 的会话不硬塞**：保持没有 `cwd`、不参与注册表改归属。给它编一个 `cwd` 会让 header 声称一个
  它从未工作过的目录；
- **落地先写 `<规范名>.part` 再 rename**：`parseSessionLogName` 不认 `.part`，所以中途崩溃留下的是
  「发现阶段会忽略的文件」，而不是一个只有半截日志、看起来却正常的会话。

## Alternatives considered

**覆盖目标库里那条同名会话。** 目标是使用者的历史，而源文件可能更旧；「以新压旧」在这里连时间戳都
不可信（复制会改时间）。

**合并两条日志。** 没有共同的祖先，事件序号会打架；合并出来的东西不是任何一条的真实历史。

**遇到冲突就整包拒绝。** 一个 id 撞上就丢掉整包，那会把「导 40 条时有一条重复」变成一次什么也做不了
的操作。

## Consequences

- 导入是**只增**的操作：它不会让目标库里已有的任何一条会话变差。
- 冲突的条数与位置在预演里就能看到，落地时不会出现「以为导了 40 条、其实 39 条」。
- `.part` 这条约定让「崩溃」与「坏数据」不会混在一起——`test/transfer.test.ts` 把导入预演、落地与
  冲突跳过分别钉住。
