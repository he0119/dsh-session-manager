# Agent Note: 点名父会话时子智能体跟着走

Status: implemented

## Problem

候选不是族的边界。只把候选搬走会把子智能体会话丢在原地，而它**根本没有别的办法搬家**：它不在候选里
（侧边栏看不见），点名叫它又是被拒的。父会话的日志搬走了，子会话的日志还在旧项目目录里，而侧边栏
那一行是从父日志的 `subagent/catalog` 长出来的——看着还挂在父下面，点开却是另一条路径上的东西，
下一次「清掉已经搬空的项目目录」就会把它一起带走。

「删干净了」也是同一个错觉：本机删除前的实测口径是库里 41 条会话、注册表只登记 31 条，子智能体那 4 条
一条都不在册，它们的存在完全依附于父会话那棵树。

## Decision

四条按会话动手的路统一按族走（`familyOf()`，删除与迁移共用同一份实现）：点名哪条，就把它与全部
**子智能体**一起放进这次操作，连带多级与跨项目目录的。

- **迁移**：勾中的每条把整族带进计划，每条各自记着「是谁把它牵进来的」（`SessionMove.via`，预演里的
  `cascaded` 条数），界面因此能说明「多出来的那几条是子智能体」；成员资格不变——成员重挂只对那些
  **本来就在册**的做，子智能体通常从来没在册过，搬完也还是不在册（迁移搬的是文件，不是成员资格）。
- **删除**：整族进同一份备份（`kind: "delete"`），复核逐条核「目录没了、备份里有」，恢复仍然是「把
  整个目录搬回原位」那条路——族在这条路上不需要特殊处理，它只是目录多几个。
- **归档与导出**：`POST /archive` 与 `POST /export` 也按 `familyOf()` 展开，导出的包里那条 catalog
  因此不会指向包外；导出的响应头带上「包里到底几条 / 多少字节」（`x-dsh-session-count` /
  `x-dsh-session-bytes`），界面那句「已导出 N 条」说的是包里的东西。
- **级联进来的条目标出处**：`RemoveEntry.via` 指的是**用户点名**的那条祖先，界面据此在行上挂
  「随父会话删」；点名的条目自己永远不挂这枚标签——哪怕它同时又是别人的子智能体。

## Alternatives considered

**只处理点名的那些。** 上面的两个错觉就是这条路的结果：搬走一半的族与「删干净了」。

**单独点名子智能体时自动向上补上父会话。** 那是把「删这一条」变成「删那一族」；见
[子智能体不能被单独操作](2026-09-30-subagents-cannot-be-operated-alone.md)。

**迁移时连成员资格一起改挂（把级联进来的子智能体补登记进目标工作区）。** 宿主自己也不把子智能体算进
工作区成员（`sessionVisible()` 直接过滤），本插件替它作主会把「在册」这件事的含义改掉。

## Consequences

- 找后代时要**扫全库**：子会话的日志落在它自己 `cwd` 的项目目录里，而那个 `cwd` 未必还是父会话现在的
  `cwd`（父会话被单独迁走过一次就长成这样），而这正是要修的那种「族被拆成两半」。这一遍不读标题——
  本机 41 条会话，全库扫一遍 75～84ms，带标题扫一遍 1.7s。
- 产物搬迁（`includeArtifacts`）只覆盖源目录那一棵：跨目录的子智能体创建的文件会落进「跳过」清单
  （理由是 `outside the source workspace`），而不是被悄悄漏掉。
- 点名的 id 会按 `createdAt` 新→旧排回去，因为级联展开会打断宿主注册表里的那个顺序。
