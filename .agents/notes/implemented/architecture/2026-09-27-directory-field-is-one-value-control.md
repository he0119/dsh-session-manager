# Agent Note: 目录字段是一个值控件，三条改值的路

Status: implemented

## Problem

源目录与目标目录都是**任意绝对路径**：源是「会话日志里那个 `cwd` 字符串」，目标是「你想搬到哪儿，
那个目录可能还没登记过」。

这排除了两种常见写法：只能用下拉框（列表列不全——值可能在候选之外），以及下拉框只负责把路径填进
另一个文本框（那是把命令化装成控件：框里永远显示占位符，看着像没选中，而真正生效的值在别处）。

## Decision

**一个值控件 + 三条改值的路**：

- 下拉框**自己就是那个值**（`value={from}` / `value={to}`），候选＝已登记工作区 **+** 库里真有会话的
  目录（后者带条数——注册表的登记条数会骗人，同一个目录下可能有没登记在册的会话）；
- **当前值永远在候选里**：值可能是「浏览…」选回来的、注册表与会话都没覆盖到的目录，补这一行之后框里
  显示的永远就是将要用的；
- **「手输路径」**是万能兜底：展开一个和下拉框同值的文本框。宿主没有目录选择器、或要在候选之外敲一个
  路径时它是唯一的路，所以它对每个宿主都在，且只换控件不改语义；
- **「浏览…」**的行为由宿主报来的能力种类决定（见
  [「浏览…」按宿主的能力走](../bug-fix/2026-09-27-browse-follows-the-picker-capability.md)）。

选择器返回值先削掉结尾斜杠（`normalizePickedPath()`）：会话 `cwd` 与注册表路径都不带结尾斜杠，
`/a/b/` 会凭空多出一个「不同的项目目录」，匹配不到任何会话。

## Alternatives considered

**纯下拉框。** 候选列不全，而使用者要搬去的目录常常正是那个不在候选里的。

**下拉框 + 一个独立文本框（下拉只负责填空）。** 框里显示的永远是占位符而生效值在别处——控件在撒谎。

**只留手输框。** 那要求使用者记得住绝对路径，而这份下拉框的候选（含条数）正是本插件比 `ls` 多知道
的那部分信息。

**按容器宽度在两种控件间切换。** 同一个值有两种外观，会让人以为它们是两个设置。

## Consequences

- 「框里显示的就是将要用的」是一条可检查的性质，也是上面第二条候选规则存在的唯一理由。
- 这条形状不依赖宿主能力：能力缺失时少一条改值的路，值与语义不变。
