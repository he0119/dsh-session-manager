# Agent Note: 改一次裁决只重算计划，不重走整条同步流程

Status: implemented

## Problem

同步弹窗里每一对"两边各自写过"的会话都要用户挑正本（「以本机为准」/「以远端为准」）。每挑一次，界面
就带着新的裁决重新要一份计划——原来的实现是重新走一遍 `prepareSync()`：重扫本机整库、重读远端索引、
逐目录问 git、算比对用的指纹、把要读内容的那些对再各取一次远端包。

本机 1425 条会话、2097 条远端会话上，这条路实测 **2.1 秒**（预演预热之后；冷的时候 8～21 秒）。而这一
次改的只是 `decisions` 这一个参数：本机清单、远端索引、项目身份、内容指纹、那几对的内容关系，预演那
一刻已经全部算出来了。

## Decision

`prepareSync()` 的返回值（`SyncPrepared`）多记一样东西：`relations`——那几对"要读内容才判得出来"的
内容关系（分叉 / 只是尾巴不同 / 一样）。新增 `replanPrepared(prepared, deps, decisions)`：拿预演留下
的输入、把 `decisions` 换掉，只跑一遍纯计算 `planSync()`，再把设置与远端那几项问题照原样拼回计划上。

`/sync` 的预演路径带 `planId` 回来、且与宿主缓存的那份对得上时，走 `replanPrepared()`；对不上（宿主
重启过、缓存被换掉）才走完整 `prepareSync()`。计划 id 沿用，`decisionsKey` 跟着更新——落地时那句"同一
份 `planId` 但选择变了就不算数"的检查照旧成立。

客户端预演请求多带一个 `planId`（`fetchSyncPlan()` 的第三个参数，只在有裁决时才发 POST 体里带上）。

## Alternatives considered

- **继续每次裁决都完整预演**（现状）。2.1 秒一次，一对会话挑两次正本就要等两遍。
- **在界面上本地改计划表**：把选中的那一行从"分叉"改成推或拉，再自己重算条数与字节数。改一行容易，
  但"哪几行受影响"的判据（分叉的两侧、条数、字节数、被跳过的对）在宿主那侧，客户端再实现一遍就是两份
  规则，迟早算出两套数字。
- **取消预演、裁决只在落地时生效**：确认按钮之前那张表就会说谎（那一对还写着"分叉、都不动"），用户
  不知道自己这一下会推还是拉。
- **把整条同步流程做增量（只重读变了的会话）**：那是另一件事，收益在首次预演与落地，不在"改裁决"。

## Consequences

- 改裁决的等待从 2.1 秒降到纯计算那一层（几十毫秒）；测试里断言"重算不再读远端包"与"结果与从零预演
  逐字相同"。
- 重算用的是预演那一刻的输入：如果预演之后本机库或远端变了，这张表可能旧几秒。落地前 `syncPrepared()`
  照旧验事实快照（设置、本机文件、远端索引），变了就从零重算——所以旧的那一份不会把会话落到错的地方。
- 计划 id 沿用同一条：界面连点两次裁决不会把宿主缓存里那份换掉；落地仍能对上。
