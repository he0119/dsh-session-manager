# Agent Note: 每个长动作都报进度，段名共用一套词汇

Status: implemented

## Problem

同步是唯一"按下之后会动"的动作：它有一套按条推送的进度（见
[同步那篇](./2026-10-03-sync-progress-streams-over-sse.md)）。其余五个动作按下之后界面上只剩一句静止的
「…中」，而这五个里有四个比同步更慢——它们都是**整目录级别的字节搬运**，实测：

- 迁移落地：一份 47 条会话 / 67.5 MB 的夹具，整段 45.3 秒，其中"逐条改写首帧"占 45.1 秒；
- 删除落地：先按字节备份整份会话目录再删，与迁移同量级；
- 导入落地：250 条 / 70.9 MB 的包，18.9 秒；同一个包的预演（逐条读包里的日志折标题）1.7 秒；
- 打开页面时那次整库扫描：本机 468 条 / 232 MB，0.18～0.45 秒（更大的库或更慢的盘上是几秒）；
- 归档：逐条走宿主的注册表动作（每条一次落盘 + 广播），勾一整页时同样可感知。

这三四十秒里，界面能给的**全部**信息是一个不变的按钮文字：在推进、卡在第一条、已经写坏了一半，三者
看不出区别。而它们全都写盘（改写日志、删目录、写注册表），中途撒手会留下中间状态——用户凭一个不动的
按钮判断不出"还要等一分钟"还是"该重来一次"。

## Decision

一份地基，六个动作共用（迁移 / 删除 / 回滚 / 导入 / 归档 / 扫库，外加原来的同步）：

- **宿主侧一个类型**：`src/types.ts` 的 `ProgressEvent { phase, total, done, id?, label? }` 与
  `ProgressReporter`。同步原来那份 `SyncProgress` 就是它（`export type SyncProgress = ProgressEvent`），
  两处不再各有一份形状。
- **宿主侧一个出口**：`src/web.ts` 的 `streamResult(res, run)`。`/state`、`/migrate`、`/delete`、
  `/rollback`、`/import`、`/archive` 都换成 SSE（`text/event-stream`），事件三种：`progress` 逐条、
  `result` 收尾（形状与原来那份一次性 JSON 完全一样）、`error`（流已经开始之后才出的错）。
- **每条事件写完必须把 socket `uncork()` 一次**（`sendEvent()` 里那一句，不是保险）：`res.write()`
  每次都会把 socket 重新 cork 住、事件躺在写缓冲里，Node 要等下一次事件循环才推给内核；而报进度的
  这些循环是**同步**的（读日志、改首帧、搬目录中间一次 `await` 都没有），不主动推的话整段干完之前
  一个字节都发不出去——所有事件在结束时一起到，进度条会从"正在准备…"直接跳到做完。同步那条路本来
  能走，只是因为它每一步都在 await 网络往返，事件循环自然会转。
- **段名是一份封闭词汇**（`ProgressPhase`）：`scan / read / pack / backup / rewrite / move / write /
  remove / restore / archive / registry / verify / warm / remote / repo / compare / pull / push`。
  每个动作只报自己真正走过的那几段，段名不按动作分叉（"备份"在迁移、删除、回滚里是同一件事）。
- **分母是"那一段要做的条数"，`total: 0` = 这一段没有分母**：只有两种没有分母——读远端索引（一次网络
  往返）、写工作区注册表（一次落盘）。没有分母的段界面只说在做什么、**不画条**——画一条 1/1 的会在等待
  期间就画满，正读成"已经做完了"。
- **`done` 是"已经做完的条数"**，事件发在**开始处理下一条之前**，所以界面说"正在处理第 `done + 1` 条"。
  分母是"要做的条数"，不是"成功的条数"：某一条失败时进度照样走到底，失败那条在结论的 `problems` 里。
- **浏览器半侧一份实现**：`src/client/logic/eventStream.ts`（原 `syncStream.ts`，改成通用）+ `src/client/api.ts`
  的 `readEventStream(response, onProgress, what)`，六个端点共用；按 `content-type` 分流，不是事件流的
  退回一次性 JSON（流开始之前就被挡下的错仍是 JSON + 状态码）。渲染只有一处：
  `src/client/components/ProgressBlock.tsx`（原长在 `SyncPanel` 里），`progressTextOf` 按 `phase` 选
  `progress.*` 文案，**认不出来的段名退到「正在处理…」**（宿主比界面新时不至于画出一片空白）。
- **进度摆在动作自己的那个弹窗正文里**：落地那一段把计划表换掉（计划表说的是"将要"，这时候已经过期
  了），标题从「将要迁移」换成「迁移中…」，取消键在落地期间禁用（与同步同一条规矩）。归档与扫库没有
  弹窗，进度块摆在动作行 / 页头下面。
- **各动作"中断了怎么办"那句话由调用方给**（`note`）：同步是"接着补齐"，迁移与删除是"能在「备份」页
  回退"，导入是"只增不覆盖、再导一次"。
- **`/export` 一个字都不改**：它的响应体**就是产物本身**（250 条 / 70.9 MB 实测 1.45 秒），改事件流
  只能把整包字节塞进 JSON（base64 多 33% 字节、双份内存）。它仍然是二进制一次性响应，
  `test/web.test.ts` 钉住这条。
- **对外契约变了**："计划不 ok"（源目录不存在、会话不在库里、包里的会话都已在库里、宿主拒了一条归档）
  从 409 变成 200 + `result` 里的 `ok: false`——流一旦开始，HTTP 状态早就发出去了。正文（`preview` /
  `problems` / `failed`）与原来那份一字不差，界面读的就是它。

## 事件是"边干边到"的（跨进程实测）

同一台机器上跑一次端到端：真的 `node:http` 服务器挂本插件的端点、客户端**另起一个进程**、会话库是从
真实库里复制的 10 条（9.5 MB）、同步那一段用一个真的 WebDAV 夹具（PUT / PROPFIND 各加 300ms 延迟）：

| 动作 | 整段 | 第一条进度 | 观察到的节奏 |
| --- | --- | --- | --- |
| `GET /state`（扫 10 条） | 554ms | +13ms | 每 40～70ms 一条 |
| `POST /migrate?mode=apply`（6 条参与） | 11.5s | +3ms | 备份 6 条在 8ms 内报完，逐条改写首帧从 +477ms 拖到 +11.3s，搬目录/复核随后 |
| `POST /import?mode=apply`（10 条） | 7.6s | +49ms | 逐条写盘 +478ms→+7.2s |
| `POST /delete?mode=apply`（10 条） | 420ms | +3ms | 备份 / 删 / 复核各 10 条 |
| `GET /sync` + `POST /sync?mode=apply` | 0.8s / 4.4s | +3ms | 推送 10 条每条 ~310ms（那 300ms 是夹具的延迟） |

**客户端必须另起进程**：服务端那些循环是同步的，同一个进程里客户端的事件循环会被一起堵住，量出来的
就是"全都在最后一起到"——那是测量假象（第一版验收脚本就是这么被骗过去的，也正是它先暴露了缺
`uncork()` 这件事）。

## Alternatives considered

**六个动作各写一份进度块。** 一个动作一个进度条就是六份"第几条 / 共几条 + 当前那一条"的渲染、六套
文案与六处 `total > 0` 判据；同步那一份已经在了，再复制五遍之后改一处文案要改六处。

**段名按动作分叉**（`migrate.backup` / `delete.backup` / `rollback.restore`…）。同一件"按字节复制整个
会话目录"在三个动作里的说法与分母都一样，分叉只会让词汇表变长、翻译变多；界面上"正在备份 3 / 12"本来
就是同一句话。

**给没有分母的段也画一条 1/1 的条。** 等待期间那条会画满，读成"已经做完了，怎么还不动"——比不画更糟
（同步那篇对"读远端索引"已经否过一次）。

**浏览器画一个不定长的假进度动画。** 那正好是用户要的反面：一个永远在动的条子说不了"还剩多少"。
本仓库的进度条是定长语义，加动画要另立一套 CSS 与无障碍语义。

**进度放在页面横幅或 toast 里，弹窗照旧只摆计划。** 进度与"将要做什么"是同一件事的两段，分开放会让
用户同时在两处找状态；而且落地时那份计划已经过期（它描述的是将要）。

**`/export` 也走事件流（进度 + base64 产物）。** 导出确实是这六个里第二慢的（1.45 秒），但它的响应体
就是产物，改协议要把整包字节塞进 JSON：多 33% 字节、双份内存，代价远大于那 1.45 秒里多画一条条。

**改成"处理完一条再报"**（`done` 是刚做完的那条的序号）。进度会晚一拍，界面也就说不出"正在处理第几条"
——而"卡在哪一条"正是这类整目录搬运最需要的那个信息。

**给 `/state` 单独留一条不变的事件流**（其它五个换 SSE、它照旧 JSON）。同一个页面上两种响应形状，
`api.ts` 里就得多一条只读路径；扫库那段等待恰恰是用户**第一次**看到这一页在干活的地方。

## Consequences

- 实测（本机，改动后用同一批夹具复测）：迁移落地 47 条 / 67.5 MB → 计划 113 ms、备份 37 ms、逐条改写
  首帧 45.1 s、搬目录 0 ms、注册表 0 ms、复核 12 ms，**整段 45.3 秒**（单条 0.2 MB 的日志改写一次
  约 0.2～0.3 秒）；导入 250 条 / 70.9 MB → 预演 1.7 s、落地 18.9 s（读包 137 ms、打包 1.45 s）；
  扫整库 468 条 / 232.5 MB → 0.18～0.45 秒（热 / 冷投影缓存）。
- 逐条改写首帧是迁移唯一的成本（99.6%）：进度条在那一段会**慢慢**走（47 条要走 45 秒），这不是卡住。
  要更快得换压缩实现或只重写首帧所在的第一个 zstd 帧，那是另一件事。
- `/export` 是唯一没有进度的动作，也是唯一一次性响应：它没有"第几条"可讲（一个包一个响应体）。
- 事件形状与同步那条完全一致，所以 `test/web.test.ts` 里逐端点核的是**段名与分母的顺序**、
  `test/client.test.mjs` 核的是"四个弹窗正文真的接上了进度块"、`total: 0` 不画条、认不出来的段名退到
  「正在处理…」。
- "进度到底会不会动"另有两处**测试里钉得住**的断言（时序类断言进不了测试：跨进程 + 慢机器上必飘）：
  一条是 `test/web.test.ts` 里用真 `node:http` 服务器量"每条事件写完 socket 里不留缓冲"（去掉
  `uncork()` 当场红），一条是 `test/client.test.mjs` 里从 SSE 字节一路核到"宿主报的那条进度真的
  进了界面状态、收尾时又清回 null"（去掉面板传给 api 的那个回调当场红）。
- 界面复用已有的 `.dsm-progress` / `.dsm-hint` / `.dsm-rowTitle`，没有新增颜色或尺寸，也没有新增
  `styles.ts` 里的声明（深浅两套主题的实测值见同步那篇）。
- 扫库那条进度只在页头下面出现（页签之上）：它是这一页自己的事，不属于任何一个分页。
- 归档那条进度没有弹窗，勾一整页时它摆在动作行下面；每一条一次宿主往返，失败逐条兜住、不影响其余
  （失败原因仍在结论里）。
- 段名与文案是编译期绑定的：`progress.*` 少一个键 `pnpm typecheck` 就红（`en` 由 `LocaleDictOf` 逐键核），
  多一个键同样红；运行期那一遍在 `test/client.test.mjs`（页面问到的每个键都在字典里）。
