# Agent Note: 只重写第一个 frame

Status: implemented

## Problem

改写会话日志的 header 时，磁盘上那份文件是多帧拼接的（见
[多帧 zstd 变成启动期硬失败](../bug-fix/2026-09-27-multiframe-zstd-is-a-hard-failure.md)）。
最省事的做法是整个解压、改一处、整份重新压回去。

难点在重压回去的时候：首帧的边界不能靠猜魔数——压缩载荷里可能偶然出现魔术字节。

同一套切分还有第二个使用者：同步的**内容指纹**（把 header 的 cwd 归一成占位符再算 sha256，见
[WebDAV 只是一层运输](../feature/2026-10-01-webdav-sync-is-a-transport.md)）。它只要"首帧明文 +
其余原始字节"，却与改写走同一条路：`readSessionLog` 整篇解码一遍、切分里整篇解码与尾部解码各一遍、
改写后的自校验再整篇解码一遍——一条会话解四遍。解码器是纯 JS 的 fzstd（实测约 6 MB/s），于是本机
85 个日志 / 67.1 MB 跑一遍要 **40.5 秒**，而要的结果只是一个哈希（其中 sha256 本身 55 毫秒）。

## Decision

只重新压缩**首个 frame**，其余 frame 字节**原样保留**。要把结果拿去改写并落盘时，首帧边界用两步定：

1. 先用魔数出现的位置（外加文件尾）收窄候选；
2. 在候选里取最小的偏移 `i`，使 `decodeAll(buf[0..i)) + decodeAll(buf[i..)) === decodeAll(buf)`
   且前半段是完整的行。

截断帧会被解码器抛错或被该等式排除。可解码的输入恒有切分（`i = buf.length` 退化为整份单帧），
所以 `null` 分支对可解码输入不可达——这是有意的保守设计，不是遗漏。

**只读用途走浅路**（`splitFirstFrameFast` + `relocateHeaderCwdShallow`）：不整篇解码，只解候选前缀，
也不做那步等式自校验。省得掉的理由是等式在这里多余——截断帧会被解码器拒绝（fzstd 报
`unexpected EOF`，`test/zstd-frame.test.ts` 把这条前提钉住），所以"前缀能解出、且以换行结尾"已经
够判定。两条路的**产出逐字节相同**：`test/session-log.test.ts` 逐份比对两者的字节，`test/sync.test.ts`
用旧实现冻结下来的 sha256 钉住指纹口径。

落盘那条路仍然走严格路：`relocateHeaderCwd` 多花的时间买的是"写出去的字节整体可解码"。

## Alternatives considered

**整份解压再整份压缩。** 尾部会在字节层面被改写：回滚时「逐字节还原」不再是结构上成立的事，只能
靠重新编码恰好一致；一条 1.8MB 的日志也不再只需要重压 ~180 字节。

**按魔数切第一帧。** 载荷里偶然出现魔术字节就会切错位置，而切错之后前面那半段解不出来——错误
出现在解码阶段，离真正的原因很远。

**只在第一个魔数之后切一刀、不验证。** 落盘那条路上与上一条是同一个问题，验证等式才是把「猜」换成
「判定」；只读的浅路能省掉它，是因为那里"切错"的后果只是哈希不同，不写盘、不改文件。

**给指纹按 mtime 加缓存。** 只挡重复预演，挡不住冷启动，也挡不住正在写入的那条会话；判据变成"上次
算出来的记录"之后，备份还原保留旧 mtime 这类情况会带来过期哈希。先把计算本身变便宜更根本。

## Consequences

- 产出结构与宿主自己写出的多帧布局一致，任何能读宿主日志的解码器都能读。
- 尾部在字节层面可审计地不变：端到端用例逐行比对，回滚后逐字节断言还原。
- 首帧本来就只有一个 header 行，所以「首帧不压缩」的代价可忽略（见
  [写侧不依赖压缩器](2026-09-27-write-side-has-no-compressor.md)）。
- 指纹从"每个文件解四遍"降到"解首帧一遍"：同一批 85 个日志 / 67.1 MB，耗时从 **40.5 秒**（77.0 CPU
  秒）降到 **87 毫秒**（0.14 CPU 秒），哈希值一格没变——远端索引里已发布的指纹不需要重新推送。
