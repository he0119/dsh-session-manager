# Agent Note: 生效模式如实探测，不假装即时生效

Status: implemented

## Problem

`WorkspaceRegistry` 持有**内存**注册表与一个 header 索引，而重建该索引的 `replaceHeaderIndex` 是
**私有**方法。于是绕过宿主直接改写 `workspace.json` 之后：

- 注册表会被宿主的旧内存副本覆盖；
- 即使不覆盖，宿主的索引仍是旧的，被搬走的会话会被过滤成「未分组」。

也就是说「改完文件就立刻生效」这件事**不一定成立**，取决于这次写盘之后有没有把宿主那一层重新读一遍。

## Decision

`effectMode(ctx)` 如实探测：这个宿主里拿不拿得到让注册表被重新读一遍的入口
（`workspaceReloadPort()`，见[写完注册表就地重挂工作区那一层](2026-10-05-reload-the-workspace-entry.md)）。
拿得到就返回 `'immediate'`，拿不到就返回 `'restart-required'`，由工具返回值告诉调用方「必须重启 DSH」。

真的写盘过的那一次不按探测说，按**实际结果**说：`src/reload.ts` 的 `effectOf()` 只在重挂成功时才报
`'immediate'`。探测回答"执行时会怎样"，只有写过盘的那次才有资格说"已经怎样"。

## Alternatives considered

**一律声称即时生效。** 使用者会看到「迁移成功」然后发现侧边栏没变——把一次已知的、可解释的等待
变成一次看起来像失败的成功。

**一律要求重启。** 本插件自己就能把那一层重挂一遍，要求重启是凭空多一次；而探测只是遍历一遍加载树。

**探测失败时按「即时生效」猜。** 猜错的方向恰好是「做了却没生效」，与上一条同因。

**按"上游有没有 `reassignSessions`"探测。** 那是初版的做法：等宿主给一个进程内 API，拿不到就要求
重启。它把"能不能即时生效"押在别人的接口上，而这件事本插件自己做得了（见新笔记）。

## Consequences

- 「要不要重启」是工具返回值里的一等信息，不是文档里的一句提醒。
- 探测结果也决定了界面怎么措辞，两侧读的是同一个 `EffectMode`，不会一边说即时、一边说重启。
