# Agent Note: 打开一条会话的内容不再扫整库，翻页也不再重解压

Status: implemented

## Problem

「内容」弹窗要回答的是"这一条会话里写了什么"。它打开一次、每往下翻一页（一页 80 条事件）、每点一次
「查看全文」，都各发一次 `GET /transcript`，而这条请求原来有三步都按"整库 / 整份"的量级做：

1. **定位**：`scanLibrary()` 把整个会话库扫一遍再 `find()` 出这一条——每条会话都要读日志头、读投影
   记录、折标题。本机 1295 条会话、1306 个日志实测 1.4 秒。
2. **读与解压**：`readFileSync()` 整份读进来，`decodeAll()` 整份一次解（同步，宿主主线程不动）。
3. **切行**：`text.split('\n')` 之后按 `from` / `limit` 取一页。

翻页时三步全部重做。本机真实库、发布版 0.6.4 的宿主进程上实测：

| 打开哪条 | 一页请求 | 第二页 | 「查看全文」 |
| --- | --- | --- | --- |
| 中位 357 KB / 214 条事件 | 1.60～1.65 s | — | — |
| 12.1 MB / 8972 条事件 | 2.07 s | — | — |
| 16.9 MB / 9269 条事件 | 4.35 s | 4.15 s | 4.19 s |

16.9 MB 那条按一页 80 条要翻 116 页；而解压那一步同步执行，一次就把宿主主线程按住约 1.5 秒——那段时间
里网页上别的请求都得排队。

## Decision

**定位不扫库。** `src/discovery.ts` 的 `locateSession()`：会话目录名就是 `encodeSegment(id)`（与宿主
同一套，见 `src/paths.ts`），所以走一遍项目目录、找同名目录、只读它自己那一份日志头就够——本机 28 个
项目目录、1295 个会话，实测几毫秒。`GET /transcript` 与 `GET /sync/diff` 都改走它。目录名不是 id 的
编码时（手改过的库）退回整库扫一遍，"找得到"这件事不依赖目录命名这个约定。

**同一份日志连着读多页时只解压一次。** `src/log-text-cache.ts` 的 `createLogTextCache()` 留一份切好的
行：判据是 `路径 + size + mtimeMs + 压缩方式`，命中时连文件都不读。解压走 `src/log-decode.ts` 已有的
分块版本（块与块之间让出事件循环），整份解压不再把宿主主线程按住。只留一份（这一页同时只看一条会话），
解开后超过 64M 字符的不缓存（文本是 UTF-16，一个字符两字节）。

改完同一份库、同一台机器：

| 打开哪条 | 第一页 | 第二页 | 再回第一页 |
| --- | --- | --- | --- |
| 中位 357 KB | 129～148 ms | 3～4 ms | 7 ms |
| 12.1 MB | 432～494 ms | 11～13 ms | 12～15 ms |
| 16.9 MB | 约 1.8 s（新进程） | 8～12 ms | 12 ms |

## Alternatives considered

- **复用 `GET /state` 的扫描缓存。** 指纹那一趟本身要 stat 1300 多个日志与 1300 多个投影文件（约
  26 ms），而内容视图要的是这一条会话的最新日志——只要它在写，指纹就变、照旧重扫。按 id 直接找更便宜。
- **把解压结果落盘。** 多一套缓存目录、版本号与失效逻辑；收益只在"重启之后第一次打开同一条大日志"。
- **一次把整份文本发给浏览器。** 45 MB 的文本，浏览器那边只会卡死；分页与单格上限是这条视图的前提。
- **只解第一页需要的那几帧。** 那要建"事件位 ↔ 帧"的索引，而分页游标是事件位（`seq` 会跳号，见
  [会话内容视图](../feature/2026-10-12-transcript-view-parses-the-log-itself.md)）；索引得在写入侧维护，
  代价比现在的收益大。留作以后。
- **改用宿主接口定位会话。** 宿主只认它内存里挂着的会话，而侧边栏看不见的那些（空会话、孤儿目录、导入
  的 Codex 会话）恰恰是这条视图存在的理由（同上）。

## Consequences

- 中位会话从 1.6 秒降到 0.13 秒；大日志的翻页从每页 1.5～4 秒降到十几毫秒。
- 宿主主线程不再被整份解压按住：128 KB 一块推进、块间让出事件循环，与
  [内容关系不占主线程](../bug-fix/2026-10-21-content-relations-off-the-main-thread.md) 同一套做法。
- 常驻内存最多多一份解开的大日志（≤ 128 MB），换一条会话就顶掉；超过上限的不缓存，只是慢一点。
- 同一毫秒、同样大小的改写看不出来：最坏是某一页看到上一次的内容，下一次请求（时间戳变了）自然读到。
- 同一进程里连着打开两份大日志时，第二份会因为堆已经长大而更慢（实测先开 12.1 MB、再开 16.9 MB 是
  2.9～3.5 秒，单独开是 1.8 秒）。这是 V8 堆的代价，不是这一层能消掉的。
- 定位依赖"目录名 = `encodeSegment(id)`"这个与宿主一致的约定；不成立时退回整库扫描（慢，但不丢会话）。
