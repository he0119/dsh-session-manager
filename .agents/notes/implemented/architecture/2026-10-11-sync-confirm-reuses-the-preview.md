# Agent Note: 确认之后照着预演那份数据落地，不再重算一遍计划

Status: implemented

## Problem

同步弹窗把"将要做什么"摆出来，用户按下「确认同步」之后宿主却把**同一份计划**从零又算了一遍：扫本机
整库（每条会话读头、折标题）、读一次远端索引、逐个候选目录问一次 git、逐条比对内容。真实库上这四段
加起来 0.5～2.3 秒（实测见 [同步的预演与落地都走 SSE 报进度](./2026-10-03-sync-progress-streams-over-sse.md)），
而这几秒里用户已经做过决定了：那份清单他刚看过，输入没变，`planSync()` 是纯函数，算出来必然是同一份。
按下「确认同步」到第一条拉取之间那几秒空档就是它。

## Decision

预演算出来的计划与它的输入一起留在宿主侧（`src/sync.ts` 的 `SyncPrepared`），预演的响应里带回一个
`planId`；确认那次带着它回来，宿主就照着那份数据落地（`syncPrepared()`），不再算第二遍。

留下的输入：本机整库（`DiscoveredSession[]`）、远端索引、项目身份（含预演问过 git 的那些目录）、比对
阶段算过的内容指纹、宿主投影缓存里那两件事（空白与两枚活动时间）。落地那一段
（`applyPreparedSync()`）因此几乎不问宿主任何东西：不扫库、不读投影缓存、不重算指纹；项目身份接着用
预演问过的那些目录（预演一个身份条目都没见过时它一个目录都没问，那几条要推的目录这时候才问一次 git）。

那份数据描述的是预演那一刻，本身会旧，所以落地前先验一遍（`stalePlanReason()`），五处：

- 这份计划是**拿哪套输入**算的（远端地址、机器名、映射表、三个库位置）：确认时宿主会重新解析同步设置，
  拿旧的映射表落地就会落到用户刚改掉的那个目录以外的地方（凭据不进这份摘要：它只影响读远端）；
- 本机的**代次文件**：目录里的日志文件不多不少，每个文件的字节数与 mtime 都还是预演那一刻那个；
- **投影缓存那两件事**（空白、最后活动时间）：它们决定"这条参不参与""两边谁更新"；
- 计划里要**覆盖本机**的那几条，宿主这会儿还没拿在手里：覆盖要撤掉本机目录，与删除拒掉活会话同一个理由；
- **远端那份索引**：重读一次、比一次指纹（比的是字段拼出来的摘要，不是文件字节）。

对得上就照走（结果里 `planSource: { kind: 'reused' }`，`plan` 就是用户确认过的那一份）；对不上就整个
从零重算一遍（`planSource: { kind: 'recomputed', reason }`）。**判据是结构性的，不是"预演过去多久了"**：
按时间只能保证"不太旧"，而看文件集合、字节数与 mtime 才既能隔着多久都照走、又能在只隔一秒而那条会话
刚跑完一轮时看出来。

预演那份只留一份、而且一次就消费掉（`src/web.ts` 的 `preview`）：界面一次只开一个同步弹窗，确认必须
用它自己那次预演的结论；拿着旧号码回来的那次落到"从零重算"那条路——不错，只是慢。

## Alternatives considered

**什么都不做（确认时重算）。** 计划是纯计算，重算的结果确实一样——代价是用户按下确认之后那几秒里界面
只有一个不动的按钮，而那几秒本来可以开始一条条拉取了；预演的 0.5～2.3 秒（冷启动更多）已经在同一条
路上花过一次。

**照预演那份直接落地，不验新鲜度。** 用户读清单的那几十秒里，本机可能又跑了一轮、别的机器可能推过
东西。那两个字是最贵的一类错误：计划说"远端更新，覆盖本机"，照旧执行就是拿一份旧的判据**撤掉本机
目录**（旧的那份只在备份里）。验一遍是几次 stat、一次目录 readdir 加一次远端索引读取，比全量重算小
一个量级。

**把新鲜度交给时间**（"预演超过 N 秒就重算"）。N 选小了等于没优化，选大了就是拿一个与事实无关的数
担保正确性；而"这条会话刚跑完一轮"这件事与过了多久没有关系。

**让预演把整包（`.dshsess`）也造出来，确认时直接 PUT。** 预演要为此把每一条会话的日志读出来、gzip
一遍、整库留在内存里（实测 84 条会话上传 65.5 MB），而预演是只读的——它不该为"也许会被确认"付这份
钱。落地时该读的日志本来就要读（要打包装），省下的只是"同一份计划再算一遍"。

**把计划连输入一起回给浏览器，确认时再送回来。** 计划里带着本机库的绝对路径与每一个代次文件的位置，
往返一趟既大又让浏览器成为"要写什么"的输入来源；`planId` 只指认宿主自己手里那份，不搬数据。

## Consequences

- `/sync` 的两次调用成了一件有状态的事：`POST /sync?mode=apply` 的体里带 `planId`。对不上（宿主重启过、
  旧客户端没带、又一次预演把它换掉了）就退回从零重算——原来的形状仍然完整可用，只是慢。模型工具
  `sync_sessions` 是单次调用，没有这一项（`runSync()` 算完就用）。
- 照预演走时，落地那次的进度只剩一条 `remote`（重读远端索引）+ 拉取 / 推送两段；退回重算时照旧把算
  计划那几段报一遍。界面两边都认，`planSource.kind === 'recomputed'` 时在成功横幅上多一句说明——
  确认时看到的条数与结果对不上时，得有人解释。
- **预演之后新建的会话这次不参与**：它不在那份计划里，下一次同步会带上。判据只覆盖"计划提到的那些
  事实有没有变"，不去枚举本机有没有多出别的东西。
- 预演那份数据在宿主侧占一份内存（整库扫描结果 + 比对过的指纹），只留一份、一次消费；预演算出来的
  指纹会被落地直接写进自己那格的索引（那些字节刚验过没变）。
