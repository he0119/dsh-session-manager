# Agent Note: 异步化的边界是阻塞预算，不是“所有 I/O 都异步”

Status: implemented

## Problem

“把操作都改成异步”听起来像一条统一标准，但它解决不了真正的问题，还会带来新的复杂度：

- 很多同步调用只有几毫秒（注册表、`sync-state`、备份清单、一次 `stat`），改成 `fs/promises`
  只是多一层 Promise 与线程池调度；
- `async` 函数里仍可能调用 `readFileSync()` / `gunzipSync()`，函数签名变了，主线程照样被按住；
- 把小的原子写（临时文件 + `rename`）拆成多个 `await`，会给别的请求留下看到半成品的窗口，
  要全异步就得同时加锁；
- Node 默认线程池只有 4 个，把大量小文件 I/O 都改成异步，反而会让真正的大读排队。

所以需要一条能判断“哪里该改、哪里不该改”的线，而不是“全改”或“全不改”。

## Decision

用**阻塞预算**判断，按用户能感觉到的停顿划线：

- **10 毫秒以内**：同步可以接受，例如小 JSON、单次 `stat` / `exists`、短小的 `rename`。
- **10～50 毫秒**：偶尔可以，但不要放在逐条循环里；一个项目目录里每条都来一次就会累加。
- **超过 50 毫秒**：应该让出事件循环。
- **超过 200 毫秒**：必须异步、分片或交给线程池；用户点一下就要等的地方尤其不能有。

具体做法：

- **只在边界异步**：网络、整份文件读写、大包解压、跨进程复制走 `fs/promises` / `zlib` 异步入口。
- **CPU 工作要分片**：异步读文件不等于异步哈希/解压；哈希按 8 MB、解压按 128 KB 分块，块间
  `setImmediate`；扫库每 16 条会话让出一次。
- **短小的临界区保持同步**：注册表、同步状态、备份清单、配置、`existsSync` / `statSync`、
  `writeFileSync(tmp) + renameSync`。它们要么很小，要么必须原子完成；为它们全链路改 `async`
  不划算。
- **不为了形式统一改签名**：`canonicalDir()` 这类被大量纯函数调用的短操作继续同步；只有真的
  跨过预算的路径才改成异步。

这条线不追求“所有 I/O 都是异步”，只追求“没有一段同步代码长时间占住事件循环”。

## Alternatives considered

- **把所有同步文件 API 都换成 `fs/promises`**：签名会扩散到计划、注册表、路径归一化等大量纯函数；
  小的原子写被拆开之后还要加锁；收益主要是形式统一，不是响应性。
- **把整个插件搬进 worker 线程**：数据要跨线程拷一份（几十 MB），附件端口、宿主服务与进度回调
  都要重新搭桥；复杂度高于收益。
- **只改函数签名，不管内部实现**：`async function` 里仍可以 `readFileSync()`；这类改动看起来
  完成了，实际停顿一点没少。
- **只做导出/同步这些“大动作”**：导入、日志首次打开、迁移落地同样会让用户等；按预算逐个判断，
  比按功能分类可靠。

## Consequences

- 代码里会同时存在同步与异步文件调用；判断标准是上面那条预算，不是“看到 `Sync` 就改”。
- 小的同步调用保持简单、原子；大的路径有明确的让出点，最长停顿按操作量而不是按库大小增长。
- 新增一条 I/O 路径时，先问“这一次会不会超过 50 毫秒”；会，就按分片 / 异步 / 线程池处理，
  并把让出点写进测试（例如扫库那条第 16 条之后必须已经让出）。
- 与这条线配套的实测与取舍见
  [迁移、差异与导出不再整份解压 / 压缩日志](../bug-fix/2026-11-14-long-ops-stop-blocking-the-host.md)。
