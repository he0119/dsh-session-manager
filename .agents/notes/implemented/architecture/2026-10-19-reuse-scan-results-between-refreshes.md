# Agent Note: 库没变时复用上一次的扫描结果

Status: implemented

## Problem

设置页每次打开、每次点刷新都要扫整库（`GET /state`：走遍项目目录、读每条会话的日志头、再从宿主的投影
缓存里取标题与空白判据）。本机真实库上的规模：23 个项目目录、998 条会话、1005 个日志文件，日志合计
619 MB，宿主的投影缓存 1003 个文件、合计 169 MB。

[读什么、读多少已经压过一轮](2026-10-19-scan-reads-each-thing-once.md)：日志只读开头 64 KB、每条会话的
投影记录只读一次。但**每次刷新仍然从零重做一遍**——打开页面、切页签回来、点刷新，都是同一份库、同一个
结果，再算一遍要一秒多。

## Decision

把上一次的结果留在内存里（一个插件实例一份），下一次先做一趟**指纹**，指纹一致就直接返回它。

指纹是这次走目录得到的一张清单，逐行列出来：

- `p:<项目目录名>`、`s:<项目目录>/<会话目录>`：有哪些项目目录、哪些会话目录（新增或删除一条会话会改它）；
- `f:<项目目录>/<会话目录>/<日志文件名>:<size>:<mtimeMs>`：每个日志文件多大、什么时候改的；
- `c:<缓存文件名>:<size>:<mtimeMs>`：投影缓存目录（`paths.projectionCacheDir`）里每个文件同样两样。

三样缺一不可：

- **`mtimeMs` 是必须的那一枚。** 实测把一份日志原样写回（字节完全一样）：`size` 不变、inode 不变，只有
  `mtimeMs` 变了。所以"大小 + inode"不足以当判据。
- **目录清单也要在。** 新增或删除一条会话不改任何已有文件的 `mtime`。
- **投影缓存文件也要在。** 标题、空白判据与两枚活动时间是从那些文件读出来的；少了这一样，宿主给一条会话
  写了新标题之后缓存会说"没变"。

### 时间戳精度：racy 窗口按"上一次取指纹的时刻"算

有些文件系统的 `mtime` 只有一秒精度（本机实测是亚毫秒）。同一秒里改两次、大小又一样时，指纹看不出区别。
做法照 git 的 racy 处理，但基准取**上一个指纹是哪一刻取的**，不取"现在"：

> 这次走目录时，只要有任何一个文件的 `mtimeMs` 落在"上一次取指纹的时刻"前 1 秒以内，就不复用缓存。

用"上一次的时刻"而不是"现在"是关键：库静止时文件时间戳早已比那一刻更旧，这条不触发；被追加的日志本来
每次都会改指纹，重扫是应该的。取"现在"的话，一个正在跑的会话会让缓存**永远**不命中。

### 没有"自己写完就作废"这一步

迁移落地、回滚、导入落地、同步拉取、删除、重新生成名称这些写盘动作都没有显式作废缓存。理由是上面那条
racy 规则已经把它兜住了：写盘一定改 `mtime`，指纹随之变化；唯一看不出来的情形是"改动落在上一次取指纹
的同一个时间刻度里"，而那种文件的 `mtimeMs` 必然落在那 1 秒窗口内，于是不复用、重扫。多写一份作废表只会
多一处可能与磁盘不一致的状态。

### 只给 `GET /state` 用

迁移计划、同步预演与落地都在动作之前重新扫一遍，不走这份缓存：那几步马上要动磁盘，值得看最新的。缓存只
影响"看到多新"，不参与任何写盘判断。

## 另外一条路：宿主内存里的投影（量过了，不是那笔大钱）

宿主的 `ctx.sessionProjectionCache.cachedSnapshot(header)` 在它自己的会话列表里是零 I/O 的：服务启动时把
整个 `session_projcache` 域读进内存，列会话时从内存里取。按它自己的说法，这是"as stale as the last
durable checkpoint but never wrong"。

但它在真实宿主上**只服务一部分投影**。2026-10-19 在一份 996 条会话的库上实测：不带 keys 读一条记录，
返回的键是 `title`、`goal`、`tokenUsage`、`contextPressure`、`contextBreakdown`、`inbox`、`sessionStats`、
`turnOutline`、`agentPreset`、`userQuestions`、`permissions`、`workingDirectory`、`subagent*`、`todos`、
`plan`——**没有 `sessionListMetadata`，也没有 `timeContext`**。

而这两个键在磁盘上是有的：每个记录文件的 `rows` 里都有 `sessionListMetadata`（`ver: 1`）与
`timeContext`（`ver: 2`），与宿主里那份单元的 `stateVersion` 也对得上。宿主那一侧只服务"这次注册过
`wire`"的单元，那两个键不在服务的集合里。所以在**空白与两枚活动时间**上，这条路给不出东西。

它只能替掉**标题**这一半。而在"文件反正要读一遍取空白"的前提下，三种做法是：

| 做法 | 每条的缓存文件读 | 宿主调用 | 评价 |
| --- | --- | --- | --- |
| 标题、空白各读一趟 | 2 趟 | 0 | 对，但读了两遍 |
| 标题走宿主、空白读文件 | 1 趟 | 1 次 | 省掉一趟，但多一个数据来源与一套身份校验 |
| 标题与空白都读文件、只读一趟 | 1 趟 | 0 | 同样省掉一趟，判据只有一处 |

后两行省掉的是同一趟 169 MB 的读，而第三行少一个数据来源、少一套"两边答得不一样怎么办"的处理。所以
**这条路不该单独做**。第三行已经交付（见开头那篇笔记）。

另外两枚实测数字留着备查：那次 A/B 里宿主调用一共 3 600 次、合计 684 ms（≈0.19 ms/次，机器当时负载
偏高），其中 45 条会话宿主说"没有这条记录"（要退回读文件）。

## Alternatives considered

- **只做"少读"，不做缓存。** 那一步已经做了，但重复打开仍是每次一秒多，达不到"打开就出来"。
- **把扫描结果落盘，跨进程复用。** 宿主重启之后第一次也快；代价是自己管版本号、原子写与损坏兜底，而收益
  只在"刚重启"那一小段。
- **用 `fs.watch` 监听变化，省掉指纹那一趟。** 省下的是二十来毫秒，换来的是事件丢失、重命名、溢出这些要
  处理的情况，相对一秒多不值。
- **指纹里加内容哈希。** 那等于把文件读一遍再比，省不下读的量。
- **用宿主 `sessionPersistence.list()` 代替自己走目录。** 它每次仍要逐条读 header（内部有限并发），省不到
  读的量，还会把"哪条会话在库里"的判据让给宿主——现在这条判据（临时文件、坏目录怎么跳过）是本插件自己的。
- **显式作废（写完盘就丢掉缓存）。** 见上面那一节：racy 规则已经覆盖，多一份作废表多一处会与磁盘不一致的
  状态。

## Consequences

- 库没变时第二次及之后的 `/state` 扫库这一段：本机真实库 **25 ms**（第一次冷页缓存 1912 ms）。紧挨着的第二
  次会多扫一遍（1314 ms），因为刚写过的文件落在 racy 窗口里——第三次开始命中。
- 命中那次的结果与真扫一遍**逐字段一致**：998 条会话，会话集合与顺序、每条的头字段、标题、空白判据、文件
  清单与字节数，0 处差异。
- 指纹那一趟的开销随文件数线性增长：2000 个文件约 20 毫秒。库大十倍是 200 毫秒，仍远小于一秒多。
- 内存常驻约几 MB（只留 header、标题、文件清单，不留日志内容）；只留一份结果，配置改了键对不上就重扫。
- **"改了但指纹没变"会静默返回旧结果**——这是这份缓存唯一的失效面，判据就是上面那三样加 racy 窗口。它不
  影响写盘：缓存坏了最坏是显示旧标题，不会让某个动作做错。
- 指纹的"有哪些日志"与扫描的"有哪些日志"用同一个函数（`parseSessionLogName()`），否则会出现"指纹说没变、
  扫描却扫出别的文件"。这一条由实现本身保证：两边都调它。
