# Agent Note: 远端建目录在同一次同步里只发一轮

Status: implemented

## Problem

`put()` 写每个文件前都要把父集合逐层 MKCOL 一遍，而远端路径固定两层（命名空间 + 机器格），于是一次
推送里 N 个包产生 2N 次 MKCOL——除头两次外全是「已经有了」的 405。

协议上这没错（405 就是幂等的落点），代价却是实打实的：WebDAV 服务端的日志里每个文件都顶着两行建目录
事件，看起来像同步在反复重建已存在的文件夹；请求量也是文件数的常数倍。

## Decision

`createDavClient()` 里用一张实例级的 `ensured` 集合记住已经确认存在的层级（相对资源根的前缀），
`ensure()` 碰到记过的层级直接跳过。201 / 200 / 204（这次建的）与 405（服务器说已经有了）都入账，
其余状态照旧抛错、不入账。

- 缓存只在**一个客户端实例**里有效：每次同步都新建客户端（`syncRuntime()`），所以下一轮同步还会各问
  一次。远端可能被别的机器或别的工具改动，跨调用缓存等于替远端做主。
- 换来的边界：这一轮里远端集合若被别处删掉，后面的 PUT 会直接失败（409），不会自动重建。一次同步的
  寿命内不值得为此每次多问。
- 也不改成「先 PROPFIND 判存在再决定要不要 MKCOL」：那是每个文件多一次读请求，正是要消掉的噪音。

## Alternatives considered

**保持现状（每次 PUT 逐层 MKCOL，靠 405 幂等）。** 协议上没错，但 N 个文件里的 2N 次请求绝大多数是
空转，服务端日志也就一直是现象里的样子。

**把缓存提到 `syncRuntime()` 或更上层，跨工具调用共享。** 省下的同样只是每轮两次 MKCOL，换来的却是
一份「远端还没建」的判断要跨调用维护与失效，收益与责任不匹配。

**只缓存命名空间那一层（`SYNC_NAMESPACE_DIR`），机器格照旧每次 MKCOL。** 省一半，但剩下那一半同样
空转，没有理由留着。

## Consequences

- 一次推送的 MKCOL 请求从 2N 次降到 2 次（N 为这一轮要推的包与索引数），远端日志里不再每个文件顶着
  两行建目录。
- `test/dav.test.ts` 钉住两条：同一客户端里重复 `ensure()` 只发一次 MKCOL；同一目录连续 `put()` 的
  请求序列恰好是「两次 MKCOL + 三次 PUT」。
