# Agent Note: 导入会话的合成附件引用不算"缺附件"

Status: implemented

## Problem

一轮手动同步在状态栏挂出一组「缺少附件」，其中一批是 `C:\…\dsh-temp` 下 2025 年到 2026 年那些
"上传文献问问题"的会话：48 条会话、54 个对象。它们引用的 PDF 本机没有，远端共享库里也没有，于是每一趟
同步都去远端问一次、404 一次，然后报一句「持有这些对象的机器还没推送它们」。

这句话是错的。这些对象没有哪台机器持有，也永远不会有：它们来自
`@deepseek-ai/dsh-deepseek-chat-import`——官网导出的非图片文件不带宽字节，导入器为了让卡片显示文件名与
大小，按导出里的文件 id 算了一个看起来合法的附件引用（源码 `conversation.ts` 的 `syntheticFileRef()`，
注释原文「no attachment object exists for it」）。于是"等一台机器把字节推上来"这件事根本不存在，
清单里这一组既清不掉、也没有可执行的处置，还把真正要人看的失败挤到后面。

判据不能只看"日志里出现过那个包名"：实测一条普通会话（来源是 `workbuddy`）因为工具输出里打印过这个
包名，整份日志含这个字符串——按子串判会把它错当成导入会话，于是它**真正缺的附件**永远不报了。

## Decision

- 认会话的判据是 assistant 消息的来源名：`isImportedSessionLog()` 先按
  `IMPORTED_SESSION_PROVIDER`（`deepseek-chat-export`）子串预筛，命中行再解析、确认
  `type === 'assistant/message'` 且 `data.message.source.provider` 等于它。会话头里没有导入痕迹，
  只能看正文。
- 只在**报账**那一侧豁免：`fetchAttachment()` 的 404 与 `repairAttachments()` 的"远端也没有"都不再
  记这一笔，`collectLeftovers()` 因此不再点名。取回、上传、计数一概不变。
- 粒度是**对象**不是会话：同一批里那个对象被**所有**引用它的会话都认成导入会话时才忽略
  （`ignoreAbsent`）。导入会话里的图片是真存下来的（导出带字节时导入器写进附件库），它们照旧被取回；
  同一个对象若还被一条真实会话引用着，缺失照旧报。
- 判定与引用共用一次解码：`attachmentRefsOfFile()` 把 `imported` 和 `refs` 一起缓存在
  `size + mtimeMs` 键上，第二次同步不再付。清单来自索引（这一趟没解日志）的会话只在**真有本机缺对象**
  时才补解一次——整库那些对象齐的会话照旧一个字节都不解（那一步的预算见
  [补附件对象不再整库解压日志](2026-11-14-sync-attachment-scan-blocks-the-host.md)）。

## Alternatives considered

- **按子串判断**：便宜，但会被正文误伤（上面那条 `workbuddy` 的会话），结果是真缺的附件不再报。
- **整条导入会话一律不看附件**：会丢掉导入会话里真实存在的图片——那些字节确实在，也确实要从共享库
  取回来。
- **对所有会话都判一次导入**：判据要读日志，等于把"整库解压 144 秒"放回每一趟同步；限定在"本次真有
  本机缺对象"的会话上，代价只有那几十条。
- **改导入器别写 attachmentId**：那是另一个包（`@deepseek-ai/dsh-deepseek-chat-import`），而且它写的是
  宿主的 `FileAttachmentRef` 契约，改形状要跨包协调；本包先不做假警报。
- **手删日志里的引用**：日志是多帧 zstd，仓库只有"重写第一帧"的能力；改完还会顺着同步覆盖远端那份，
  再导一次官网数据又回来。改判据不动用户数据。

## Consequences

- 这类会话不再出现在「缺少附件」里，也就不再提供「只看这一条」——它本来就没有可做的事。
- 远端索引里仍然记着这些合成引用（那是"这条会话引用了什么"的事实），别的机器读到也会同样忽略，
  不必各写一份判据。
- 认不出来源的会话（老日志、只有用户消息、来源名被别的工具改写）按**不是**导入处理：宁可多报一句，
  也不静默吞掉真正缺的附件。
