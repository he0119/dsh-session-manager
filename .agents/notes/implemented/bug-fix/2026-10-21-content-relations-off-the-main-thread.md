# Agent Note: 内容判据不再按死宿主主线程，也不再每轮重算同一对

Status: implemented

## Problem

自动推送每五分钟跑一轮，每一轮都会对"两边各自写过"的那些会话读整份日志判谁是谁的前缀（`src/sync.ts`
的 `contentRelationsOf()`）。这一段原先做三件会占住主线程的事：

1. `deps.dav.get()` 取回远端那个会话包之后，`readBundle()` 用 `gunzipSync()` 整份解开；
2. 两边日志各用 `decodeAll()` **一次性**解压——它是纯 JS 的 fzstd，整份塞进去一次算完；
3. `readFileSync()` 读本机那份，`split('\n')` 之后交给 `diffSessionLogs()`。

每一项都是同步的，而且只在"取远端包"那一处 `await`，所以一对大日志就能把主线程按住一两秒。本机拿真实
会话库量过（三条十几 MB 的日志造成三对分叉）：

| | 一轮总耗时 | 主线程被堵总时长 | 最长一次 |
| --- | --- | --- | --- |
| 改前 | 5.0 s / 5.2 s（连跑两轮一样贵） | 3.0 s / 3.3 s | 1.4 s / 1.6 s |
| 改后 | 11.3 s / 0.37 s（第二轮全部命中缓存） | 1.0 s / 0.3 s | 0.27 s |

单份日志的解压也量过：压缩后 13.7 MB、解开 48 MB 的那一份，整份解压 1826 ms 期间主线程一步不动；
分块（128 KB）之后总耗时 2069 ms，但最长一次只停 58 ms。

宿主和网页服务是同一个进程：主线程被按住的这段时间里，`/state` 与别的请求全排在这条链子后面。线上那次
"网页一直转圈、SSH 秒回"就是这个形状；再叠上 cgroup 的 `MemoryHigh` 与打满的交换分区，进程被按在 `D`
状态里，看起来像整台机器卡死。

另一半是重复劳动：自动推送每五分钟算一次，可"两边都没再动"的那几对照样从 NAS 重下一份包、重解两遍、
重比一遍——同样的输入、同样的结论，白花时间。

## Decision

`contentRelationsOf()` 改成三件事：

1. **不整份解压**：新增 `src/log-decode.ts` 的 `decodeAllChunked()`，用 fzstd 的流式 `Decompress`
   按 128 KB 一块推进，块与块之间 `setImmediate` 让出一轮事件循环；块边界切在多字节字符中间时由
   `StringDecoder` 兜住。输出与 `decodeAll()` 逐字符一致（多帧也一样），代价是总耗时多约 13%。
   流式认不出的（一个 Raw 块超过 128 KB，这种数据本来就不合法）退回整份解压：宁可多停一会儿，也不能
   把一份读得出的日志判成"读不出"。
2. **包与文件走异步入口**：`transfer.ts` 拆出 `parseBundle()`，新增 `readBundleAsync()`
   （`zlib.gunzip` 的 Promise 版，解压在线程池里）；本机那份改用 `fs/promises` 的 `readFile`。
   每一对之间也 `setImmediate` 让一次。
3. **同一对不再重算**：模块级的 `contentRelationCache`（上限 512 条，丢最早的），键是两边**全部代次**
   的 `代次:sha256:字节`。任何一边动一个字节都会换键，所以它只省重复劳动、不改变判据；本机那侧只要
   有一个代次没拿到指纹就不缓存（缺哈希的键可能把两份不同内容认成同一对）。测试要用隔开的缓存时注入
   `deps.relationCache`。

## Alternatives considered

- **把这一段丢进 Worker 线程**：主线程彻底不参与，但插件产物是单文件打包，Worker 入口要另出一份产物，
  构建与 `check:package` 都要跟着改；而且 `decodeAll` 是宿主注入的解码器，搬进 Worker 还得把它一起传
  过去。收益是"完全不占主线程"，代价是这一套结构翻倍，先不做。
- **改用 `node:zlib` 的 `zstdDecompress`（线程池）**：确实完全不占主线程，但它只解**第一帧**——会话日志
  是"一个代次一帧"的多帧文件，得自己写帧切分；`engines` 还允许 Node 22，那里没有这个 API，得再加一条
  回退路。等宿主最低版本抬到有它的那天，再拿它换掉分块这条。
- **只推不拉时干脆不算内容关系**：省得最多，但那样"本机续写了对方没有的条目"这一对就再也推不上去
  （计划里它退回 `diverged`，两条都不动），自动推送会静默地漏推，不能接受。
- **给这一对设大小上限，超了就跳**：同样是静默漏推，而且用户看到的是"这条大会话怎么不同步了"，比多花
  几秒更糟。

## Consequences

- 宿主主线程上最长的一次停顿从"单对日志整份解压"降到约 0.3 s（本机三条大日志实测），网页请求不再被
  一次同步整段挡住；一轮总耗时略长（分块与异步入口的代价），但第二轮起几乎为零（缓存）。
- 第一轮仍要把两边日志读一遍、解一遍，内存峰值随日志大小走（本机三条大日志约 0.86 GB）。这属于"一次
  同步本来该花的钱"，但宿主侧的 cgroup 上限（`MemoryHigh` / `MemoryMax` / 交换分区）仍要留够余量，
  否则大批量解压还是会把它推到换页。
- 缓存只在进程里：重启后第一轮照旧全算。它按内容哈希做键，不按时间，所以不会因为"过了五分钟"失效。
