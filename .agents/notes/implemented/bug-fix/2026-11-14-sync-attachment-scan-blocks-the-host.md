# Agent Note: 补附件对象不再把整库日志解压一遍

Status: implemented

## Problem

同步收尾那一步「补对象」（`repairAttachments()`）要为**每条**本机会话算一遍"它引用过哪些附件"，
而这件事只有一个办法：把日志整份解压、按行扫 `attachmentId`。这个函数原来是同步的
（`decodeLogText()` → 一次 `decodeAll()`），外面那层 `for (const session of local)` 也没有任何
`await`——整库多大，主线程就被按住多久。

本机实测（1475 条会话 / 1491 个日志文件 / 1.2 GB）：

| 步骤 | 实测 |
| --- | --- |
| 整库附件扫描 | **144 秒**，最慢的单个文件 2.3 秒 |
| 冷启动算内容指纹（1.2 GB） | 3.1 秒 |
| 扫本机（只读文件头） | 0.58 秒 |

宿主是单进程单线程：这 144 秒里页面的请求、长连接、工具调用全部排队，表现就是"同步一跑 CPU 一个核
跑满、整个 DSH 卡住"。它只在**手动同步**时跑（自动推送那条路 `pushOnly === true` 会跳过），所以是
"有时候"；而且每次都重扫，日志没变也照解不误。推送 / 拉取每条会话前也要为找附件把那条日志整份解一
遍——一条 16 MB 的日志就是 2.3 秒。

## Decision

四处一起改：

1. **索引条目里记下附件清单**（`RemoteSessionEntry.attachments`，`{kind, id, name?}`）：
   - 推送时顺手写进去（推送本来就要扫一遍）；
   - 补对象时，本机副本与远端条目**判成一样**（`identical`）就直接用这份清单，一个字节的日志都不解；
   - 自己那一格的老条目（清单缺席）扫一次后补写回索引，下一次连扫描都不需要；
   - **空数组 = 查过、一个都没有**，与"没查过"（字段缺席）必须分得开，否则没有附件的会话会被反复扫。
2. **扫描改成异步分块**：`attachmentRefsOfFiles()` 用 `decodeLogTextChunked()`（128 KB 一块、块间
   `setImmediate`），逐条会话报 `attachScan` 进度（`ProgressPhase` 新增一段）。最慢的单次停顿从
   2.3 秒降到约 0.1 秒。
3. **按文件缓存扫描结果**（`size + mtimeMs`，与指纹缓存同一套判据）：同一份文件在一个宿主进程里只解
   一次。实测第二轮从 144 秒降到 8 毫秒。
4. **冷启动指纹也分块**：`contentFingerprintChunked()`（8 MB 一块、块间让出）在 `prepareSync()` 里
   先把两边都有的文件算完，`planSync()` 只查表——它仍然是纯函数，测试注入 `fingerprint` 时走老路。
   整库 1.2 GB 从"一次 3.1 秒"变成"总耗时 1.1 秒、最长一次停顿 264 毫秒"。

顺带修掉一个判据错误：`attachmentActionOf()` 在引用没有 `bytes`（索引里不存它）时原来直接判
`present`，于是"本机缺、远端有"的对象永远取不回来。现在先看文件在不在，再看字节数。

## Alternatives considered

- **把扫描丢进 worker 线程**：主线程确实解放了，但仍然占满一个核、多一条消息通道与生命周期要管；
  索引清单 + 缓存直接把这份活去掉，worker 只是把"卡"换成"慢"。
- **把扫描缓存落盘**：能帮到"远端条目还没有清单、写它的机器也还没升级"的那段时间，但索引清单补上之
  后这份缓存就没人用了；多一个文件格式与失效规则，不值得。
- **干脆不补对象**：老会话（升级前推的、拉坏的）就永远修不回来，这正是当初加这一步的理由。
- **只扫最新一代日志**：代次文件是同一份日志的不同格式代（1491 个文件对 1475 条会话），省不到 1%。

## Consequences

- 常规手动同步不再解压任何日志：索引里有清单、且两边一样的会话直接跳过扫描。（本机独有、远端索引
  压根不认得的会话没有条目可记，仍会扫；它们通常是还没同步过的新会话，量很小。）升级后的**第一次**同步仍要扫一遍
  没有清单的老条目（本机约 127 秒），但主线程每 100 毫秒左右就让出一次、进度条逐条走，DSH 全程可用。
- 远端索引每个条目多一小段（带附件的条目约 +0.1～0.2 KB），整份索引仍在 0.5～0.7 MB 量级；`attachments`
  是可选字段，加它没有升索引版本，老宿主读得进、写回时丢掉，下一次补扫会补回来。
- 补对象偶尔会**再写一次索引**：只发生在"自己那一格的老条目第一次被补上清单"的那一趟。
- 推送 / 拉取时那条会话的日志仍是解一遍（要判对象缺不缺），但改成逐块解压，单条大日志不再把宿主按
  住两秒。
- `docs/formats.md` 的索引字段表、`docs/flows.md` 的同步流程与 `docs/internals.md` 的索引都跟着改。
