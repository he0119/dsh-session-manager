# Agent Note: 宿主持着的会话不搬，但要说出来

Status: implemented

## Problem

一次迁移做三件事：搬会话目录、把日志 header 的 `cwd` 改成目标、把这几条挂到目标工作区（第三件交给
宿主自己做，见[改完注册表把活儿交给宿主自己做](../architecture/2026-10-05-hand-the-change-to-the-host.md)）。

第三件在**一条会话还活着**时必然失败。宿主 `attachSession()` 校验 `cwd` 用的是**它内存里那份**
header（`ctx.sessions` 里那条，`liveSessionIds()` 读的就是它），而活的会话内存 header 还是旧路径——
磁盘上改好了也没用，回绝的话是 `its cwd resolves to '<旧路径>'`。失败还只是第一步：
`ensureWorkspace()`（新建目标工作区）走的是 `dsh-storage-json` 的单单元契约，宿主拿内存里那份
**整份落盘**，插件刚写好的 `workspace.json` 当场被盖回改动前的样子。于是磁盘上是"旧归属 + 已经搬走
的会话目录"，重启之后宿主按磁盘算归属：这批会话谁都不算，全落进侧边栏的「未分组」，目标工作区 0 条。

本机的现象就是这个形状：一次 51 条会话的迁移（日志与目录都搬到位、目标工作区也写进了注册表），宿主
在 `02:55:54.680Z` 新建了一条 `sessionIds: []` 的工作区记录（`updatedAt` 与 `createdAt` 同一毫秒），
迁移写的那条记录从磁盘上消失；10:57 那次重启之后 22 条会话落进「未分组」。宿主持着的会话不止一条：
本机观测到 26 条（重建索引与冷读都会把会话留在内存里），迁移撞上的那条只是其中一个。

## Decision

- **计划里就把它们摘出去**：`buildRelocationPlan()` 收一个 `live` 集合（`BuildPlanOptions.live`，
  由 `MigrateDeps.liveSessionIds()` 从 `ctx.sessions.list()` 取）。宿主持着的会话不进候选——日志不搬、
  不进注册表变更，因此留在原目录、归属仍归源工作区，源工作区不会被摘空、更不会被删。
- **点了名就报问题**：用户显式点名一条宿主持着的会话时报一行 problem（`ok=false`，不许静默少搬），
  说清"它活着、这次搬不动、重启 DSH 之后再迁"；整个来源都活着时也给这条原因，而不是"没选中会话"。
- **没点名就如实报出来**：`RelocationPlan.liveSkipped` 一路带到工具返回值（`liveSkipped` 计数 + 摘要里
  逐条列出 id）与界面（`preview.liveSkipped` 与 `migrate.liveSkipped` 那行提示）。少搬几条可以，
  不说才是坏账。
- **宿主没接住那一步时，把这次算好的注册表整份写回文件**：`takeEffectOnHost*()` 收下注册表终态
  （`TakeEffectOptions.registry` 与 `EffectDeps.registryPath`），失败路径上写回，并把
  `registryRestored` 记进 `EffectOutcome`；措辞由 `describeEffect()` 分岔——写回去了才敢说"重启后
  一致"，没写回去就如实说"宿主可能已经覆盖过磁盘，重启前先核对"。迁移 / 导入 / 同步三个落地口共用
  这一份。

## Alternatives considered

**照旧搬，等宿主回绝了再靠回滚收场。** 回滚要重放备份里的日志与注册表、用户还得从头再跑一次，而这段
窗口里磁盘上的状态是坏的（会话已经搬走、归属还在旧工作区）；更糟的是"回绝"不是必然发生——宿主可能
挂上了一部分才失败，那时磁盘上的注册表已经被它盖过一次。

**有活会话就拒绝整次迁移。** 这条限制比它看起来宽：宿主内存里活着的会话可能是一整个工作区的量
（本机观测 26 条），而且重启之后客户端恢复某条会话又会让它变回活着的——"等它们都没活了再迁"在真实
GUI 上做不到，功能会被整个卡住。**点名**的那几条仍然拒绝，所以"用户明确要求搬这一条"这一档没有被
放松，松的只是"途中有几条搭不上车"。

**把活会话从宿主内存里摘掉，或者重挂一次 `agents.resume()`。** 那是宿主的 agent 生命周期：写句柄与
回合状态都在里面，插件伸手就会碰到别人的服务装配——重挂加载条目那次就是把 `sessionController` 一起拆掉
的（见[被否决的那篇](../../rejected/architecture/2026-10-05-reload-the-workspace-entry.md)）。而且一条正在
跑的会话本来就不该被搬走：它的日志被移走之后，宿主照样往旧路径写。

**让预演与执行两套口径各算一次 `live`。** 预演说"22 条全搬"、执行时只搬 9 条，正是这次要修的账；
两个入口读同一份 `MigrateDeps`，`/state` 报的 `live` 与计划用的也是同一个函数。

## Consequences

- 一次迁移可能是**部分**的：摘要、工具返回值与界面都会点名没搬的那几条，续迁的办法是"重启 DSH 之后
  再迁一次"（宿主松开它才会变回可搬）。
- 少搬的那批仍归源工作区，所以源工作区不会被删；源项目目录也留着（它的会话还在里面），清理空目录那
  一步因此不碰它。
- 宿主那一步没接住时，磁盘上留下的是这次的结果（而不是宿主的内存副本），"重启后一致"重新成立；
  迁移的注册表复核也因此不再因为宿主盖过盘而误报。
- `test/engine.test.ts`（计划层）、`test/migrate.test.ts`（执行 + 写回）、`test/web.test.ts`（界面端点）、
  `test/tools.test.ts`（工具层）各钉住一条，`test/client.test.mjs` 钉住界面那行提示。
