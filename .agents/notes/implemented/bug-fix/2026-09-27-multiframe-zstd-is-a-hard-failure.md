# Agent Note: 多帧 zstd 变成启动期硬失败

Status: implemented

## Problem

宿主按「一条事件一次 flush」追加写日志，磁盘上的 `.zstd` 因此是**多帧拼接**（实测单文件可达上千帧，
最大见过 6.5MB 压缩 / 33MB 明文 / 1962 帧）。而 `node:zlib` 的 `zstdDecompress(Sync)` /
`createZstdDecompress` **只解第一帧、其余静默丢弃**，连截断帧都不报错。

只解首帧，剩下的就是 session 头那一行——整个会话看起来「没有内容」。

这个坑在本仓库的开发过程中真的发生过一次：21 个日志被截成 ~180 字节，靠执行前的字节级备份才完整
恢复。它不属于「写注释提醒一下」那一类。

## Decision

把「解码器必须多帧感知」从约定变成**硬失败**：

- 解码器由调用方注入（`DecodeAll`），核心层自己**不挑**解码器；
- `assertMultiFrameAware(decodeAll)` 构造两个 raw 帧、期望读回 `"AB"`，只解首帧的解码器会让它抛错；
- 回归用例里**直接用 `node:zlib` 验证这条守卫确实会拒绝它**（`test/zstd-frame.test.ts`）。

## Alternatives considered

**在文档与注释里写明「不要用 `node:zlib` 的 zstd API」。** 事故已经证明这拦不住：那种写法在大多数
普通日志上是对的，只有多帧文件才会静默少读——错误出现在最容易忽略的地方。

**核心层自己去挑一个多帧感知的解码器。** 那会把「怎么解压」变成核心层的事，而它同时被工具层、
界面端与测试用在不同进程里；注入解码器还让测试能拿一个已知会犯错的实现去验守卫。

**自己实现多帧拼接解码。** zstd 解码本身不该由本包实现——已经有能用的库，本包只需要确认它是多帧
感知的。

## Consequences

- 守卫在插件激活时跑一次，失败就抛；宁可起不来，也不产生「看起来正常的空会话」。
- 每个读日志的入口都必须显式拿到 `DecodeAll`，类型上没有「不小心用了默认解码器」这条缝。
