# Agent Note: 宿主不认的登记不算成员，搬完剩下的要说出来

Status: implemented

## Problem

「整个来源一起搬」之后，源工作区在侧边栏里还留着——一块画出来却一条都不显示的空工作区。

本机实测（`$DSH_HOME` 那一份真实注册表，13 个工作区 / 470 条会话）：逐个来源跑一遍全量迁移的预演，
**9 个**工作区会活下来，各自还剩 1～2 条登记，共 10 条——按理由分是 4 条悬空登记（盘上早就没有这条
会话）、3 条空白、3 条已归档。搬得干净的只有 4 个，它们的登记成员全是侧边栏可见的。

三条理由是同一处口径的三张脸：迁移的候选只收**侧边栏显示的那些**（见
[迁移排除侧边栏不显示的会话](../architecture/2026-09-28-migration-excludes-what-the-sidebar-hides.md)），
而 `reHome()` 判"这块工作区被搬空了吗"看的是**登记数组**。于是：

- 已归档 / 空白 / 父会话不在这批里的子智能体：宿主认它们是成员，但它们不进候选，永远搬不走；
- 悬空登记：宿主**本来就不认**（`WorkspaceEntity.sessionIds` 按"header 的 cwd 归一 == 记录的 path"
  过滤，见 [「认领」是宿主那份成员表](2026-10-04-accounted-means-the-hosts-membership.md)），侧边栏早就
  当它们不存在；可插件判空时还拿它们当筹码，那块记录就永远删不掉。它们从哪来也是设计的一部分：
  插件删除会话时刻意不清注册表（见
  [删除先备份，且不碰注册表](../architecture/2026-09-28-delete-backs-up-and-spares-the-registry.md)）。

两种失败形态都一样难看：用户点了「全部」，迁移报"搬了 N 条"，侧边栏仍留着那块工作区，而预演与结果里
一个字都没提为什么——`liveSkipped`（宿主持着的会话）那条口子已经补过，这两条还没补。

## Decision

- **判"搬空"按宿主认的成员算**：`plan.ts` 用 `accountedOwners()` 算出**登记了却不被认领**的会话 id
  （盘上没有 / cwd 对不上记录的 path），作为 `ReHomeOptions.staleSessionIds` 传给 `reHome()`。这些 id
  不再算成员，源工作区因此能被删掉；删的时候它们随记录一起消失。
- **顺手清理被碰到的记录**：这一次真搬出过会话的那些记录里，悬空登记一并摘掉（宿主本来就不认它们，
  留着只会下次再绊一跤）。计划里没碰过的记录不动——那不是我这次的事。
- **清账要报账**：`RegistryChange.droppedStale` 记下摘掉了什么，落盘复核（`verifyRegistryChange()`）
  据此放行"这几条 id 从注册表里消失"（否则每次都会误报"会话 id 少了"）；宿主那一步也照这条清单
  `detachSession()`，不然它内存里那份还留着它们、下次自己落盘又写回来。
- **搬不走的要说出来**：`RelocationPlan.strandedSources` 列出"还剩人、因此不会被删"的源工作区与那几条
  会话（带理由），措辞收在 `describeStranded()` 一处，预演摘要、执行摘要、界面提示、工具返回值
  （`stranded`）读的都是它。留下的都是侧边栏不显示的，所以下一步只有一条：先去「会话」页处理它们
  （已归档的取消归档、空白的删掉、子智能体连着它的父会话一起迁），再迁一次。
- **只报"搬不走的"**：用户自己挑了子集时，剩下的可见会话不算 stranded（那是他点的名，不是搬不动）。

## Alternatives considered

**直接把只剩隐藏成员的工作区也删掉。** 那是数据损失：已归档的会话会在记录消失后落进「未分组」，
空白会话的归属也一起没了；而且这与"候选只收侧边栏显示的"那条决定互相矛盾——一边说"看不见的不搬"，
一边把它们的归属删掉。

**「全部」时把已归档 / 空白也一起搬走。** 真能一次清干净，但它把那条决定的语义改了（用户看到的清单
会多出他没勾过、侧边栏也看不见的会话），要动 README、界面文案与工具契约；先做报账，等真有这个诉求
再加显式开关（例如"连侧边栏不显示的会话一起搬"）。

**只报账、不清理悬空登记。** 4 条悬空登记那类残留（本机 10 条里的 4 条）会一直在，而它们连会话都不是——
报"这个工作区还剩 1 条已不存在的登记"对用户没有任何可行动作。

**判空时直接问宿主 `members()`。** 计划层是**纯计算**（零 DSH 依赖、预演不碰宿主），要它去问宿主就等于
预演也依赖宿主在线；而且宿主的答案只在"它已经看过磁盘"之后才对，计划期正是要给出"执行后会怎样"。
用 `accountedOwners()` 复刻同一条判据（`accounting.ts` 本来就是干这个的）才与预演/执行两个入口一致。

## Consequences

- 全量迁移之后，只剩悬空登记的源工作区会被真的删掉（本机 4 个），侧边栏不再留空组。
- 只剩已归档 / 空白的源工作区仍然留着（本机 6 个）——这是有意的，但预演、执行摘要与界面都会点名
  "还剩哪几条、因此不会被删、下一步怎么做"，`migrate_sessions` / `plan_session_migration` 多一个
  `stranded` 计数。
- 注册表复核多了一条放行条件：`droppedStale` 里点名的 id 允许消失；没点名而消失照旧报
  "会话 id 在落盘结果里没了"。落盘复核因此不再因为清账而误报。
- `test/residual-workspace.test.ts`（隔离夹具 + 像真宿主的端口：悬空登记不挡删除、隐藏成员留下并被点名、
  挑了子集时不误报）、`test/registry.test.ts`（`reHome()` 与复核的放行/抓错）、`test/web.test.ts`、
  `test/tools.test.ts`、`test/client.test.mjs` 各钉住一条。篡改验证四处：计划层不传 `staleSessionIds`、
  报告层永远空 `strandedSources`、宿主侧不摘悬空登记、复核不放行——各自都让对应用例变红。
