# Agent Note: 远端两格副本同代次时，更长的（续写过的那份）赢

Status: implemented

## Problem

一条会话在 A 机器上写过，被 B 拉下来继续写、再推回远端，之后 B 每次预演都会看到「重推刷新（本机续写了
N 条）」。推完一轮，下一轮还是同一句——数字一模一样，永远收敛不了。

远端索引是**一台机器一格**：B 推上去的是 B 自己那一格里的 `<id>.dshsess` 与 B 那格索引里的一条记录。
A 那格还留着 A 早先推的同一 id。读远端库时两格要合成一条（`readRemoteLibrary()`）：代次是超集的那份赢；
两边代次相同、内容不同（`relation()` 只能报 `diverged`）时比活动时间；活动时间也读不到（旧版同步推的
记录、投影缓存里没有那枚钟）就退回「格子名排序取第一个」。

最后那条兜底与"谁更新"毫无关系：`HMY-UM790PRO` 排在 `vibe-coding` 前面，所以 B 推上去的、续写过的那份
永远被 A 的旧副本盖住。计划拿本机文件与 A 的旧副本比，内容判据说"本机续写了 1 条"，于是每一轮都要求
重推；推上去写进 B 那一格，下一轮合并又输给 A。

## Decision

两格同代次、内容不同时，先比**最高代次那个文件的字节数**：日志是追加写，同代次更长的那份就是续写过的，
`longerSide()` 判它赢；字节数也一样才退回活动时间，再不行才按格子名排序。

## Alternatives considered

- **让"自己这一格"优先。** 每台机器都对着自己的格子比对，于是 A 认为自己是同步的、B 也认为自己是，
  两边的差异被悄悄藏起来：A 再也拉不到 B 的续写，B 也不再推。比现状更糟。
- **合并时读两格的包做内容比对。** 判断最准，但一次预演要为每一对重复的会话下载两份包（本机 50 对、
  约 150 MB），把预演从 2 秒拖到几十秒。
- **推送时顺手改对方那格的记录。** 格子是各机器的所有权，改别人的记录会让两台机器互相覆盖。
- **按"哪个格子名排在前面就跳过重推"。** 那等于承认 A 的旧副本是正本，B 的续写永远上不去。

## Consequences

- B 推完一轮之后，下一轮预演就是「远端已经有这一份」，不再重复上传；别的机器拉取时也会拿到续写过的
  那一份（而不是 A 那格的旧副本）。
- 判据只对"同代次、内容不同"成立：代次不同仍按超集判，字节相同/读不到仍按活动时间判，其余情形与
  原来一致。
- 文件被改写（不是追加）而字节数变少时这道判据会判错，但那种情形本就落在 `diverged` 上由用户裁决
  （以本机为准 / 以远端为准），不会静默丢内容。
