# Agent Note: WebDAV 同步是运输层，只增不覆盖

Status: implemented

## Problem

同一个项目在多台机器上往往装在不同目录（`/home/alice/dev/proj` 与 `/opt/work/proj`）。会话库却不能
直接同步：库里每一条的目录名由 `projectKey(cwd)` 决定，header 里的 `cwd` 又与目录名绑死（见
[迁移是三件事同时改](../architecture/2026-09-27-migration-rewrites-three-things.md)）。把 A 机的库
拷到 B 机，header 里写的还是 A 的路径——轻则 Ungrouped，重则 `corrupt session log`。

已有的导出 / 导入能跨实例（导入会把 `cwd` 改写成目标工作区），但它是一条**人工**流程：去界面挑会话、
下载、搬文件、在另一台机器上传、选目标、预演、确认。两台以上、每天都要做的时候，这件事本身就是负担。

## Decision

远端只当**运输层**：放的是 `.dshsess` 包与一份索引，落地一律复用导入那条编排（`planImport` /
`applyImport`），由它把 `cwd` 改写成这台机器的路径。

```
<url>/machines/<machineId>/index.json                这台机器贡献了哪些会话
<url>/machines/<machineId>/<encodeSegment(id).dshsess>  一条会话一个包
```

- **一机一格**：WebDAV 没有锁，多台机器共写一份 `index.json` 就是"后写的盖掉先写的"。每台机器只写
  自己那一格、读别人的全部（同一 id 由多台贡献时取**领先**的那份：代次是另一个的超集且共有代次内容
  一致；没有领先关系才按格子名排序取第一个，结果确定），于是不需要锁、也不需要"谁先谁后"的约定。
  只看格子名是不够的：一台机器把拉下来的会话继续写下去之后，它的格子里是更长的那份，而格子名恰好排
  在前面时别处拉到的会是旧的那份（缺最新代次，还看不出少）。
- **只增不覆盖**：库里已有同 id 的会话一律不拉。两边都有时按代次指纹判四种关系——内容一致（不动）、
  本机严格领先（共有代次逐条一致，说明远端那份确实是本机这份的前缀 → 重推刷新）、远端领先（不动，
  报告）、两边各自写过（不动，报告）。判据是"远端那份是不是本机这份的前缀"，不是时间戳：文件的
  修改时间经不起复制，而没有共同祖先的两条日志本来就分不出谁更新（与
  [导入只跳过，不覆盖](../architecture/2026-09-27-import-skips-never-overwrites.md) 同一条口径）。
  索引里存的指纹是**与 cwd 无关**的内容哈希（把 header 的 cwd 归一成占位符再算）：落地一定会改写
  别人的 cwd（库目录名与 header 的 `cwd` 绑死），按字节比就会把拉下来的那份判成"两边各自写过"——
  报告里的理由是错的，更要紧的是它在那台机器上**继续写之后也推不回去**，新代次永远留在本机。
  cwd 是"这份会话在这台机器上落在哪儿"，不是"这是哪份会话"。
- **显式映射表**：远端 `cwd` → 本机目录，配在插件配置里。没配映射的会话跳过并列出来，**不猜**。
- **密码只放引用**：`passwordRef` 是环境变量名，值由宿主 credentials 服务解析（缺席退到
  `process.env`）。配置备份、同步、截图都不会把密码带走。
- **两个入口共用一份编排**：`sync_sessions` 工具与 `GET|POST /sync` 都调 `src/sync.ts` 的 `runSync()`，
  默认只预演。
- **远端驱动只用四种方法**（PROPFIND / GET / PUT / MKCOL）加 Basic 鉴权，实现在 `src/dav.ts`，不引
  webdav 库：多一个运行期依赖就要跟着它的安全更新与 Node 版本走。

推的那一侧每次同步都会重写自己那格的索引，条目只描述"我这台机器现在还拿得出的会话"：本机删掉的
下一次推送就从索引里消失（远端那份包不主动删），别的机器已经取走的副本不受影响。

## Alternatives considered

**把 `sessionsRoot` 直接指到 davfs / rclone mount 上，多机共用一个库。** 除了 `projectKey(cwd)` 会按
机器路径分叉成两拨目录，宿主的写入还假设本机文件系统的原子 `rename`——网络盘上这条不成立。

**多机共写一份索引、或共用一个越来越大的包。** 无锁写就是丢更新；一个大包还会让"只拉一条"变成
"每次整包下载"，而 WebDAV 上真正贵的是往返。

**按工作区标题或 `git remote origin` 自动配对路径。** 标题重名、非 git 目录、同一个 remote 的多个
clone 都会错配，而错配的代价是把会话落到一个不是他要的目录里（还要连带改 header）。先做显式表，
缺映射时如实报告——这条留在报告里比留在猜测里便宜。

**同 id 覆盖或合并代次。** 覆盖可能用更旧的历史压掉更新的；合并两条没有共同祖先的日志会打架（事件
序号）。分叉的两份都保留，代价是同一条会话不会合流——这一条写进了 README、说明页的常见疑问与预演
输出。

**远端那份比本机旧时也覆盖它。** 那会丢掉远端已经续写、本机还缺的代次。只有"远端是本机这份的前缀"
（共有代次逐条一致）时才允许刷新。

**引一个 webdav 库。** 只用得上四种方法与一种鉴权，代码量在这里换得到（`src/dav.ts` 一个文件，含
一个宽容的多状态响应解析器）。

## Consequences

- 同步是**只增**的操作：它不会让两边已有的任何一条会话变差；代价是删不掉远端、同 id 不合流——两条
  边界在 README 的「同步」一节与说明页的常见疑问里都写明了。
- `machineId` 必须每台机器唯一（缺省主机名；两台同名机器会互相盖掉对方那一格）。
- 只支持 Basic 鉴权；Digest / OAuth 之类的服务器暂时用不了。
- 路径映射是配置项，不是自动发现：新增一台机器或换目录时要补一行映射，否则预演里那几条会一直
  "缺映射"。
- 验证：`test/dav.test.ts` 打一个真的 WebDAV 夹具（含 401、404、405 与畸形多状态响应），
  `test/sync.test.ts` 用两台假机器跑端到端（推、拉、空转、重推、坏包、缺包），工具层与端点各有一条
  钉住"预演只读、apply 才落地"和"没配置时如实拒"。
