# Agent Note: 会话包要把附件对象一起带走

Status: implemented

## Problem

日志里只有引用，没有字节：一条带图的会话在日志里写的是
`{"type":"image","attachment":{"attachmentId":"sha256:…","mediaType":…}}`，而那几个字节在宿主的**附件库**里
（`$DSH_HOME/attachments/v1/objects/<sha 前两位>/<sha>`，文件对象在 `file-objects/`）。包（导出与同步的
`.dshsess`）只带日志时，同一份会话到了另一台机器上，会话、标题、正文都在，**只有图片与文件是空的**——
界面上就是那句「图片加载失败，点击重试」。

实测的形状（一次性对上的两侧）：一个 `DSH_HOME` 与主库不同的实例里，导入的
`session-ca69a53a-…` 引用 3 个对象，新实例的 `attachments/` 下一个文件都没有；源库
`~/.dsh/attachments/v1/objects/` 里那 3 个对象都在，sha256 与日志里的 id 逐位一致。也就是说数据没坏，
只是**包没有把被引用的字节算进"这次要带走的东西"**。

## Decision

包的格式升到 v2：清单多一节 `attachments: [{ id, kind, name?, bytes, offset }]`（文件对象那份 `name`
决定它落回本机时的路径，见
[文件对象要带上它的名字](../bug-fix/2026-10-16-file-objects-need-their-name.md)），对象字节追加在载荷尾部（日志
之后），`id` 自带 sha256 所以条目不再单列摘要。**格式号照"这个包里到底多带了什么"定，不照"这份代码是哪
一版"定**：一个对象都没带成（没给端口、日志里没有引用、或者引用的对象本机就没有）就写 v1——清单里连
`attachments` 那一节都不出现，与升级前逐字节同形；真要带对象才升 v2，因为那时装旧版的宿主确实读不了。
两侧都读 v1 与 v2（`BUNDLE_MIN_FORMAT_VERSION = 1`），手上已经有的老包照旧导得进去，只是没有对象可带。

- **打哪些对象由日志决定**：逐行扫 `attachmentId`（先做整篇的字符串预筛，命中才逐行 `JSON.parse`），按
  `kind:id` 去重；同一个对象被多条会话引用只进一份。
- **对象从哪读、落到哪只走一个纯路径端口** `AttachmentPort.pathOf(ref)`（[`src/attachments.ts`](../../../../src/attachments.ts)）。
  核心层零 DSH 依赖，宿主半侧用 `ctx.attachments.imageHostPath()` / `fileHostPath()` 实现它、在
  `src/tools.ts` 里探测成端口注入。**宿主没有这个服务时端口缺席**：包只带日志、导入只写日志、索引里不记
  附件——与升级前逐字节一致，功能静默降级而不是报错。
- **先落对象，再写日志**：会话不会以"图是挂的"状态先出现在库里。落对象**非致命**（失败逐条回报在
  `attachmentProblems` 里），日志写不下去仍然抛错。
- **导入计划逐条给动作**：本机没有的对象 `create`、已有的 `present`、这个宿主落不了的 `unavailable`。
  `plan.ok` 在"只补对象、不建会话"时也是真——把同一个包再导一次就是那条修复路径（会话 `skip`、对象补上，
  日志一字节不动）；界面据此让确认按钮在这种情况下**可用**。
对象落地与宿主自己写对象的规格一致：先写 `<path>.part` 再 rename（内容寻址，覆盖安全），文件 `0o400`、
目录 `0o700`；已存在且大小相同就直接算 `present`，不重写。

## Alternatives considered

**只带引用，导入时回源机器再拉一次。** 需要源机器在线、需要另一套协议与凭据，而包本身已经是"离线可复原
的载体"——把这条保证分叉成两种，等于承认有的包不能独立使用。

**把图片 base64 塞进日志。** 改写日志就破坏了"导出的东西与磁盘上的东西是同一件事"（见
[容器那篇](../architecture/2026-09-27-dshsess-is-one-gzip-stream.md)），而且同一张图被多次引用会重复膨胀。

**每个对象单独一个文件 / 单独一个压缩包附件。** 包从一个变两个，下载、同步（远端一条会话一个包）、备份
三处都要成对搬运；容量上也没有好处（日志的 zstd 帧已是压缩态）。

**让宿主的附件服务自己打包。** 核心层零 DSH 依赖是本仓库的结构约束（`src/*.ts` 除三个壳文件外都不许
import 宿主包）；一个 `pathOf()` 纯函数端口就把这个能力借过来了，不必把编排搬进宿主。

## Consequences

- 实测（真实会话，只读原库、落地到临时 `DSH_HOME`）：`session-ca69a53a-…` 日志 1 103 652 字节，打出来的
  包 1 188 715 字节，多出的 95 346 字节正是那 3 个对象（64 425 / 16 542 / 14 379）；导入后 3 个对象都在、
  sha256 与日志里的 id 一致、权限 `0o400`；把同一个包再导一次，会话 0 条、对象 0 个（3 个都是 `present`）。
- 老包（v1）照旧能读能导；新写出来的包里，没对象的那些也照旧是 v1，所以"升到 v2"只发生在确实带了对象
  的包上——破坏面跟着内容走，而不是跟着版本号走。
- 这一笔只动了设置页的「导出 / 导入」（`src/web.ts` 的两个端点）。**同步（推送 / 拉取）那条路不把对象塞
  进包**：它按远端一份内容寻址的共享目录搬（包只带引用），见
  [同步的附件对象走远端一个共享目录](2026-10-16-sync-carries-attachment-objects.md)——同一份对象在两台机器
  之间只上传一次，也不必跟着每轮重推的包反复走。
- 界面要把这件事说出来，不能静默：导出报"带走了几个对象"与"有几个在本机库里找不到、这次带不走"；导入
  的计划表头上方报"包里有几个对象、其中几个本机没有"，落地后报"另写入几个"，落不了的那几个单独提醒。
- 附件的失败面与会话的失败面是分开的：对象落不了不影响会话导入（`ok: true` + `attachmentProblems`），
  否则一张图缺失会把整条会话挡在库外——那比"图挂了"更糟。
- 宿主没有附件服务（没挂 `dsh-attachment-local`）时一切照旧：`attachmentsOf` 只在有端口时注入，包与索引
  与升级前一致。
