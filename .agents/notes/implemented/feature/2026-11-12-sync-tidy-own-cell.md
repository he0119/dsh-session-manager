# Agent Note: 整理远端只清自己那一格

Status: implemented

## Problem

远端是一机一格。同一条会话常同时存在于两格里：A 推过一份，B 拉下来继续写、又推了自己那份。合并视图
只挑一份当正本（见 [同代次更长的那份赢](../bug-fix/2026-11-12-sync-merge-prefers-longer-cell.md)），另一份没人
再读，却一直占着 NAS。

本机实测：1417 条会话里，**1066 条的远端副本落在 `HMY-UM790PRO` 那一格、且与本机内容一致**——七成以上
的会话在远端有两份。按预演算出来的账：本机这一格里有 **933 个包是多余的，合计约 666 MB**（索引里记的
代次字节数），删一遍要几十秒。远端原来也没有任何删除入口。

## Decision

同步落地时多一个勾选框「顺手整理远端」，只在落地那次生效，只删**自己那一格**里多余的包：

- 另一格有一份**更全**的（代次超集，或同代次但更长——日志只追加，更长就是续写过的）→ 本机这份是被取代
  的旧副本，删；
- 另一格有一份**一模一样**的 → 只留格子名排序最靠前的那一格，名字靠后的机器各自删自己那一格；
- 两边各自写过（`diverged`）→ 不动，留给用户裁决。

判据必须两台机器算得出**同一个答案**（比较用码位排序，与 `machines` 列表同一套），否则 A 认为 B 更新、
B 认为 A 更新，互相删完远端一份都不剩。删包放在**索引写完之后**：中途失败最多留下几个没人引用的包，
不会留下指向空文件的条目；那些包下一次整理时按"没有索引条目"顺手清掉。预演只报数字（几个、多少
字节），真删的判据在落地那次按当时的远端索引重算。删的过程报进度（与推送同一套事件，段名 `tidy`，
一个包一条）：几百个包、几十秒，界面不该停在"推送"那一格不动。

## Alternatives considered

- **直接删别的机器那一格。** 对方下次推送会把自己那格的 `index.json` 整份重写，删掉的条目会复活；
  只删包不删条目更糟，别的机器拉取时撞 404。跨格写还正好绕开了"一机一格"要躲的那件事。
- **谁本地有就删谁的对家。** 两台机器各说各话（都认为自己是正本），差异被悄悄藏起来，比重复更糟。
- **定期对账脚本、不进界面。** 省事，但删远端的东西没有预演与确认，也没有"这一趟删了多少"的交代；
  而且机器交叉写会不断攒出新的重复，一次性的脚本管不住。
- **什么都不做。** 正确性没问题（合并规则保证取最好的那份），代价是远端长期一倍冗余，且没有手动入口。

## Consequences

- 指向「一条会话在远端只留一份」；多出来的空间按上面那 1066 条算约 0.8 GB（本机这一侧的能量到的数字）。
- 冗余从"两格互为备份"降为一份；内容不会丢——两台机器的本地库都还在，留下的那份万一没了，下次同步
  会从还有本地副本的机器重新推上去。
- 只删重复与被取代的：`diverged` 那几条不动，仍由用户在弹窗里裁决。
- 各清各的格，所以两台机器都要升到这个版本，远端才会真的降到一份。
