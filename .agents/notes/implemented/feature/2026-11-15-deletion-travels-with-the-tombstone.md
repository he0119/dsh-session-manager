# Agent Note: 删除跟着墓碑走，删掉的会话不再被同步带回来

Status: implemented

## Problem

删除只删本机。远端那一格里的包（`dsh-session-manager/<机器>/<id>.dshsess`）与它索引里的那条记录都
原地不动，于是**下一次同步把这条会话当"远端有、本机没有"重新拉回来**——删除等于没发生。用一台本地
WebDAV + 一条 352 字节的会话复现过：删完本机目录，再跑一次同步，`pull` 表里就是这一条
（`action: 'create'`、`code: 'missing'`），落地之后目录又回来了。整理远端那一步救不了它：`planTidy()`
只删"自己那一格里被另一份取代 / 重复"的包，不删"用户不要了"的会话。

同一件事在别的机器上也一样：A 删掉一条会话，B 的本机库里还留着旧的那份，B 下一次同步就把它重新推
上去，A 下一次同步又把它拉回来。要断掉这条回路，"删除"这件事本身得留下痕迹，而痕迹只能由删它的那台
机器写（WebDAV 没有锁，多台共写一份索引就是后写的盖掉先写的）。

## Decision

删除不再只是"删本机"这一件事，它变成"本机删掉 + 在自己那一份索引里留一条删除记录（墓碑）"：

- **墓碑的样子**：索引里可选的一串 `deleted: [{ id, at }]`（`at` 是删除时刻，毫秒）。没有删过任何
  会话的机器，索引形状与这一天之前逐字节相同；老宿主不认识这一项，读得进、写回时丢掉。格式见
  `docs/formats.md`。
- **删除时清远端**：`RemoveRequest.alsoRemote`（界面那枚「同时删除远端」，配了同步时默认勾上）。
  落地那一步在删完本机之后调 `src/sync.ts` 的 `removeRemoteCopies()`：删掉自己那一格里的包、把它从
  自己那份索引里摘掉、并把这次删的 id 写进 `deleted`。远端那份没有备份（它只是这台机器推上去的
  副本），所以这一步失败不拦本机删除，但会把后果写进问题清单：「删除记录没留下，下次同步可能把它们
  又拉回来」。
- **同步据此三分**（`tombstonesOf()` 把各机器索引里的墓碑合成一份，同一个 id 取最晚那次）：
  - 远端那份比墓碑旧（或索引里没有活动时间）→ **不拉**，计划里给一条 `code: 'deleted'` 的跳过行，
    说清"已在某台机器上删除"；这份包等它那台机器下次同步时自己清掉。
  - 本机那份比墓碑旧 → **跟着删**：进 `plan.deleted`（界面多一张「跟着删」的表），落地时先备份
    （与删除那条路同一个备份根、同一种 `kind: delete`），再删本机目录与自己那一格里的包。不删的话它
    会在下一次推送里被重新推上去。
  - 本机那份比墓碑新 → **留着**，照常参与比对与推送（"谁更新谁赢"）；自己那份索引里的这条墓碑同时
    作废（下一次同步不会再拿它去删别人那份）。
- **墓碑只在"这条又回来了"时才摘掉**：本机又有了它（拉回来、或本机那份更新所以留着）就摘；否则一直
  留着。会话 id 是随机 uuid、不会重复使用，所以"留着的墓碑会不会误删以后一条新会话"不是问题。
- **只推不拉那条路不删**：后台自动推送（`pushOnly`）计划里的 `deleted` 一律清空——跟着删一条会话要
  先进备份再删目录，那是"用户按下同步、看过计划"才该发生的事。
- **同步计划里那张「跟着删」的表**排在「推送」与「这次不动」之间：它是**要动手**的事。结论那句也跟着
  变成"会拉取 X 条、会推送 Y 条、会跟着删 Z 条"；落地之后那句提示补"另跟着删掉 Z 条（旧的那份已进
  备份）"。

## Alternatives considered

- **删除时把别的机器格子里的包与索引条目一起删掉**：能立刻让远端干净，但要么留"索引条目指向空气"
  （别的机器下次拉取撞 404），要么就得改别的机器那份 `index.json` —— WebDAV 没有锁，它同时也在推，
  后写的会盖掉先写的。既有边界是"每台机器只写自己那一格"，这条不破。
- **不留墓碑，只删包**：自己那一格的包没了，别的机器那一格还在，下一次同步照样拉回来；而且那台机器
  一推送，"远端有、本机没有"的判定照样成立。墓碑是唯一能表达"这条被删了"的东西。
- **墓碑另放一份共享文件（比如 `dsh-session-manager/deleted.json`）**：又回到多台共写一份的老问题；
  而且它一旦被写坏，坏的是所有人的删除记录。
- **墓碑带过期时间（比如 30 天后自动忘掉）**：一台睡了半年的机器醒来时，它的旧副本就不受约束了，
  会原样推回来。宁可留一行字（一条会话一行，`{id, at}` 几十字节）。
- **给"跟着删"单独一道确认**：同步那一步本来就要求用户看过计划再按「确认同步」，计划里那张表就是
  那道确认；再加一层只会让人闭着眼继续按。
- **`alsoRemote` 默认关**：等于把"删除会复活"当默认行为。默认勾上，勾选框旁边那句说明写清代价
  （远端没有备份、别的机器上的副本会在它们下次同步时删）。

## Consequences

- 删除弹窗多一枚勾选（配了同步才出现，默认勾上）：删除这件事从"删本机"变成"删本机 + 清自己那格"，
  用户在按下之前就知道远端那份没有备份。
- 同步弹窗多一张表（最多四张）；只有真的"别处删过、本机更旧"时才出现。
- 墓碑会一直留在删它的那台机器的索引里（一条会话一行），直到那条会话又回到这台机器上。它会跟着每次
  索引重写一起写回去（`indexPayload()` 的第三个参数）。
- **时钟差会漏判**：判据是"本机这份的最后活动时间 vs 墓碑时刻"。删它的机器时钟若明显偏慢，别的机器
  上那份就可能被判成"更新"而留下来；反过来偏快会把一份其实更新的副本删掉。备份兜住后一种。
- **老版本会丢墓碑**：老宿主重写自己那份索引时不认识 `deleted`，写回就丢了；随后它的旧副本会复活。
  要依赖"删了就各处都删"，得先让每台机器都升到认识这一项的版本（见 `docs/formats.md`）。
- 别的机器的副本不会在删除那一刻消失：它要等那台机器下一次同步（在那之前它留在远端，但谁也不会再拉
  它）。这是"只写自己那一格"的代价，也是它安全的原因。
- 删除的复核（`verified`）只判本机：远端那一步失败进问题清单，但不把"本机删干净了"说成失败。
