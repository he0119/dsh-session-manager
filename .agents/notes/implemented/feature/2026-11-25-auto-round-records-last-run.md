# Agent Note: 后台跑完那一轮也写「上次同步」

Status: implemented

## Problem

「上次同步」那条记录原来只有**手动**那一趟写（界面按「确认同步」，或模型工具 `sync_sessions`）。页头那枚
按钮上的字是「同步 · 3 小时前」，读的就是它。自动那一档（只推 / 双向）可以开着之后，机器每写完一轮就
自己跑一趟，干的明明是同步的活儿，却一个字节都不记：一台连着用了两天的机器上，界面写着「2 天前」，
而同一时刻远端那一格的 `index.json` 是 20 分钟前刚重写的、后台那一轮推了 2.9 MB。

更要紧的是那条记录旁边的绿点说的是「自动开着」（见
[页头那枚同步状态点哪一档颜色](../architecture/2026-11-13-sync-chip-dot-colors.md)）。绿点加「2 天前」，
读起来就是「后台这两天没跑过」——功能明明在用，界面却在报停。

## Decision

后台那一轮跑完也写同一条记录：`autoPushRunRecord()`（[auto-push.ts](../../../../src/operations/sync/auto-push.ts)）
把一轮的结论折成 `SyncRunRecord`，由 `resolveAutoPushRuntime()` 的 `run` 包装在每轮结束时调用写入口，
写入口由入口（[index.ts](../../../../src/index.ts)）注入——那一层不认识 Cordis，也不解析 `$DSH_HOME`。

四条判据：

- **搬了东西的那轮写**：`pushed` / `pulled` 条数、`problems`、`leftovers`、`takesEffect`，与手动那趟同一套
  字段。`ok` 是 `true`，哪怕有几条没做到——那几条走 `problems`，页头那枚点按遗留变黄，不按 `ok` 变红。
- **空跑（`idle`）那轮不写**：它只是「看了一眼」，一条都没搬。写进去会把上一趟真搬了东西的时刻盖掉，
  「上次同步」那行的读数从此永远是「刚刚 · 拉取 0 条、推送 0 条」。
- **没跑成的那轮写**（`ok: false` 加原因）：后台无人在场，页头那枚点只有靠这条记录才红得起来。
- **没发生的（没开自动、上一轮还在跑）什么都不留**：那两种情况下这一轮压根没跑。

记录里多一列 `source`（`manual` / `auto-push` / `auto-sync`）。理由是那句「拉取几条」：只推那一档
从不往下拉，写成「拉取 0 条」会被读成「拉了、一条都没拉到」。界面按它挑句子；旧记录没有这一项，
按手动那趟画（那时确实只有手动那趟会写）。

`takesEffect` 两档分开算：只推那一档一个字节都不动本机，「要不要重启」对它不成立，写死 `immediate`；
双向那档按 `effectOf(outcome.effect, 宿主的探测)` 说话，与 `/auto-push` 端点同一个判据。

## Alternatives considered

- **每轮都写，空跑也写**：时间戳会一直很新，但那行的读数永远停在 0/0，把「上次真的同步了什么」埋掉；
  而且活动期间每 5 分钟重写一次存储，没有信息增量。
- **只让双向那一档写**：只推开着的人看到的还是「几天前」，问题原样在。
- **不记 `source`，界面按当前配置那档说话**：配置是活引用，随时可能刚改过，记录里那趟可能是改之前的
  档；而且分不出「手动」与「后台」，两种说法本来不一样。
- **把记录拆成两份（上次手动 / 上次自动）**：两行几乎一样的时间戳，读的人要自己比，多一份要同步的状态。
- **界面直接读调度器内存里那一轮的结论、不写入磁盘**：进程一重启就没了，而这条记录存在的全部意义就是
  「关掉窗口、重启之后还答得出昨晚那趟成没成」。

## Consequences

- 存储在那几轮真搬了东西时各重写一次（几十字节）；空跑不写，所以不会在活动期每 5 分钟刷一遍。
- 记录多一列 `source`；旧记录读回来没有它，界面按手动那趟画。表 schema 对它是宽容的（只核「是个字符串」），
  以后多一条写入口时这一版读得回来。
- 页头那枚绿点的语义没变（仍是「自动开着」），但按钮上的「多久以前」现在通常很新——两个信号不再互相打架。
- 后台那一轮失败（连不上远端之类）现在会让页头那枚点变红；此前只有手动那趟失败才会。
- 后台那轮与手动那趟共用同一条记录，谁后跑完谁写。两趟不会同时写：写远端那把闸是同一把，先后串着。
