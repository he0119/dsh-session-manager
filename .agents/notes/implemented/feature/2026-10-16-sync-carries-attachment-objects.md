# Agent Note: 同步的附件对象走远端一个共享目录

Status: implemented

## Problem

日志里只有引用、字节在宿主的附件库；导出 / 导入那条路已经把它们打进包里了（见
[会话包要把附件对象一起带走](2026-10-13-bundles-carry-attachment-objects.md)），**同步那条路还没有**：
它照旧一条会话一个 `.dshsess` 包，包里只有日志。后果有两个，第二个才是真正难办的：

1. 新会话推到另一台机器上，会话、标题、正文都在，**图片与文件是空的**。
2. **已经同步过的那些会话再也修不回来**：同步的计划按**日志**的指纹判"两边一样"，判成一样的那些既不推
   也不拉。于是旧版本推上去的会话（远端只有日志）、旧版本拉下来的会话（本机只有日志）在升级之后仍然
   谁都修不动——计划里它们永远是"不动"。

数量的形状（一次只读、对整库量的）：90 条会话带附件，665 处引用 / 643 个唯一对象；对象合计 59.8 MB，
日志合计 210.9 MB（对象约占 22%）。其中只有 22 个对象被多于一条会话引用，跨会话去重只省得下 1.6 MB——
**所以"共享一份、两边各自引用"省的不是容量，而是重复上传**：同步是"一条会话一个包"，自动推送每写完
一轮就把那个包整个重推一次，对象塞进包里就是让那些一辈子不变的字节反复走一趟网。

## Decision

附件对象放远端一个**共享**的内容寻址目录，与机器格同级：

```
dsh-session-manager/<machineId>/<sessionId>.dshsess      每条会话一个包，包里只有日志（照旧 v1）
dsh-session-manager/attachments/objects/<sha 前两位>/<sha>      图片对象
dsh-session-manager/attachments/file-objects/<sha 前两位>/<sha> 文件对象
```

- **包本身不带对象**（照旧 v1、清单里连 `attachments` 那一节都没有）：对象是内容寻址、写完不改的，而包
  是"每写完一轮重推一次"的。格式号照"包里多带了什么"定这条规则不变，同步这条路正好是"一个都不带"。
- **推送**：扫这条会话日志里的引用（与导出同一套扫描），按前缀 `list()` 一次问清远端这一层有哪些
  （一次同步里每个前缀只列一次，两个方向共用这份缓存），只 `PUT` 远端没有的。远端已有的连着两次推送
  一个字节都不传。
- **拉取**：引用从**包里的日志字节**读（本机那份这会儿还不存在或正要被换掉），先落对象再写日志——与导入
  同一条不变式。本机已有的对象一个字节都不取，所以两台机器共用的那张图只传一次。
- **补对象**：日志两边一样、对象却没对齐的那些会话单独走一趟（两个方向都做）。本机缺的就取回来，远端缺
  的就传上去。**「远端也没有」整轮汇总成一句**（`absentObjects` 一个去重集合，收尾时报数量）——拉取那条路
  与补对象那条路撞上的是同一种状态，处置也是同一件事；一个会话引用几十张图时，逐条报会把问题清单淹掉。**只在手动同步时做**：它要把本机带引用
  的日志都解开扫一遍，是整库尺度的开销——值得花在用户点「同步」这一次上，不值得每写完一轮就花一次（后台
  那条只推不拉的路因此不跑它）。往远端传的那一侧只认"远端索引里认得的会话"：远端压根不认得的（比如空白
  会话）不替它占空间。
- **远端目录名 `attachments` 是保留的**：列机器格时跳过它（读远端那一份索引时，与「测试连接」的探针
  里各一条同源的过滤），否则远端会多出一台叫 `attachments` 的"机器"——探针漏掉那条会让设置页念出
  "机器：robot-a、attachments"。
  机器标识算出来正好叫这个名字时（`reservedMachineIdProblem()`）同步计划直接报一句，而不是让那台机器的
  格子静默地对所有别的机器不可见。换不出一个"不可能撞上"的保留名：机器格名是 `encodeSegment()` 的结果，
  字母数字加 `._-~`，任何合法段名都可能被某个标识算出来。
- **宿主没有附件服务时整块不参与**：包、索引、同步结果与升级前逐字节一致（`SyncOutcome.attachmentIn/Out`
  两项缺席，不是零）。界面据此一个字都不说。

界面与工具把这件事说出来：同步横幅与自动推送那句在真搬了对象时补一句「另取回附件对象 N 个（X）」/
「另上传附件对象 N 个（X）」，工具结果多 `attachmentsIn` / `attachmentsOut` / `attachmentsMissing` 三个数。

## Alternatives considered

**把对象也塞进同步的包里**（导出那条路的 v2 做法）。每台机器各自带一份、每轮重推时整包重传，正是这条路
最花钱的地方；跨机器去重也一起没了。导出那条路不同：那是一次性的、用户手里的文件，包必须能独立复原。

**对象放每台机器自己的格子里**（`<machineId>/objects/…`）。同一张图两台机器各存一份，跨机器去重没了；
"共享库"这个形状本来就是为了这个。

**远端索引里记下每条会话引用了哪些对象**。好处是计划阶段就能报出对象数、补的时候不必列目录；代价是索引
体积与每次同步的读取量跟着对象数涨（整库 643 个对象、平均每条会话 7 个），而索引是每次同步都要整个读回
来的那一份。这一笔先用"按前缀列目录"：一层目录最多 256 个桶，一次同步里每个桶只列一次，数报在落地结果里
而不是计划里。

**逐个对象 `HEAD` 一下问存在性。** WebDAV 对 `HEAD` 没有普遍保证（不少实现直接 405），列一层桶更省请求，
而且一次就把那一层全部对象名给回来了。

**把"补对象"做成计划里的一类条目**（"只补对象、不动日志"）。计划与界面要多一整套动作与原因文案，而它在
落地时扫一遍是等价的：用户看到的是"另取回 N 个对象"，不是"有一条会话要被处理"。日志一个字节都不动这件事
也因此更好说清。代价是计划为空时确认框只说"两边一样，没有要同步的"，而确认之后其实还会补对象——这一句
由界面补上（`sync.nothingAttachments`，说不说取决于 `/meta` 的 `attachments` 能力位：宿主没有附件库
服务时不许诺这件事）。

**远端删除 / 垃圾回收**（没人引用的对象删掉）。`DavPort` 现在没有 `DELETE`，而且"没人引用"只有全库视角才
判得出来——远端看不到别人的库，谁都不敢删。远端包本来也是只增不删的，这一笔不引入新的回收语义。

## Consequences

- 真机端到端（真 WebDAV + 两个真宿主，会话是 1 103 652 字节那条真日志、8 个真对象）：
  - A 推送新会话：`pushed` 1 条、`attachmentOut { uploaded: 8, bytes: 1 083 599 }`，包 386 147 字节、
    `formatVersion 1`、清单里没有 `attachments` 那一节；共享库里 8 个对象。
  - 同一个远端再同步一次：`uploaded: 0, skipped: 8`，`find -newermt` 一个对象文件都没被写过。
  - B 拉取：`pulled` 1 条（落地 386 781 字节）、`attachmentIn { written: 8, bytes: 1 083 599 }`，8 个对象
    权限 `0o400`、宿主真读回 8/8（含请求变体），落地的日志与 A 的那份 sha256 相同。
  - **修复路径**：把 B 的附件库整个删掉、会话留着（"早先拉坏了"的样子）再同步——计划里 `pulled` /
    `pushed` 都是空，`attachmentIn { written: 8, bytes: 1 083 599 }`，宿主读回 8/8，日志里没有
    `ATTACHMENT_NOT_FOUND`。
- 装旧版（0.5.0）的那台机器读到新的远端布局时，只会在"远端机器"里多列一个 `attachments`（它那一格没有
  `index.json`，按"这台机器还没推过内容"跳过，不报问题）。**不构成破坏性变更**：包的格式没动，旧版照旧
  读写自己的包，只是不搬对象。
- 机器标识是 `attachments` 时同步不工作（计划里明说一句）——这台机器的格子会被所有别的机器跳过。
- 远端共享库只增不删：`DavPort` 没有 `DELETE`，这一笔也没引入回收语义（与远端包一样）。
- 一次同步里每个前缀目录最多列一次；整库 643 个对象最多 256 次 `PROPFIND`，实测这一笔的 8 个对象落在
  8 个桶里、一次同步 8 次。
