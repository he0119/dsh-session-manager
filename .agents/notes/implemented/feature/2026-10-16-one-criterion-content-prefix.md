# Agent Note: 同步判谁领先只看内容前缀，代次与哈希只是快筛

Status: implemented

## Problem

同一对会话在两处有两个结论：差异页读内容，说「只是续写」（远端那份是本机的前缀）；同步计划比代次
集合与哈希，说「同一个 id 两边各自写过」，把这一对放进"比谁更新"的时间桶。计划那句文案还拿
"两边各自写过"当桶名，于是"只有一边写了"的对看起来像两边都有动作，要么白白等时间分高下，要么
逼用户去裁决一件本不需要裁决的事。判据不统一，两处就不可能说同一件事。

## Decision

判据只留一条：**谁是谁的前缀**。代次与哈希降级成快筛——能确定就直接下结论（同哈希 = 同一份、
共有代次逐条一致且代次领先 = 领先），筛不动的对取两边日志做前缀判定，用的就是差异页那套
`session-diff.ts` 的关系（`same` / `local-extends` / `remote-extends` / `forked`），不写第二份判据。

`planSync()` 保持纯计算（不碰网络）：输入多一个 `contentRelations`（会话 id → 内容关系 + 两边尾巴
条数），筛不动的对由编排那条异步路算好传进来。归类跟着判据走：`local-extends` ⇒ `local-ahead`
（自动推送）、`remote-extends` ⇒ `remote-ahead`（自动拉取）、`forked` ⇒ 时间/裁决那一桶（裁决照旧
适用）。同一条会话在差异页与计划里因此是同一个结论。

代价只花在筛不动的那些对上：`prepareSync()` 先算一遍计划拿到 `needsContent` 名单，逐对取远端的包
与本机日志判关系，再带内容关系算第二遍（指纹有缓存，第二遍不重读内容）。取不到的一对退回"筛不动"，
那一对照旧两条都不动——下限是不丢内容。

计划说明按结论说话：续写写「本机续写了 N 条」/「远端续写了 N 条」，真分叉写「各自写了对方没有的
条目（本机多 N 条、对方多 M 条）」。差异页的 header 段给 `cwd` 挂「预期内」标签（它按机器映射换算，
本来就会差）；id / createdAt / parentSession 真不一样才值得看。

## Alternatives considered

- **让差异页的结论反写回计划**：用户点开差异之后才修正归类，没点开的那些对照旧错着；判据还是两份。
- **只改文案不改判据**：话说得再准，桶还是分错的——该自动推的还躺在时间桶里等裁决。
- **计划里每对都取包做前缀判定**：判据统一但代价随库规模走（整库 936 条日志），而快筛已经能定掉
  绝大多数对；只给筛不动的那些付这份钱，实测是几十对、单条日志几十 KB 量级。
- **把前缀判据也写一份到 `sync.ts`**：两份判据迟早再次分叉（这次要修的正是这个），所以直接用
  `session-diff.ts` 的关系。

## Consequences

- `relation()` 的三处 `diverged` 出口都改问内容关系；`SyncPlan` 多一个 `needsContent` 名单（单列
  一项是因为 `pushOnly` 那条路会把分叉行整表摘掉，而"这一对需要判"与"这一次动不动它"是两件事）。
- 同步多一段进度「判内容关系」（`ProgressPhase` 加 `relate`），分母是筛不动的对数。
- 计划算两遍（纯计算 + 指纹缓存），第二遍不重读内容。
- 该自动走的对不再出现在裁决面前：用户要挑正本的只剩真分叉。
