# Agent Note: 两边各自写过时挑一份当正本，另一份落成新会话

Status: implemented

## Problem

同一个会话 id 在两边各自写过之后，同步只有一个结论：`diverged`，两条都不动。差异页已经能把两份
内容摆出来给人看，但看完没有下一步——要么放弃一份（丢内容），要么永远让那一对卡在"不动"里。库
里实测有 97 对这样的会话。

## Decision

裁决进同步计划：`SyncPlanInput.decisions`（会话 id → `keep-local` / `keep-remote`）给出每对
分叉的正本。计划行上落成两个新结论码 `keep-local` / `keep-remote`，替代原来那条 `diverged`。

**落选那份不删**：落地时先把它落成一条**新会话**（新 id `session-<uuid>`，标题带「原标题 · 来自
<机器> <时刻>」的来源标记），再让正本占住原来的 id。顺序反过来就会先把落选那份覆盖掉，那正是
"另一份不丢"要防的事。落成新会话走导入那条路（`planImport`/`applyImport` 新增的 `rename`），
所以包自校验、改写 header 的 cwd、附件对象与注册表都与导入同一条不变式。

标记标题由 `branchSessionLog()` 落进日志：只重写首帧的 header（换 `id`，首帧重编码成 raw-block
帧），并**改最后一条 `session/title` 的 `data.title`**，其余帧原样拼接、尾部与原文逐字节一致。不能
在最后一条标题之后插一帧新标题：v4 的每个事件 `seq` 必须等于它在正文里的位置（宿主
`event.seq !== index` 即拒绝），插在中间会让标记的 `seq` 大于后面那些事件，整份日志被读成
"complete frame contains a torn JSONL record"。改最后一条标题只动 `data.title`，`seq` 与位置都不变，
原标题文字仍作为前缀保留（「原标题 · 来自 <机器> <时刻>」）。没有标题时标记追加到末尾——末尾之
后没有事件，`seq` 仍连续；小日志读得到，大日志本来也没有标题可读。多代次日志只有最新一代带标记
（读标题只读最新一代），其余代次只换 id。

## Alternatives considered

- **在最后一条标题之后插一帧新标题**：看似只加一行，但会让标记的 `seq` 与位置错开，宿主按 v4 的
  连续 `seq` 拒绝整份日志；这是实际踩到的坑。
- **删掉原标题、把标记写成唯一标题**：会丢原标题文字；现在只改最后一条标题的 `data.title`，前面
  的标题与正文都不动。
- **把标记无条件追加到日志末尾**：大日志上两条读标题的路都只扫开头，标记会被读不到，表现成"落成
  的新会话连个名字都没有"；没有标题时才退回末尾。
- **给落选那份保留原 id，让正本换新 id**：反了——用户挑的是"哪份当正本"，正本要占住原 id 才谈得上
  收敛；再说标记标题的语义就是"这是另一条"，与新 id 一致。
- **删掉落选那份**：最省事，但丢内容，与"另一份不丢"直接冲突。
- **只把两枚按钮置灰**：禁用态只说"现在不能点"，说不出为什么，也仍占着主操作位；现在整段换成原因
  与出路。
- **先让人选，落地再报「正开着」**：把一次必然失败的选择拖到最后一步，用户已经点过确认才知道白做。

## Consequences

- 同步计划多两个结论码，界面在差异页给两枚「以本机这份为准」「以远端这份为准」，说明里写明另一份
  会落成新会话；选中后带着这组 `decisions` 重新预演，确认那次复用重算出来的计划（同一组选择才复用）。
- 裁决只在手动同步这条路上生效：自动推送（`pushOnly`）按原口径把它们摘掉——无人在场时既不该覆盖
  本机，也不该悄悄替用户落新会话。
- 活会话（宿主手里还有写句柄）不只是后台拦下：计划里先把「活动中」那几条点出来，差异页也不再给
  两枚按钮，只说明先切到别的会话或重启宿主。落地那一步同样会拒，给按钮只会让人以为选了就能同步；
  没映射、映射指到的目录不存在这两类仍是行上的原因。
- 落成的新会话标题里带来源机器与时刻，同 id 多次分叉落出来的几条靠这半句区分。
