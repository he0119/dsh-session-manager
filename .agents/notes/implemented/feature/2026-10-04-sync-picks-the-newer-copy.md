# Agent Note: 同步在两边都有同一个 id 时择新，空白会话不搬

Status: implemented

## Problem

同一个远端被两台以上机器用时，同一个 id 会在两边各有内容，而旧口径对这两件事都没有出路：

- **空白会话**（建出来但一轮都没开始过）没有正文，却和别的会话一样被推送：占一格索引、占一个包，
  别的机器拉取到的只剩一条空壳，还得自己收拾。
- **同一个 id 在两边各自续写过**（A 推送、B 拉取，然后两台各自继续写）时，旧口径是"库里已有同 id
  的会话一律不拉取"。两边都不动，谁也拿不到对方那一半内容，报告里只有一句「两边各自写过」——用户
  没有下一步可做，只能自己删了再拉、或者手工搬。

## Decision

`planSync()`（[src/sync.ts](../../../../src/sync.ts)）的决定表按两条规则重排，判据都来自宿主投影缓存
（[src/projection-cache.ts](../../../../src/projection-cache.ts) 多读 `sessionListMetadata.blank`、
`sessionListMetadata.lastPromptAt` 与 `timeContext.lastMessageTime`）：

- **空白不搬**。`sessionListMetadata.blank` 说它是空白时：
  - 本机空白：不上传，也不进「远端已经有这一份」那类行；推送的那一段还会把它从**自己那一格**的索引里
    撤下来（远端那份包不主动删）。别的机器因此不再看得到它——与本机删掉的会话同一条口径。
  - 本机空白而远端那条有内容：以远端为准，走下面的覆盖那条路（空的那份没什么可保护的）。
- **两边都有同一个 id 时择新**。判据是宿主从日志内容里折出来的**最后活动时间**——宿主给了两枚钟
  （`lastPromptAt` 最后一次提问、`lastMessageTime` 最后一条消息，agent 自己写进去的也算），取**晚的
  那枚**；推送时把它记进自己那一格的索引（索引格式版本 3，字段 `lastActiveAt`）：
  - 内容逐代一致（cwd 之外）：不动。
  - 本机确实是远端那份的前缀：重推刷新远端（原有行为）。
  - 远端确实是本机这份的前缀（remote-ahead）：以远端为准 → 覆盖。
  - 两边各自写过（分叉）：比最后活动时间，晚的那份赢；一样新、或有一边读不到时间 → 两条都不动并
    说明原因（退回旧口径，**不猜**）。

  两枚钟里必须有细的那枚，理由是实测出来的：只比"最后一次提问"时，"推送之后本机又跑了几轮、两边的
  日志各自长出来"这种情况两边的时间往往**一模一样**（提问时间在下一次提问之前不动），而它正是最该分高
  下的场合——日志被重写（压缩续写）之后，先前推送过的那份就与现在这份"各自写过"了。

远端那份赢时的落地：**先备份本机那份、再换成它**。备份种类多一个 `replace`
（[src/journal.ts](../../../../src/journal.ts)），语义是"把备份里那份搬回原位"（与 `delete` 那份
一样），但回滚时**连注册表一起还原**（与 `migrate` 一样）——覆盖会把这条会话搬进它自己的 cwd、并
reHome 它在注册表里的登记，只搬目录会让登记停在被覆盖之后的位置。

落地目录仍是**本机这条自己的 `cwd`**：它在本机已经有家（还有工作区登记），不该因为远端记着另一条
路径就把它搬走；本机这条没有 `cwd` 时才按"显式映射 → 仓库身份"认，与新建拉取同一条路。

安全顺序：取包并校验 → 备份 → 删旧目录 → 导入。任何一步失败本机原样不动；宿主内存里活着的会话一律
拒绝（与删除同一条理由：宿主手里有它的内存副本与写句柄，
见 [删除先备份，注册表不动](../architecture/2026-09-28-delete-backs-up-and-spares-the-registry.md)）。

输了的那台机器下一次同步自然收敛：远端那份在它眼里是"远端更新"，它换过去之后把自己那一格里那条已经
过时的记录撤掉（只撤自己的格子，别人的不动）。

## Alternatives considered

**让用户逐条选哪边赢（计划表里给一个选择器）。** 要新增一份"选择"的持久化、一条新端点，而且两台机器
都会各自看到同一个分叉、都要各选一次——两边选得不一样时还得再来一轮。自动按时间择新、并且**旧的进
备份**（随时可恢复）已经覆盖了"我不同意"这一档。

**按文件 mtime 比"谁更新"。** 经不起复制：`cp -r`、备份恢复、同步落地都会把 mtime 改成那一刻，会把
用户刚拉取到、其实更旧的那份判成"更新"。

**只比"最后一次提问"这一枚钟。** 实现过一版，在真实库上立刻暴露：本机这份被日志重写（压缩续写）过、
远端那份是重写之前推送的，两边内容各自长出来，而提问时间两边一模一样（同一个 id、同一条会话），
于是判不出高下——正好落回这条规则要解决的那个局面。`timeContext.lastMessageTime` 把 agent 自己写进去
的那些也算进去，补的就是这一段。

**按事件序号（`turnBoundary.lastStepStartSeq`）比"谁更新"。** 序号是每台机器自己的日志位置：跨机器时
它只说明"我这边写到第几帧"，两边各自续写时分不出先后，还会被编译进去的种子帧算乱。

**按 `createdAt` 或代次数比。** `createdAt` 是会话诞生的时间，两边一模一样；代次数多的一边也可能只是
多了一次空转（空代次在真实库里就有）。

**把空白会话照旧推送，只在界面里标一下。** 白占一格索引与一个包，别的机器还要人工收拾；而"空白"
这件事只有那台机器知道，标在远端没有意义。

**空白的判定退回"日志里没有事件"这条启发式。** 只写 header、或只有 seed 事件的会话会被判错（真实库里
就有 seed-only 的会话）；宿主投影缓存是权威来源，拿不到就不判（宁可按"会显示"处理）。

**覆盖前不备份，反正远端还有一份。** 本机那份可能正是用户还要的（比如它多出的那一代）；远端那份在
别的机器手上，回滚本机时不一定够用。

**覆盖时连注册表也换成远端那份。** 注册表是这台机器的（工作区标题、归档、置顶都可能与另一台不同），
覆盖只该改会话内容与它的 cwd 归属。

**同一台机器的两格之间合并代次。** 两条没有共同祖先的日志没有可靠的合并口径（事件序号会打架），这条
在 [WebDAV 同步是运输层](2026-10-01-webdav-sync-is-a-transport.md) 里已经否决过一次。

## Consequences

- **索引格式版本 1 → 2 → 3**：2 起每条多一个可选 `lastPromptAt`（最后一次提问），3 起写的是
  `lastActiveAt`（两枚钟里晚的那枚）。读的一侧三种都收：版本 1 的老索引照旧能用，只有 `lastPromptAt`
  的版本 2 拿它当活动时间（丢掉它等于让已经推送过的那些格子白瞎），缺这一项的那些条目只是判不出谁
  更新。解析不校验版本号，所以不必同时升级所有机器；老版本插件读到新索引也照常工作（它不认识这两个
  字段）。本机这条与远端**完全一致**时，下一次推送会顺手把它那枚钟补成 / 升级成当前的 `lastActiveAt`
  ——只补这一种，其余条目的指纹可能已经不描述本机现状，给它们改时间就成了撒谎。
- 同步从"只往库里加"变成**也会改本机已有的会话**：代价由"先备份再换"承接。备份清单里多一种
  `replace`，显示「覆盖前」，动作是「恢复」（搬回目录、注册表照旧——与删除那份同一套）。
- 一台机器上一次同步里，一条会话最多被换一次（换完就是远端那份，下一次判"一致"）。
- 「最后活动时间」在现实里会缺：老索引、宿主没挂投影缓存、这条在缓存里没有记录、或两枚钟都读不到。
  这时退回旧口径（两条都不动 + 说明），不猜。
- 两枚钟都是**写日志那台机器的本地时间**：跨机器比时带一点时钟偏差的风险（与前一版只比提问时间同一
  个风险等级）。同一台机器上自己与自己比没有这个问题。
- 验证：`test/sync.test.ts` 的计划层多两条（含空白、时间里三种"判不出来"、两枚钟各自分高下、以及版本
  2 那枚钟照旧认），端到端多三条（远端领先时的覆盖 + 备份 + 旧记录撤下、空白不上传且从索引撤下、两台各
  自续写最后收敛到同一份），另有一条钉"推送那一刻记的是晚的那枚钟"；`test/migrate.test.ts` 有一条钉
  `replace` 回滚的两种语义，`test/visibility.test.ts` 有一条钉两枚钟的读法（含只有细的那枚、形状不对
  两种），`test/tools.test.ts` 有一条钉工具侧接线。全套从 `tests 363 / pass 361 / fail 0 / skipped 2`
  变成 `tests 373 / pass 371 / fail 0 / skipped 2`。
