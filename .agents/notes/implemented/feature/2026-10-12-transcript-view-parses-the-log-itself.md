# Agent Note: 会话内容视图——在插件里把日志解析出来，而不是去问宿主

Status: implemented

## Problem

会话页能列出整库（包括侧边栏看不见的那些），能归档、导出、删除、重算标题，却**看不到一条会话里到底
写了什么**。这在两种场合直接卡住人：

- **排查**：这条会话为什么没有标题？为什么宿主说它是空的？它最后一次主模型请求用了哪个 route？
  这些答案都在日志里，而日志是几十 MB 的 zstd 多帧 JSONL，只有写脚本才读得动。
- **历史会话**：从别的工具导进来的、被归档的、父目录搬走过的那些，侧边栏根本不给入口，宿主自带的
  聊天视图也就打不开它们。

宿主的聊天视图当然能显示一条活会话——但它要先把会话**挂进宿主内存**，而且只认它自己列表里的那些。
本插件已经有一条**零 DSH 依赖**的读日志路径（标题扫描用的 `decodeAll` 端口 + `src/discovery.ts`），
所以"看内容"这件事没有理由绕开它去求宿主。

## Decision

**核心层加 `src/transcript.ts`：行 → 完整时间线，纯字符串/JSON，宿主与浏览器两侧共用。**

- 输入是**行**（第一行 header），输出是一页条目 + 整份日志的计数 + 分页游标 + 读不出来的行。
- **一条事件 = 一条条目**，不按内容块拆：`seq` 是宿主的游标，而分页游标要用"第几条事件"（日志里的
  `seq` 会跳号，实测有 4 → 6 这种，拿它当游标会漏条）。助手消息的正文与思考因此在同一条里分两格。
- **工具调用只算一次**：`assistant/message` 的 content 里也带着 tool-call 块，但日志另有独立的
  `tool/call` 事件（同一次调用、同 `callId`），时间线取后者；`tool/result` 自己不带工具名，按
  `callId` 从调用那条补上。
- **完整优先，但必须有上限**：不认识的类型也照原样压成一行 JSON 摆出来（`llm/retry`、`command/run`
  之类不该消失），而单格文本、整页文本总量、单页条数都有上限；被截的格子记下原长度并单开一条
  `GET /transcript?id=…&from=<那一条>&limit=1&maxChars=…` 把原文取回来。坏行不当作整份失败：报条数
  与行号，其余事件照旧（`problems` / `problemCount`）。
- **计数只扫行头**（`^\{"type":"`），不解析正文：整库是几百 MB，而"共几条、几类各几条"是页头那行字的
  全部依据；只有 `user/message` 需要多解析一次（要按 `source.kind` 分辨"人发的"与"标题模型那次合成
  的"）。
- **端点**：`GET /transcript`（一次性 JSON，只读、按事件位分页、只读**最高代次**那一份日志——宿主自己
  也是这么挑的）。三处拒绝在流/响应体里说清楚：没给 id（400）、库里没这条（404）、整份读不出来（422）。
- **界面**：会话页每行一枚「内容」（在行尾那一格、悬停才出场，见
  [行上的动作等悬停](../architecture/2026-10-12-row-action-waits-for-hover.md)），点开是官方 `Modal`
  里的时间线：按种类筛选、按回合分节（节标题点一下就折起来；节的边界取自日志自己的 `turn/start`
  与 `turn/end`，不属于任何回合的会话级事件自己一段、没有标题可折）、`seq`/时刻/事件类型逐条标出、
  思考折起、工具调用与结果各占一块、被截的格子给「看全文」。节标题贴顶（滚进这一回合时它自己停住），
  右端写着这一回合几条与起止时刻，底色取卡片同一层——用 `bg-base` 在深色主题下会横出一条比卡片更黑的
  色带；页头写着已读与总数。
  正文滚到贴底就自己往下接（底部没有按钮，也没有结束语）；这一页撑不满一屏
  时"滚到底"永远不会发生，所以读完每一页还要复查一次。弹窗正文层自己写字号，不继承文档
  根的 16px（见 [弹窗正文层的字号](../bug-fix/2026-10-12-dialog-body-declares-its-own-type.md)）。
- 「内容」那枚按钮落在行 `<label>` 里，所以点击时 `preventDefault()`：标签的默认动作是把这次点击转
  给勾选框，而"看内容"不该顺带改变勾选状态。

## Alternatives considered

- **让宿主提供这条内容接口**（`sessionQuery.readSession` 之类）：那要先把会话挂进宿主内存（或至少要求
  它是宿主认得的会话），于是侧边栏看不见的那些——空会话、孤儿目录、导入的 Codex 会话——正好全都看不到，
  而它们恰恰是最需要这个视图的那批。宿主那条路留给标题重算（见
  [重新生成标题](2026-10-12-retitle-attaches-the-session-to-ask-the-title-service.md)），那里确实需要
  活会话。
- **一次把整条会话读给浏览器**：6 MB 的会话解出来是几万条事件，浏览器拿到只会卡死；分页与单格上限是
  这条路的必然代价（用户仍能「看全文」，只是按条取）。
- **按内容块拆条目**（一条助手消息拆成"思考""正文""工具调用"三条）：读起来更顺，但条目与事件不再
  一一对应，"看这一条的原文"就没法指认了；现在把块放在同一条里分格，两种好处都留。
- **底部摆一枚「加载更多」，读完再补一句「已到日志末尾」**：往上接这件事在人滚到底时已经表达了，按钮
  只是多一次点击；那句结束语说的是"日志读完了"，筛选之后它与"这一屏到头了"混在一起（分界是页头那行
  「已读 N / 共 M 条」）。整条底部因此都不摆东西：关掉靠标题栏那枚 ×，往下接靠滚到底。
- **按 `turn` 字段把条目分堆**（相邻且 `turn` 相等就并成一节，第一版就是这么切的）：真实日志里 `turn`
  只有一部分事件带（`turn/start`、`step/start`、`system/message` 有，`user/message`、工具调用与结果、
  `agent/inbox/spliced` 大多没有），于是同一回合被劈成好几节、标题重复出现，折起来还会把同一回合的另
  一半留在外面。边界改由日志自己给。
- **不认识的类型一律不显示**：那"完整"就成了一句空话——`permission/preset`、`llm/retry`、
  `compaction/prune` 恰恰是排查时最先要看的东西。

## Consequences

- 核心层多一个纯函数模块，视图读到的是它解析出来的结果，所以"界面上看到的"与"日志里写的"只隔着一层
  解析。它也**不引 `src/types.ts`**：那个模块带着
  宿主侧的 node 类型，一条 `import type` 会把整份声明拖进客户端的编译单元（第一版就是这么撞上
  `Cannot find name 'Buffer'` 的），所以 header 只在自己这边声明用得到的那几个字段。
- 视图的效果是"任何时候都能回答日志里写了什么"：新建会话、导入会话、归档会话、子智能体，一视同仁。
- 上限是**显式**的：界面会写出"截断了 N 个字符"与"有 M 条读不出来（第几行）"，而不是悄悄少给一点。
- 用例钉住的是边界：分页不重不漏（坏行跳过时游标照样前进）、码点截断（emoji 不会被切一半）、整页
  文本总量到顶时把下一条留给下一页、工具名按 `callId` 配对、坏行的行号按原始文件算、上限参数被夹到
  合法范围。
