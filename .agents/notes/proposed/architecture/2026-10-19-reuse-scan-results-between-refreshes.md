# Agent Note: 库没变时复用上一次的扫描结果

Status: proposed

## Problem

设置页一打开就要扫整库（`GET /state`：走遍项目目录、读每条会话的日志头、再从宿主的投影缓存里取标题与
空白判据）。本机真实库上的规模：23 个项目目录、994 条会话、1003 个日志文件，日志合计 619 MB，宿主的
投影缓存 1003 个文件、合计 169 MB（平均每个 173 KB）。

页缓存预热之后，各项各跑三次取范围：

| 步骤 | 耗时 |
| --- | --- |
| 走目录 + `stat` 每个日志 | 13–17 ms |
| 整份读日志 + 解首帧 | 303–306 ms |
| 只读日志前 64 KB + 解首帧 | 192–195 ms |
| 只读投影缓存（不解析） | 347–370 ms |
| 只读投影缓存 + `JSON.parse` | 678–768 ms |
| 只 `stat` 投影缓存 | 3–4 ms |
| `scanAll()` 不带标题 | 356–366 ms |
| `scanAll()` 带标题 | 1036–1096 ms |
| 再加逐条判空白（＝现在 `/state` 扫库这一段） | 1741–1799 ms |
| 问 git 项目身份（23 个目录、并行、进程内首次） | 351 ms |
| 按指纹比对一趟 + 直接复用上次结果 | 21–25 ms |

三个结论：

1. **同一个投影缓存文件每条会话被读两遍。** 标题在扫的那一趟读（`createTitleResolver`），空白判据在
   `summarizeSessions()` 里又读一遍（`createBlankResolver`），同步那条路还要读第三遍（`sessionMeta`）。
   每次都是 678–768 ms，读完就丢。
2. **日志读多了。** `scanProjectDir()` 用 `readFileSync()` 把整份日志读进来，却只解首帧。首帧实测
   168–299 字节（中位 212），1003 个文件没有一个超过 64 KB。为了这 212 字节，每次扫要读 619 MB。
3. **每次刷新都从零再来。** 上面这些没有任何一处记住上次的结果，所以打开页面、点刷新、切页签回来，
   每次都要重做一遍。

## Proposal

### 一、少读（已交付，见 [扫描时每样东西只读一次](../../implemented/architecture/2026-10-19-scan-reads-each-thing-once.md)）

下面这两条已经做完，留着是为了说清这次缓存建在什么之上：扫描本身现在只读一遍日志开头（64 KB）与每
条会话一份投影记录。

- 读日志头改成**只读文件开头**：先读 `min(size, 65536)` 字节，`readHeaderQuick()` 解不出来（假边界、
  首帧异常大）时再整份读回退。实测 `303–306 ms → 192–195 ms`，读的量从 619 MB 降到 63 MB。页缓存
   冷的时候省得更多。
- 投影缓存**每条会话只读一趟**：标题、空白判据、`lastPromptAt`、`lastMessageTime` 一次取出，扫描结果
  里带着这几样；`summarizeSessions()` 与同步计划读扫描结果，不再各自去读文件。实测 `/state` 扫库这
  一段 `1741–1799 ms → 1036–1069 ms`。

### 二、记住上一次的结果

把上一次扫描的结果留在内存里（进程内，一个插件实例一份）。下一次扫描先做一趟**指纹**：

- 走目录得到"有哪些会话目录、每个目录里有哪些日志"（这一趟本来就要做，`readdir` 很快）；
- 每个日志文件记 `size` + `mtimeMs`；
- 每个投影缓存文件记 `size` + `mtimeMs`。

指纹与上次一致就直接返回上次的结果，不一致就重新扫并更新缓存。实测指纹这一趟 `21–25 ms`，命中之后
直接返回，重复打开因此从 `1704–1739 ms` 降到 `21–25 ms`。

三个细节：

- **只认 `mtimeMs` 与 `size`，加 inode 不够。** 实测把一份日志原样写回（字节完全一样）：`size` 不变、
  inode 不变，只有 `mtimeMs` 变了。所以判据里必须有 `mtimeMs`。
- **粗粒度文件系统上保守一点。** 有些文件系统的 `mtime` 只有 1 秒精度（本机实测是亚毫秒）：同一秒里
  改两次、大小又一样时指纹看不出来。做法照 git 的 racy 处理：`mtimeMs` 落在"上一次扫描开始时刻"之后
  1 秒以内的文件，这一次一律重读。库静止时这条不触发；正在写的会话每次重读一两条。
- **根路径变了就整份作废。** 配置允许改写 `sessionsRoot` / `registryPath`，缓存按这两枚值分组（或者一
  个插件实例一份，配置改了重建）。

### 三、自己写完就作废

迁移落地、回滚、导入落地、同步拉取、删除、重新生成名称这几条路写完盘之后，显式把缓存作废，不等指纹。
指纹理论上也能发现（这些写操作都会改 `mtime`），但"我自己刚写完"这件事不该靠推断：显式作废让"写完之后
界面一定看到新结果"不依赖文件系统的精度。

## 另外一条路：宿主内存里的投影（量过了，不是那笔大钱）

宿主的 `ctx.sessionProjectionCache.cachedSnapshot(header)` 在它自己的会话列表里是零 I/O 的：服务启动时把
整个 `session_projcache` 域读进内存，列会话时从内存里取。按它自己的说法，这是"as stale as the last
durable checkpoint but never wrong"。

但它在真实宿主上**只服务一部分投影**。2026-10-19 在一份 996 条会话的库上实测：不带 keys 读一条记录，
返回的键是 `title`、`goal`、`tokenUsage`、`contextPressure`、`contextBreakdown`、`inbox`、`sessionStats`、
`turnOutline`、`agentPreset`、`userQuestions`、`permissions`、`workingDirectory`、`subagent*`、`todos`、
`plan`——**没有 `sessionListMetadata`，也没有 `timeContext`**。

而这两个键在磁盘上是有的：每个记录文件的 `rows` 里都有 `sessionListMetadata`（`ver: 1`）与
`timeContext`（`ver: 2`），与宿主里那份单元的 `stateVersion` 也对得上。宿主那一侧只服务"这次注册过
`wire`"的单元，而在投影缓存看到的那个注册表里，这两个键不在服务的集合里。所以在**空白与两枚活动时间**
上，这条路给不出东西。

也就是说，它只能替掉**标题**这一半。而在"文件反正要读一遍取空白"的前提下，三种做法是：

| 做法 | 每条的缓存文件读 | 宿主调用 | 评价 |
| --- | --- | --- | --- |
| 现在的代码（标题、空白各读一趟） | 2 趟 | 0 | 对，但读了两遍 |
| 标题走宿主、空白读文件 | 1 趟 | 1 次 | 省掉一趟，但多一个数据来源与一套身份校验 |
| 标题与空白都读文件、但只读一趟 | 1 趟 | 0 | 同样省掉一趟，判据只有一处 |

最后两行省掉的是同一趟 169 MB 的读，而第三行少一个数据来源、少一套"两边答得不一样怎么办"的处理。所以
**这条路不该单独做**：它做不出比"每会话只读一趟"更好的结果，却要多维护一条判据。

另外两枚实测数字留着备查：那次 A/B 里宿主调用一共 3 600 次、合计 684 ms（≈0.19 ms/次，机器当时负载
偏高），其中 45 条会话宿主说"没有这条记录"（要退回读文件）。

## Alternatives considered

- **只做"少读"，不做缓存。** 改动最小、风险最低，但重复打开仍是每次约 1 秒（实测带标题 1036–1069 ms），
  达不到"打开就出来"。
- **把扫描结果落盘，跨进程复用。** 宿主重启之后第一次也快；代价是自己管版本号、原子写与损坏兜底，而
  收益只在"刚重启"那一小段。
- **用 `fs.watch` 监听变化，省掉指纹那一趟。** 省下的是 20 毫秒，换来的是事件丢失、重命名、溢出这些
  要处理的情况，相对 1.7 秒不值。
- **指纹里加内容哈希。** 那等于把文件读一遍再比，省不下读的量。
- **用宿主 `sessionPersistence.list()` 代替自己走目录。** 它每次仍要逐条读 header（内部有限并发），省
  不到读的量，还会把"哪条会话在库里"的判据让给宿主——现在这条判据（临时文件、坏目录怎么跳过）是本插
  件自己的。

## Acceptance criteria

- 库没有改动时，第二次及之后的 `GET /state` 扫库这一段在 100 毫秒以内（本机 994 条）；第一次不比现在慢。
- 追加、改写、删除、新增任意一条日志或任意一条投影缓存之后，下一次扫描必须反映新内容：每类一条用例，
  改完立刻再扫一次，断言结果变了。
- 本插件自己写完盘的几条路（迁移落地、回滚、导入落地、同步拉取、删除、重新生成名称）之后，下一次扫描
  不得返回写之前的结果；每条路一条用例。
- 指纹命中与不命中的两次扫描，结果逐字段相等：会话集合与顺序、每条的头字段、标题、空白判据、文件清单
  与字节数。
- 库静止时连续扫两次，第二次不再读任何日志与投影缓存文件（用一个记读次数的桩钉住）。
- `pnpm typecheck && pnpm build && pnpm test && pnpm check:package` 全绿；真实 dev GUI 上量一遍打开设置
  页到列表出现的时间。

## Risks

- **"改了但指纹没变"会静默返回旧结果。** 判据是 `size` + `mtimeMs` + 目录清单，粗粒度文件系统上同一秒
  内的两次改动可能漏判。缓解是上面那条 racy 规则；同时要把幂等性写进注释——这个缓存只影响"看到多新"，
  不影响写盘。
- **外部写者。** 读文件那条路看得见别的进程写的改动，宿主内存表那条路看不见，要等一次 checkpoint。
- **内存常驻。** 994 条的 header、标题与文件清单约几 MB（几百 MB 的日志不会被缓存，只缓存 header）；
  库规模变化大时要有丢弃上限。
- **指纹那一趟随文件数线性增长。** 现在 2000 个文件约 20 毫秒，库大十倍是 200 毫秒，仍远小于 1.7 秒，
  但实现时要用一个数把它记下来。
- **两处判据必须同一个口径。** 指纹的"有哪些日志"与扫描的"有哪些日志"要用同一个函数
  （`parseSessionLogName()`），否则会出现"指纹说没变、扫描却扫出别的文件"。
