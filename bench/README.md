# 性能基准

这个目录回答一个问题：**这次改动会不会让用户等得更久、卡得更厉害？**

它跑的是真实代码：真的 `createApiHandlers()`、真的扫库、真的压缩日志、真的夹具 WebDAV。规模对着
维护者本机会话库取（默认 400 条 / 约 36 MB 压缩，最大一份日志解开 12 MB；`full` 档 1200 条 / 48 MB）。
每次改动跑一遍，与提交在 `baseline.json` 里的数字比：**停顿不得超过预算，归一化后的耗时不得比基线慢
25% 以上**。

## 怎么跑

```sh
pnpm bench              # 默认档（约 10 秒）：合并前跑这一条
pnpm bench:small        # 80 条会话，改一行想快速看一眼时用
pnpm bench:full         # 1200 条 + 48 MB 的大日志，发版前或怀疑大会话库退化时用
pnpm bench:update       # 有意变慢（换了实现、多了功能）时重写基线，并在 PR 里说明
pnpm bench -- --only sync.preview,scan.cold    # 只跑某几个场景
```

退出码：通过 0；有场景超预算或比基线慢 1 + 容差 就 1。`--tolerance 0.4` 可临时放宽（默认 0.25）。
`--json` 输出机器可读结果，`--list` 列出场景。

## 量的是什么

每个场景独立起一个**子进程**（冷缓存、独立 RSS、互不污染），报三样：

| 列 | 含义 |
| --- | --- |
| `wall(ms)` | 这一段动作的总耗时（中位数；冷场景只量一次）。 |
| `相对基线` | 先除以校准耗时，再与基线比。跨机器比较靠这一步，见下。 |
| `停顿/预算` | **最长一次主线程停顿**（`monitorEventLoopDelay` 的直方图最大值与 5 ms 心跳取大）。这一列对着 AGENTS.md 的阻塞预算判。 |
| `RSS(MB)` | 峰值常驻（`process.resourceUsage().maxRSS`），只记录、不判定。 |

为什么停顿是主角：这个仓库的预算按"用户点一下会不会卡"划线。总耗时 800 ms 但每 5 ms 让出一轮，用户
只看到进度条；总耗时 120 ms 但中间按住主线程 120 ms，界面整个僵住。预算：启动期小活 10 ms，其余
"用户会等"的地方 50 ms。

## 场景

| id | 量什么 | 预算 |
| --- | --- | --- |
| `calibration.cpu` | 固定 CPU 活（sha256 × 4 × 24 MB），用来把机器快慢归一化 | — |
| `plugin.register` | 插件 `apply()` 里注册 6 个工具 | 10 ms |
| `scan.cold` | 冷启动后第一次扫完整库（`scanAllAsync`） | 50 ms |
| `state.cold` / `state.warm` | `GET /state` 第一次 / 第二次（后者走扫库缓存） | 50 ms |
| `transcript.large` | 打开最大的那条会话（解开 12 MB 日志）第一页 | 50 ms |
| `transcript.page` | 同一条翻到第 2000 条（走日志缓存） | 50 ms |
| `export.20` | 导出 20 条会话 | 50 ms |
| `import.plan` / `import.apply` | 导入预演 / 落地 20 条（落地在库的副本上做） | 50 ms |
| `migrate.preview` / `migrate.apply` | 迁移预演 / 落地 20 条（落地在副本上做） | 50 ms |
| `delete.preview` / `delete.apply` | 删除预演 / 落地 20 条（先备份再删，副本上做） | 50 ms |
| `sync.preview` | 同步预演：扫本机 + 读远端索引 + 三对"两边各自写过"的内容比对 | 50 ms |

写操作（`*.apply`）跑在**复制出来的库**上，测完就删：基准绝不碰夹具本体，也不碰你的真实会话库。

## 夹具

`bench/fixture.mjs` 生成，按 profile 缓存在 `bench/.work/<profile>/`（不入版本库）。同样的种子与生成器
版本 → 逐字节相同，所以基线才有可比性；生成器改了会作废重来。

形状对着真实库取：

- 400 条会话分在 24 个项目目录，60% 很短（40–300 条事件）、35% 中等、5% 很长；
- 第一条是"最大的一份日志"：解开 12 MB（`full` 档 48 MB），第一帧只有 header，之后每 12 条一帧、
  逐帧 zstd 压缩（宿主就是这么写的——迁移改写首帧的前提）；
- 每条会话配一份宿主投影缓存记录（标题、空白、两枚活动时间）；
- 一张注册表，带着工作区与归档集；
- **远端那一格用生产代码推上去**：从"另一台机器"的库跑一次真 `runSync({apply:true})`，索引与包因此
  是真实格式。远端有本机也有的（内容一致）、只有远端有的、以及三对"两边各自写过"。

## 基线怎么读

不同机器快慢不同，所以**不直接比毫秒**：每个场景先除以同一次运行里的 `calibration.cpu` 耗时，得到一个
与机器无关的比值，再与基线里同样算出来的比值比。基线里同时存了绝对的 `stallMs` 与预算，那一列是
绝对判定（停顿是代码结构问题，不该随机器放大）。

基线由 `pnpm bench:update` 写入 `baseline.json`（按 profile 分别存）。更新它等于承认"这次是故意变慢"：
PR 描述里要写清慢在哪儿、值不值。

## 加一个场景

在 `bench/scenarios.mjs` 里加一项：

```js
{
  id: 'my.scenario',
  title: '一句话说明量的是哪一下',
  budgetMs: 50,          // 允许的最长停顿；纯 CPU 校准类场景写 undefined
  iterations: 3,         // 冷场景写 1
  async prepare(context) { /* 不计入耗时：造数据、预热缓存 */ },
  async run(context) { /* 被量的那一段；顺手 assert 它真的走到了要测的路 */ },
  async teardown(context) { /* 清理 */ },
}
```

`run()` 里一定要断言"结果形状对"——否则一个报错分支也能测出一个漂亮数字。用 `bench/http.mjs` 的
`call()` 打真实 handler，或直接调编排函数。

## 限制

- 不测浏览器渲染与网络：那是浏览器与宿主的事，这个仓库能管的是宿主进程里的耗时与停顿。
- 夹具 WebDAV 在本机回环上，网络延迟不真实；同步场景测的是解析、比对与落地那段 CPU。
- 停顿用直方图 + 心跳，分辨率 1 ms；个位数毫秒的差异不必当真。
- 冷/热口径写在各场景的 `iterations` 与 `prepare` 里：冷场景只量一次，热场景先预热再量。
